# Architect ruling - S6-02a/S6-02b packet questions

Decision: `D-2026-10-16-s602-questions`. Applies `D-2026-10-16-s6-verification` and `.agent/architect-A-S6-verification-answers.md`. These are contract choices for the two implementation packets, not owner visual acceptance.

## S6-02a

1. **Amend the proposed fixture-calibrated bands.** Freeze the following version-1 bands in every plan before any later report: later total feeder-demand energy and later total PV-available energy must each be within 10% of the corresponding baseline total, inclusive; initial battery SOC must be within 2 percentage points, inclusive. Integrate the accepted five-minute feeder-demand and `pv_available_power` values as kWh over each 60-minute window. Use PV *available* power so policy-driven curtailment cannot make the comparability input appear to change. When a baseline energy total is zero, require the later total to be zero; missing, negative, ambiguous or non-finite inputs fail comparability to INCONCLUSIVE. Compare exact decimal/rational values before display rounding. Site, asset, model, roles, cohort rule and clock basis remain exact-match requirements; no evaluator or fixture may widen these bands after freeze. **Packet change:** replace question 1 with these numbers, channels, zero rule and arithmetic; pin them in the plan/API fixture and test inclusive edges, just-outside edges and zero baseline.

2. **Amend the proposed slot convention.** Align both windows to UTC five-minute boundaries; each is exactly twelve half-open slots `[t,t+5 min)`. For each power role require one accepted, time-valid slot value covering the whole slot, or accepted non-overlapping subinterval values that exactly partition it. Integrate `kW * covered seconds / 3600` for load, PV, requested and delivered critical power. Point samples alone do not establish a slot's energy; require the public report's declared interval semantics and refuse gaps, conflicting overlaps or interpolation. For SOC, require an accepted sample at every slot start and at the window end; the start sample represents that slot for the five-minute reserve-breach count, and the end sample is terminal SOC. Compare the time-valid reserve at each slot start; a reserve change inside a slot makes that slot unassessable under this version. Count 300 below-reserve seconds for each slot whose start SOC is below its reserve. Display this as a five-minute sampled guardrail, not proof of continuous physical SOC. No sample may be carried across a missing boundary. **Packet change:** state this convention in coverage, evaluator, Lab profile and evidence API; add boundary/partial-slot/conflict and missing-terminal tests.

3. **Accept with an explicit cutoff.** A replacement gets a new immutable plan ID and `supersedes_plan_id`; it may reuse the same baseline and later UTC bounds only while no later-window report has been accepted and no later run has begun. After either event, use a new later window and a new plan ID; an idempotent retry of the original freeze returns the same ID. Test both sides of the cutoff and keep the superseded plan addressable. **Packet change:** replace question 3 with this rule in plan write/read and tests.

## S6-02b

1. **Amend the proposed copy to a short interim label:** `Trial missed a safety or service limit`. Show the failed metric, value, threshold, unit and evidence IDs beside it, and retain `INEFFECTIVE` as the typed outcome. Use this label only for a measured reserve/service `GUARDRAIL_FAIL`; a target-only miss reads `Target not met`. If another required fact is unknown, show `Could not conclude` with the known failure in details. The owner has deferred the general plain-language status-copy pass to one W1-conclusion task. **Packet change:** specify these interim strings and variants in the outcome matrix; do not broaden this slice into a copy review.

2. **Accept the latest-current default.** Without an explicit outcome ID or recorded cutoff, open Verification on the latest current read state, including PENDING or REASSESSMENT_PENDING after withdrawal. Give the prior outcome an explicit historical link. An explicit historical selector stays in the URL across child links/reload and shows the selected immutable outcome with a prominent `Historical` label and its separate current state; it never turns the old VERIFIED into a current badge. Conflicting selectors remain typed errors. **Packet change:** replace question 2 with these route/default/history assertions and owner walkthrough cases.

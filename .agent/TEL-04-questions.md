# TEL-04 builder questions (2026-10-27)

Items the spec does not cover. Each is left unhandled in code (no design chosen); the Architect decides.

Status: ruled 2026-10-27 by the Architect (Claude); see TEL-04-Q1..Q5 and TEL-04-Dev1..3 in the spec resolutions (section K). **Q1, Q2 and Q3 need code changes before review; Q4 needs one test assertion.** Q5 and Dev1..3 are accepted as built.

**TEL-04-Q1. Gateway unavailable before START.** `GatewayUnavailable` from `identity` (check_identity) or from `release_previous` is not mapped to an exit code (exit 4 is defined only "at 10 consecutive publish instants"). Today it propagates: traceback, exit 1, no START. Should it be exit 4, exit 2, or a retry?
   **Ruling TEL-04-Q1 (Architect, Claude): change.** Any `GatewayUnavailable` before START (from `check_identity` or from `release_previous`) exits **4**, with no retry in process. Note that `read_credential` (`ipc.py:135-143`) raises `GatewayUnavailable` for a missing or unreadable credential file too; that is still exit 4, because the gateway writes that file when it starts, so a missing file means the gateway is not up yet. Behaviour: print one stderr line `FIELD-POLLER gateway unavailable before start: <detail>`; print no START line and no EXIT line (Q4); do not write or rewrite `session.json`. Because `session.json` is untouched, the next start retries `release_previous` with the same previous reference. Restarting is the supervisor's job (TEL-08 runbook, TEL-07). Tests in `host/tests/test_field_modbus_tcp_proof.py`: (a) a subprocess run of `_offline_command(...)` with `--stop-at` (missing credential, no pipe) gives returncode 4, `start is None`, `exit_line is None`, stderr contains `gateway unavailable before start`, and `state/session.json` does not exist; (b) an in-process `modbus_poller.main([...])` with a pre-written `state/session.json` `{"session_ref": "<old ref>", ...}`, `GatewayPublisher.check_identity` monkeypatched to return `{}`, and `GatewayPublisher.release_previous` monkeypatched to raise `GatewayUnavailable("test")`, returns 4. Its captured stdout has no `FIELD-POLLER START`, and `session.json` is byte-identical to what was written.

**TEL-04-Q2. Gateway unavailable at the final seal.** After `--stop-at` the poller calls a final `seal_and_release`. A `GatewayUnavailable` there propagates (exit 1, no EXIT line). Exit 4? Retry?
   **Ruling TEL-04-Q2: change** (applied together with Q3). `GatewayUnavailable` at the final step exits **4** after `--stop-at`, not exit 1. Stderr gets one `FIELD-POLLER gateway unavailable at the final seal: <detail>` line. `status.json` is rewritten, and the EXIT line is printed as `FIELD-POLLER EXIT 4 <status>`, with `retained_reports` = the texts still held. There is no in-process retry: replay windows are bounded and the gateway's state is durable, so the next session's `release_previous` seals and releases what did land. `GatewayRequestRefused` at the final step stays exit 3, as built. The test is under Q3.

**TEL-04-Q3. Retained texts at `--stop-at`.** If the last publish instant(s) hit `GatewayUnavailable`, the retained texts are not admitted before the final `seal_and_release` (the spec names only the seal). They are counted in `status.retained_reports` and lost. Should the final step admit the retained texts first?
   **Ruling TEL-04-Q3: change.** The final step (loop step 5) admits the retained texts first. Factor it as `Poller.finish() -> None`, which `run()` calls after the schedule. Order: `clock.sleep_until(stop_at)` if `stop_at` is set; then, if `self.retained` is non-empty, `admit(retained texts, in order)`. That call goes through the same code path as `publish`: it counts toward the crash hook's `admit_calls`, `_count` tallies the admissions, HOLD lines print, and `retained` is cleared. Then `seal_and_release` and `_sealed`. On `GatewayUnavailable` at either call, `retained` is kept unchanged and the step raises `_Stop(4)` (Q2). `consecutive_unavailable` is not consulted here. Re-admitting texts that had already landed gives `ALREADY_ADMITTED`, as in step 4. Tests in the proof file drive `Poller.finish()` in process, with a `GatewayPublisher` over `field_fixtures.FakeLink`, a dummy client, a `tmp_path` state dir, and `stop_at=None` or a past instant: (a) `retained` holds 2 texts and the script answers `admit` → `[ADMITTED, ALREADY_ADMITTED]`, `seal` ok, `release_run` ok. Then `link.ops == ["admit", "seal", "release_run"]`, the admit body's `reports` equal the 2 texts in order, `retained == []`, and admissions are `ADMITTED 1, ALREADY_ADMITTED 1`. (b) `admit` raises `GatewayUnavailable`: `_Stop` code 4, `link.ops == ["admit"]`, `len(retained) == 2`, and `write_status()["retained_reports"] == 2`. (c) `retained` is empty and `seal` raises `GatewayUnavailable`: `_Stop` code 4 and `link.ops == ["seal"]`.

**TEL-04-Q4. EXIT line on exit 2.** Configuration refusals before START print only to stderr; no `FIELD-POLLER EXIT 2 ...` line (there is no status file yet). Exit 3/4 after START print EXIT with the status. Confirm.
   **Ruling TEL-04-Q4: confirmed, with one test assertion added.** An EXIT line is printed if and only if START was printed. Every exit before START prints stderr only, with no status file and no EXIT line: exit 2 (configuration), exit 3 (`SEAL_REFUSED`/refusal in `release_previous`) and exit 4 (Q1). After START, exits 0, 3 and 4 print EXIT with the final status. Exit 9 (crash hook) prints nothing, by design. Test: `test_replay_without_stop_at_and_a_crash_hook_off_simulated_exit_2` also asserts `exit_line is None` for both runs. The Q1 tests assert the same.

**TEL-04-Q5 (confirm interpretation, implemented).** Gate 7 says the harness reads diagnostics "just before" the pause. The PV interval ending at the pause start (07:15Z) can only be admitted after 07:15Z (its publish instant), so a read strictly before the pause would see PV contact move. The harness reads after the last pre-pause publish (`status.last_publish_instant == 07:15Z`) and again >= 3.5 s wall later. Confirm.
   **Ruling TEL-04-Q5: accepted as built.** Checked against the harness `tick` in `test_faults_follow_the_table`. The PV interval ending 07:15Z can only be admitted at its 07:15Z publish instant. A read strictly before the pause would therefore see PV contact move, and the gate would test the wrong thing. The gate's intent is "contact stops moving while paused". The earliest point where contact is final for the pause is after the last pre-pause publish: `status.last_publish_instant == 07:15Z`. The second read must come ≥ 3 s of wall time later; ≥ 3.5 s is built. The built guard asserts that the second read still saw `last_publish_instant == 07:15Z`, which keeps both reads inside the pause. The gate 7 wording is corrected in the spec (TEL-04-Q5). No code change.

## Declared deviations (review packet "Known deviations" 1-3)

**TEL-04-Dev1. FakeCentral responder.** Ruling: **accepted as built, with a spec correction.** Q-T46's single responder `(200, receipt_text(body))` was a spec error. `deliver` also runs the gateway's diagnostics pass, and `receipt_text` refuses a diagnostic payload (`UNKNOWN_FIELD clock_offset_ms`). The built `with_diagnostics` gives batch-route posts to the Q-T46 responder. It answers posts whose path ends `/diagnostics` with the `test_gateway_upload.py:503-506` shape: 201, `diagnostic_id`, `received_at`, `payload_sha256`. It asserts on any other path. DROP applies to the first two **batch** posts, and gate 6 counts batch requests only. TEL-05 keeps its real `BatchIngestionService` responder for the batch route and uses the same diagnostics answer. No code change.

**TEL-04-Dev2. Deliver loop.** Ruling: **accepted as built, with a spec correction.** "`deliver` until `attempted == 0`" ends while dropped batches still wait out their 5 s back-off. The built `deliver_all` repeats the loop. After each pass it sleeps 1 s, until `diagnostics.queue.sealed_pending_batches == 0`, and asserts (a test failure, not a silent return) at 120 s. That assertion is correct, and it is the harness's delivery rule from now on: TEL-04, TEL-05 and TEL-05b all use `deliver_all`. No code change.

**TEL-04-Dev3. Gate 7 read timing.** Ruling: the same as TEL-04-Q5, **accepted as built**. No code change.

In plain words

  • Today the app is fast only for pages it has already made. Each page is built from many small database reads, one after another, which takes 1 to 24 seconds (up to 56 s while the background is busy). The finished page is stored and served again in about 0.1-0.2 s. To make that happen before you look, a background crawler requests about 1,900 pages after every data change. A page that is not on its list is slow.
  • The crawler is a symptom, not the design. The design you accepted on 2026-11-03 (AG-20: "snapshots are the primary read source") says: compute each day's results when the data arrives, and build any page by adding up stored days. That was built for day grades and for six board parts. The rest of each page is still computed when someone looks, so the page store and the crawler became the real speed mechanism.
  • Recommendation: finish the design you asked for, in stages. Results are stored per Site and per period when data lands. Each page reads and adds those up. Each Site has one cheap version number, which replaces today's 80-230 ms check. A small cache keyed on that version stays, but the crawler goes. Background work moves to its own process.
  • Target (not yet measured): any range on any Site page in about 0.5 s on first view, and Portfolio in about 0.8 s, with no pre-loading, for every Site type. The design is meant to hold from 4 Sites to about 100 Sites without a redesign, with a clear further step for 1,000+. The rows built so far cut the board from 11 s to 2.7 s; the targets are proven stage by stage, not promised up front.
  • Effort: about 13.5 lane-units over 7 stages, including cold-chain and EV. Nothing changes before the walkthrough or the 17 Nov client demo. The work changes the database and the stored pages, and you asked for the walkthrough to run on a clean, good database. The one candidate quick step (the crawler in its own process) has measured risks and needs a rehearsal first, so it moves to after the walkthrough.

2. Root causes (structural, not symptoms)

R1. Cost grows with the number of possible URLs, not with the data

The store keeps one finished body per (route, parameters, language, Site set, W, code version). Every distinct page is its own piece of work. For 4 Sites and about 30 days, that is already about 1,900 crawled requests. For any from/to range, the URL space is unbounded: a year of days has about 66,000 possible ranges per Site. Whatever the crawler does not request is a full compose.

Key: response_store.py:82-88 (request_key). Crawl lists: var/polish_walk1113/prebuilt-routes.json (167 entries + financials follow-ups = 218), warm-report.json (47 ranges, 1,672 requests, labelled "WARM-1 (D-17N.1; reverses D-ANY.3 for the 17 Nov build only)").

R2. Invalidation is far coarser than the change

W is one count per Site over 84 input tables. One new reading writes about 12 change rows (1.56 M change rows for 131 k readings). Any write to the Site invalidates every stored page of that Site, for every day and every range, even when only one day changed. A quiet tick can still write: Kisiwa's fuel_night processed 7 rows at 08:15 with no new data. Amplifier: about half of the change rows come from bookkeeping tables (recompute_job, event_outbox, event_consumption, analytic_run_evidence). They move W when no business data changed. Option C must decide, table by table, which writes bump the version. Any code change invalidates everything, because the code version is in the key. After this morning's deploy, re-storing took 11 minutes for the prebuild and about an hour for the ranges.

chain/watermark.py:1-27; change rows by table (read-only SQL): mini_depth_revision_evidence 474 k, analytic_run_evidence 386 k, recompute_job 191 k, event_outbox 151 k, accepted_evidence 131 k. Code version: chain/watermark.py:11-22.

R3. Every hit pays a validation cost that grows with history

Each request counts the Site's change rows before it can answer: 158 ms for Kobo today, up 50% since yesterday, and growing with every reading forever. A plain counter would answer this in about 1 ms. A max(change_id) shortcut is not safe: ids are handed out at insert time, not at commit time, so a lower id can commit after a higher one has been seen. That is why the count was chosen (W1).

postgres_response_store.py:41-53 (the reviewer re-measured 125 ms); rationale migrations/versions/0047_chain_response.py:9-14. Measured max(change_id) read: 1.1 ms (shown for scale only, not proposed).

R4. Pages are composed from near-raw tables, one read after another

A board runs 15-20 read families in sequence. The Portfolio re-derives evidence, money and Findings per Site-day. The outcome summary rebuilds each Site's whole board instead of reading stored results. The stored day results that do exist are fast (2-160 ms), but most page parts do not read them. This is the part the 2026-11-03 design meant to remove.

site_outcomes/read.py:438 (compose), :693-697; site_outcomes/mini.py:507; estate/portfolio.py, estate/evidence_money.py:476-607 (per-Site loops); read.chain_day 31 ms p50 in the same log.

R5. Background work and users share one process, and the tick polls everything

One uvicorn process serves the owner, 218 prebuild GETs and 4 range-crawl threads, all under one Python interpreter lock and one connection pool (85 connections in use). The tick runs 12 stages for every Site every 2 minutes, about 1 s each, even with nothing to do: 52 s for 4 Sites. The tick caps itself at 5 Sites per run (--max-sites 5, tools/demo_combined.py:79). At 100 Sites, each Site would therefore be visited only about every 20 ticks, roughly every 40 minutes. The visible symptom at scale is staleness, not a long tick.

R6. How it got here: the accepted design was only partly built

The accepted design (AG-20, §11b) says snapshots are the primary read source, the ETag is the latest snapshot revision, and budgets are 1 s cold and 300 ms warm. Under demo time pressure the page store became the lever instead. The steps were: CH5c-R2 option A, then the any-range answer of 2026-11-10 (D-ANY), then WARM-1, labelled a workaround, then D-SR.83, which extended the prebuild to every day. Each step was reasonable for its deadline. Taken together, they turned speed into a crawling problem. The 2026-11-10 answer already named this as the decision to reverse; AR-5, which retires the pre-load list, is still queued.

3. The coordinator's candidate, evaluated

Candidate: build-on-arrival per-Site-day read models. Pages read or add them up, each Site has one version number, rebuilds are incremental, and background work is isolated.

Right What it gets right

  • Compute when data changes, not when someone looks. This is the owner's 2026-11-03 instruction and the accepted §11b design.
  • Much of the machinery already exists and is proven, although the stored row bodies today are page fragments, not parts that add up, so some kinds must be re-shaped (see §4b). There are two stored-row tables with revisions and "as known at k", and an event register that marks (Site, day, kind) dirty. A reader shows a period as PENDING when its input has arrived but has not yet been processed. A parity harness compares old and new output (six kinds: 42 pass, 0 fail).
  • Caveat: every stored kind today is mini-grid only (config/chain/event-register-v1.yaml:40-52).
  • One version number per Site removes R3, and isolating the background removes R5.

migrations/versions/0043_chain_snapshots.py, 0059_site_period_read.py; chain/period_read.py:1-20; config/chain/event-register-v1.yaml; var/polish_walk1113/parity-6kinds-final.json.

Correct What needs correcting

  1. "Per Site-day" is too narrow. Facts need their natural grain:
    • the hour window, for mini depth;
    • the Site-local day, for grades, money lines and claim parts;
    • the Finding revision, for financials and evidence;
    • the thread, for the Finding lifecycle;
    • the month, for billing.
    site_period_read is already keyed by (Site, kind, period).
  2. Ranges are sums only if the facts store the parts that add up. Store numerators, denominators, seconds and amounts. Compute ratios, grades and claim limits when the page is read. Never add across currencies (D-MONEY.3).
  3. The version must follow commit order. Use a counter row per Site, bumped inside the writer's transaction. Do not use max(id) (see R3).
  4. Live lists stay live. Work, actions and thread states change when a user acts. They are small, so they are read in one batched query and they bump the version.
  5. Keep a thin cache. Without one, every view re-adds and re-serialises 200-500 KB. Keep a cache keyed on the version that answers 304, with no crawler.
  6. Building on arrival needs an event-driven worker. With the polling tick (R5), it would be slow at pilot scale.

A. Harden the page store

  • Migration path.
    1. Process split with a connection budget, rehearsed on a scratch copy (the idle-prebuild skip is dropped; see M1 in §8).
    2. A counter migration; W reads the counter.
    3. 304 wiring.
  • Guarantees. All unchanged; the watermark guard and clock guard keep working as they do today.
  • Honest limit. This is the approach the owner questioned on 2026-11-10 ("why a special fast load for demo data only"). At 100 Sites the re-crawl after a deploy is measured in days of CPU (§7).

B. Read models only

  • Migration path. Page part by page part, each behind the existing ASSETOPS_PERIOD_READ_KINDS switch and proven by the parity harness. Retire chain_response at the end.
  • Guarantees. Carried as in §6.
  • Weakness. A Portfolio body is 412 KB. Re-adding and re-serialising it on every view costs 0.2-0.5 s of CPU for something unchanged, and it loses the "stale on outage" fallback (INFRA-1).

C. Read models + thin cache

  • Migration path. As B, but chain_response stays. Its key changes from count to version, and the crawler is switched off kind by kind as each page part moves onto facts.
  • Guarantees. Carried as in §6. INFRA-1 stale fallback kept.
  • Why it is preferred. It is the §11b design, the cheapest to run per view, and it reuses everything already built and proven.

4b. Why the rows built so far have not delivered, and how BL-66 maps onto C

BL-66 (any range under 2 s, no pre-loading) is the same direction as option C, and part of it is built. The board fell from 11 s to 2.7 s. The Portfolio is still at 12-24 s. These are the measured reasons:

  1. Only part of each page moved onto stored rows. On the board, mini depth moved. Dispatch (0.9 s), source (0.57 s), money head (0.6 s) and Findings (0.56 s) are still composed. On the Portfolio, dispatch.day and evidence.claim moved. Money lines and provenance did not: money.lines and MN-1 are parked on task/ANY-2-AR4b, and evidence.provenance is queued.
  2. A second compose hides behind the stored rows. AR-4's evidence rows saved only 2-4 s, because evidence_money.site_data_gap_days_many composes again (.agent/coordinator-handoff.md:109, :132: week 18 → 13 s, and about 13 s is left in the dispatch.day compose path).

5. Target design (option C)

Design rules

  1. The serve path never derives a fact from raw readings. Add an AST and SQL guard: site_outcomes/*, estate/*, site_overview/* and the Finding read routes may read only the fact tables and the declared live lists. The old compose stays as the parity oracle.
  2. Facts store parts that add up; the page computes the ratios. Store kWh, seconds covered and required, amounts in their original currency with a rate_ref, and counts of days by grade. Compute ARPU, cost per kWh, uptime, claim limits and window grades from those parts when the page is read. Today's site_period_read bodies are page fragments (0059:7-8), so the kinds a range sums are re-shaped. This costs a new builder version and a backfill per kind, both inside the stage sizes in §8.
  3. A range is a list of Site-local days (plus native hour windows at its edges where a kind needs them), subject to D5. Coverage already works this way (D-E5.42). dispatch.day and evidence.claim use the UTC s3_day grain today; under D5 they move to Site-local days, proven on aligned ranges by the parity harness, and edge-day differences are reported before any switch.
  4. Every fact kind exists for every Site type the page shows. Today all stored kinds are mini-grid only. Cold-chain and EV get kinds for the board, the range overview and Findings by day (C3b), so one range aggregator serves every Site type.
  5. Invalidation that cannot be forgotten.
    • Builder identity. Each builder's version becomes a hash of its source closure (its module, the pure functions it imports from the project, and its config), computed the way code_version is today (chain/adapters/file_code_version.py:47-53), and joined with a readable label. A check-all guard fails if a hand-written label exists without the hash. A change to any function a builder uses therefore yields a new version, with no human step.
    • Presenter identity. The thin cache keeps code_version in its key, so a change to the read or aggregation code refills bodies on demand, as today.
    • Blue/green per kind. When a builder version changes, its new rows are built in the background while the reader keeps serving the previous version's rows. The reader switches only when the new set covers every period the old one did. History therefore never reads PENDING after a deploy, which would be a visible regression against today's "slow but correct". A period whose inputs changed still reads PENDING until rebuilt; that is the honest-missing rule.
    • Backfill cost (estimate from today's check-only runs: 0.3 s per hour kind and 1.6 s per day kind per Site-day; a rebuild is about 2 s). The demo takes about 2-5 min per kind. The pilot, at 100 Sites × 365 days, takes about 20 CPU-hours per kind, so about 2.5 h on 8 parallel builders. That duration is why blue/green is required at pilot scale.
  6. One version per (tenant, Site), safely.
    • The design. Store the version in a site_read_version row, incremented by the 0047 trigger functions. The row lock gives commit order. An estate route's version is the sorted list of its Sites' versions plus a tenant-wide version.
    • Lock order. A trigger that touches several Sites locks them in sorted Site-id order, then the tenant row last.
    • Short transactions. Builders commit per Site-period, so a long backfill never holds a Site's row lock against user writes such as uploads and operational entry.
    • Which tables bump the version. Bookkeeping tables (outbox, consumption, recompute jobs) stop bumping it once the facts carry their own PENDING state; the fact-input guard records this decision table by table.
    • Fallback if C1 measures contention. Keep the append-only change log for ordering, and let one committer advance the per-Site version from it, as an asynchronous high-water mark. This adds lag of a few seconds but takes no locks in writers.
    • Exit evidence for C1. Lock waits and deadlocks measured under a tick, a builder backfill and user writes running at the same time.
  7. Background never shares a process with users, and multiple user workers come only after process-local state moves out.
    • Lab sessions live in an in-memory dict (host/lab_execution.py:2116).
    • Five file-backed stores lock only within one process (runs/adapters/json_commit_store.py:42, yaml_run_store.py:110, evidence/adapters/json_evidence_store.py:90, analytics/adapters/json_assessment_store.py:42, sites/adapters/yaml_user_site_store.py:73).
    • C5 moves them out, or routes those requests to one process, before --workers rises above 1.
    • Every process gets a connection budget. Today one API process holds about 90 idle connections across about 35 engines, against max_connections 300.
  8. Bodies meet the §11b payload budgets. Long lists (Portfolio scope disclosure about 244 KB, financials evidence) load on demand when their mock element is opened. The element itself is kept. MOCK DEVIATION check Each such change cites the v69 element it lazy-loads and keeps its form. Nothing is trimmed.
  9. Operational alarms from S0, not S1.
    • A builder-stall alarm: a dead worker leaves periods PENDING indefinitely, which is honest but must be noticed.
    • The reader's PENDING-at-k anti-join over the outbox and consumption ledgers (150 k outbox rows today) is timed in C1-C3, because it could grow with history the way R3 did.
    • chain_response (539 MB) prunes rows of dead code versions on deploy, not only at reset or prepare.

Existing pieces reused: chain/period_read.py (PeriodReadBuilder, PeriodReader, PENDING-at-k from outbox and consumption), chain/dispatch_day_rows.py:174-197 (switch and absent-day handling), chain/adapters/postgres_snapshot_store.py, config/chain/event-register-v1.yaml, estate/coverage.py:102-119, 301-313 (Site-local day rule, D-E5.42), response_store.py INFRA-1 _degraded (kept).

10. What needs your decision

D1. Direction. Choose option C or option A.
  • Option C finishes the snapshot design you asked for: results are stored when data arrives, pages add them up, a small cache sits on top, and there is no crawling. It costs about 13.5 units after the demo.
  • Option A hardens today's page store. It costs about 2.5 units, but a range that is not on the list stays slow, and it does not scale.
Architect recommends C.
D2. Before the walkthrough. Architect recommends no change at all.
  • The quick step proposed in the first version had three parts, and each carries a measured risk:
    • a second user worker (Lab runs break, and file stores lose their locking);
    • a separate crawl process (it could exhaust database connections and stall the crawl);
    • skipping idle prebuilds (pages could expire after midnight, or the crawl could run non-stop).
    The first and third are dropped.
  • Your choice is whether a reduced version of the second (R0, §8) may land between the walkthrough and the 17 Nov demo, only after it passes a rehearsal on a scratch copy. Or nothing changes until after the demo.
  • R0 makes pages less slow while the background works; it does not remove the slowness.
D3. Budgets (targets, proven stage by stage). These hold for any range, any Site type, with no pre-loading:
  • Site pages: first view ≤ 0.5 s p95; repeat ≤ 50 ms.
  • Portfolio (up to 31 days): first view ≤ 0.8 s p95; repeat ≤ 100 ms.
  • Data appears within 2 ticks, and shows "pending" until then.
  • A code change never makes history unreadable.
  • The §11b body sizes are kept, by loading long lists only when their part of the page is opened. No mock element is removed.
D4. Timing. C1-C5 start after the 17 Nov client demo. Alternatively, the demo moves until C1-C4 land, which is about 11.5 units. Architect recommends after, keeping the presenter rule for ranges that are not prepared, because these changes need a clean database rebuild.
D5. What a "day" means in a range.
  • The date bar's presets today are full UTC days. Kobo and Kisiwa run on UTC+3, so a UTC day there runs from 03:00 to 03:00 local time. Two stored kinds (Portfolio dispatch and evidence) also use UTC days, while coverage already uses each Site's local days.
  • Architect recommends: a picked date means each Site's own local calendar day. "14 Nov" on the Portfolio is 14 Nov 00:00-24:00 at each Site.
  • What you would see: in a Portfolio that mixes time zones, the Sites' days cover slightly different instants. Each Site's numbers then match its own board for the same dates exactly. The first and last day's totals may shift slightly from today's, and these differences will be shown to you before the switch.
  • The alternative is to keep UTC days everywhere, including the Site boards, which then stop matching local calendar days.
D6. One home for client-value data (a joint confirmation with the conversion-potential Architect).
  • ARPU, collections, cost per kWh, unserved kWh, uptime and billing inputs are stored in the same daily fact tables as everything else, as parts that add up.
  • Customer-level records stay in the billing store proposed in conversion §10/§13.
  • Collected money is shown beside the estimate, never added to it, as that document recommends.
  • This needs that Architect's agreement first. Then you confirm once for both documents.

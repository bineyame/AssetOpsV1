# Binding post-W2 sequence

Decision `D-2026-10-20-post-w2-sequence` (Architect, 2026-10-20). This amends the owner-approved two-lane proposal of 2026-10-18 and takes effect **when reviewed W2-07 merges**, after migration `0026`. W2 owner acceptance remains a later walkthrough. The owner approved building the waves before client conversations; no client-feedback gate precedes the W4 case model. This is sequence and allocation authority, **not** a build spec, panel promotion, or owner approval of later-wave core panels.

## Shared ownership, migration chain and execution

Lane A is the sole editor/integrator of `backend/migrations/versions/`, router mounts in `backend/assetops_backend/main.py`, the v6.9 dependency registry and its checker, `frontend/src/shell/` and shared navigation, `tools/checks/navigation-truthfulness.ps1` and its tab inventory, `tools/check-all.ps1` and `tools/checks/`, and shared `frontend/src/ui/` components. Lane B owns its domain modules and page components only. When Lane B needs one of these shared edits, it supplies a concrete contract/diff request to Lane A; Lane A integrates it after the consuming slice's spec is closed and both lanes merge current `main`. One Architect rules cross-lane contract and mock questions. Do not have both lanes edit a shared file in different worktrees.

Migration reservations are global, not lane-local. `0027` follows W2-07's `0026`. Lane B's W3-01 is deliberately schema-free, so both Step-1 lanes can build from the same accepted W2 base. `0028` is integrated only after `0027` reaches main; any Step-1 W3-02 schema work can be prepared in a private spec/patch but must not introduce a second Alembic head. Likewise the remaining numbers above are merged in numeric order; a later numbered slice may build disjoint code but waits to integrate its migration until its predecessor is on main. Lane A owns rebase/re-chain and the single head proof. A reserved number with no schema change is recorded as unused in its packet, not silently reassigned. No branch merges with a migration conflict or unresolved `down_revision`.

The W4-01 case model freezes at independent review ACCEPT and merge: identity versus Action, lifecycle and transition table, actor/attestation, correction/revision, Site/Asset links, event order, API/read shapes and refusal codes. W3/W5/W6 consume that version. A requested change goes to the Architect with the exact W4 contract clause, affected registry edges, migration/compatibility effect, and all affected lane specs. The Architect records a versioned amendment and directs a compatibility migration/test before either lane implements the changed contract; an implementer cannot choose a local interpretation.

The closed unavailable tab inventory is a **multiset**, not a set: Recommendation occurs twice (cold and EV Finding); Alternatives, Scenarios, Incidents, Maintenance, Cooling, Availability, Energy / site power occur once each, and Cost/Risks/Opportunities chips once each. Each promoted destination removes exactly its corresponding unavailable occurrence only after a reviewed truthful route exists. Lane A updates both guard and positive/negative fixtures atomically. Do not weaken the component's noninteractive/no-destination rule to make a route pass.

Both lanes use the same W2+ mock/layout and copy dry-read, focused checks per phase, one same-revision real-Postgres full backend suite per slice, independent review, desktop/narrow side-by-side evidence, and mismatch rated High when user-visible against the mock. One full suite runs at a time, outside an active builder's heavy test phase; Postgres stays within the 100-connection host limit. Each lane merges main after every main merge and resolves compatibility before continuing. Owner wave-start approval of IDs/core panels/demo values and wave-exit result review remain the delivery-strategy gates; the two-lane approval does not itself promote a panel.

**OPS-01 in Step 1.** The original `OPS-01` backend test-speed task is already merged (2026-10-15), so Step 1 consumes its harness and closes a bounded post-W2 speed follow-up under the OPS-01 record, with no duplicate implementation task ID or product migration. Scope: measure the W2-expanded real-Postgres suite on this Windows host, remove reproducible test-harness bottlenecks/flakes caused by the added cold/EV modules, keep worker DB isolation, cleanup, connection cap and exact collection/outcomes, and document the stable `-n 2 --dist loadfile --no-loadscope-reorder` command. Acceptance: same-revision JUnit with zero DB skips and unchanged node IDs/coverage, migration/downgrade/process/lock tests intact, two clean bounded runs with timings and peak `pg_stat_activity`, no unexplained failure or >2x expected wall-time hang. Any change to production semantics leaves this follow-up. It runs alongside Step 1 in the single shared test queue, not as a third product lane. The accepted 2026-10-15 OPS-01 result (~8 minutes) is the baseline, not a claim that W2's larger suite retains that time.

## Spec readiness and writing order

No row above authorizes a builder until that slice has a full build spec and task packet. For each, the Architect/Planner first close a **concrete-artifact pre-build check** against the then-current main: exact mock panel/row/column/chip and empty-state map; fixture Site/Foundation revisions and accepted evidence IDs; identifiers, JSON shapes and ordering; all seam path:symbols; authorization/refusal codes; currentness/UTC; source classifier and money gates; migration DDL/index/downgrade and guard allowlists; UI component, route and copy choices; measured 1440/390 layout budgets; one persisted positive and one missing/conflicting replay; full-suite/test-count implications. Then perform an implementer and copy dry-read commit by commit, settle every design question in the spec, run the registry checker, and obtain the independent spec review. A builder may refine mechanics but never decide an omitted mock or contract question.

Write specs in this order, starting the next without waiting for an unrelated lane's build: **(1)** W4-01 and W3-01 together, including the shared ownership ledger; **(2)** W3-02 while W4-01 builds, then W4-02; **(3)** W3-03 while W4-02 builds, then W4-03; **(4)** W6-01 and W5-01/W5-03 after W4-01 contract freeze, but close W5 specs only after the W2 structural gate; **(5)** W6-02/03/04 and W5-02/04 in their lane order. OPS-01 Step-1 follow-up is specified and measured in parallel by the tooling owner through the shared suite queue. If a spec finds a missing architecture node or unsound seam, the Architect closes that exact contract and updates both affected specs before either builder crosses it.

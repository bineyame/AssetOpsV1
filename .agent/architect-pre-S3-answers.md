## Mandatory pre-S3 architecture contracts

### A-claim-work-routes — resolve from `D-2026-10-09-pre-s3-claim-routes-and-actor`

- A Finding or Action has an immutable UUID plus tenant and Site UUID. Canonical product routes are `/sites/{site_code}/findings/{finding_id}` and `/sites/{site_code}/actions/{action_id}`; APIs are `/api/sites/{site_code}/findings/{finding_id}` and `/api/sites/{site_code}/actions/{action_id}`. Each root may have child views when built; tabs do not mint new root identity. Site code is resolved **inside** the authenticated tenant, never as global authority. This route contract is domain-neutral for mini-grid, cold-chain and EV.
- A Finding list links the stable root ID and exact immutable `finding_revision_id` where a historical claim is intended. Omitted `revision_id` selects the latest permitted Finding revision at stated `knowledge_at` and returns that selected ID and watermark; supplied `revision_id` freezes it after later revisions. Action state is reduced from immutable ActionEvents, so its exact historical selection is `event_id`/recorded cutoff; Plan and Verification child views use their own `plan_revision_id` and `outcome_id`. Do not invent an ActionRevision row. Every selected ID must belong to the same root/tenant/Site; root ID alone never implies a particular historical statement. Back-links retain Site, window and exact selection.
- Unauthenticated is 401; authenticated but unauthorized Site/root is 403 when that scope is known to the caller, while a foreign-tenant or nonexistent identity is 404 to avoid disclosure. An absent revision is 404; a supported root whose read/projection is not yet available returns a typed unavailable/lagging state, not a fabricated empty successful claim. Unbuilt tabs are hidden or honestly unavailable. Site-scoped lists precede W3 global roots; a future global index points to these same canonical IDs.

### A-actor-identity — resolve from the same decision

- Persist `actor_kind` (`HUMAN` or `SYSTEM`), server-resolved `actor_id`, action/source channel, recorded time and authorization basis with each auditable assumption, policy or work event. A human `author_id` is an authenticated principal; a client-supplied string, local OS username, fixed development tenant or gateway credential does not establish a human author. `SYSTEM` events use a stable service principal and the triggering job/command/fixture ID. A system process cannot fill a human author field or imply human attestation.
- Human-attested records require the authenticated human actor plus the exact attested content/version, attested time and immutable proof/reference; an operator's later correction appends a new event/revision with reason. An automated observation, Lab run or gateway receipt is source provenance, not a human sign-off. The S2 provisioning CLI's OS-user name remains labelled **local context**, never verified tenant actor.
- For S4-02's price edit and S6-01's accepted Action/policy change, the Planner must supply a verified operator path or a clearly labelled server-authorized `SYSTEM` demo operation with immutable audit provenance. If neither exists, the write is unavailable; do not forge `financial_assumption_revision.author_id` or let the browser choose it. This is an implementation gate of those packets, not an S3-01 dispatch requirement.

### Bounded A-evidence-readiness-health — resolve from `D-2026-10-09-pre-s3-evidence-readiness-health`

- `CapabilityReadiness` is a backend selected-window read of rule-versioned required roles against registered bindings and **accepted** evidence. It carries tenant/Site/domain, half-open window, `knowledge_at`, Foundation/binding/rule revisions, per-role observed coverage/quality/limits, evidence IDs, source/projection watermarks and `READY | LIMITED | UNKNOWN | NOT_APPLICABLE`. Missing required evidence is Unknown or Limited with a reason, never healthy or zero. Rejections/duplicates and pending gateway rows do not satisfy role coverage. Configuration readiness is separately labelled and never substitutes for observed capability.
- `SourceHealth` is an operational projection with at least two distinct clocks: **server contact freshness** from latest centrally received diagnostic (`CURRENT | STALE | UNKNOWN` under registered cadence) and **reported-fact age** from that diagnostic's `observed_at`/source contact times, with clock basis, trust/offset and delayed-report limits. A newly received old diagnostic can make contact CURRENT while its queue/pressure/device-contact facts remain old or Unknown; UI must show both. For simulated `RUN_VIRTUAL` observations, do not compare virtual time with real server time as a physical freshness or network-lag measure. SourceHealth is not asset condition or an AcceptedEvidence row.
- Both reads disclose source/gateway IDs, received/observed times, coverage/missingness, `built_at`, source watermark and projection lag. A stale projection is `STALE_PROJECTION`, not a current capability conclusion. Site read contracts are defined now for all three domains; role requirements and actual cold/EV projections wait for their domain waves. `D-edge-health-cases` adds S7 outage/pressure fixture variants and is not an S2 ordinary-contact prerequisite.

## S4-01 contract for Planner refinement

**First claim.** Build one mini-grid candidate generator-support Finding type. A CURRENT, coherent selected dispatch assessment with at least one bounded `CANDIDATE_AVOIDABLE` segment creates/continues it; retain the segment's candidate duration and Necessary/Indeterminate portions as distinct facts. An Indeterminate assessment alone never becomes an avoidability Finding. It may append an `UNCONFIRMED` revision to an already existing episode if a current selected assessment now limits that episode; a stale/failed/unassessed projection changes the read state without manufacturing a new FindingRevision. A later complete Necessary-only or no-Candidate assessment can close the candidate claim as `NO_LONGER_SUPPORTED`, explicitly not “repaired” or “savings realised.” A separate evidence-gap Finding needs a later type/rule, not an opportunistic S4-01 claim.

**Identity/matcher.** Allocate a stable `finding.id` and `finding_key` once per tenant/Site/mini-grid/generator asset/candidate-support episode. Store the initial accepted candidate anchor, selected public cohort, exact window(s), observed episode bounds and matcher version; never derive ongoing identity from a mutable dispatch first-ON key, day, hash or Lab run. On each current selected assessment, match supported spans against persisted episodes across UTC-day boundaries. Overlap or a gap of at most 20 minutes extends the same episode only with a defensible coherent series; contradiction, ambiguous cohort or insufficient coverage cannot be used as a bridge. A supported gap greater than 20 minutes starts a new Finding with `recurs_after_finding_id`. Late evidence can extend a Finding earlier without renaming it. If it splits a prior episode, keep the ID on the part containing its immutable anchor and create linked Finding(s) for other supported parts; if it bridges two already persisted IDs, preserve both histories, choose the earlier anchor/UUID as canonical and record a durable merge/supersession relation. Do not display both as active duplicates.

**Revision/lineage.** Persist Finding and immutable FindingRevision with idempotent `(finding, canonical selected assessment basis, transition)` semantics. A FindingRevision must name its exact selected `assessment_revision_id`, AnalyticRun/model version, selected window AssessmentRevision and every additional interval AssessmentRevision used by a cross-window episode. Use an association table if one scalar FK cannot represent all supporting revisions; keep the primary FK required by the technical design. Persist or reliably resolve the exact accepted evidence ID/digest set for the selected assessments, with as-accepted and selected Foundation/binding revision IDs and the source/batch/envelope path. Do not attach all readings in a run as if every one proved the claim: distinguish the complete analytic input set from the accepted records actually cited by the candidate segments. Backdated control changes, late accepted evidence and model upgrades append a FindingRevision when the basis/claim/limits change; retries of one basis do not. Historical `dispatch-3` revisions remain pinned-readable but cannot be current input to a `dispatch-3.1` Finding. A later reviewed `dispatch-3.x` version is an explicit new Finding basis, not a relabel of the old revision.

**Lifecycle/read.** Record opening, changed support, unconfirmed support, no-longer-supported closure, recurrence and split/merge as durable transitions; never overwrite a prior FindingRevision. S4-01 implements the canonical `/sites/{site_code}/findings/{finding_id}` and `/api/sites/{site_code}/findings/{finding_id}` detail with optional exact `revision_id`; root and revision must resolve inside the authenticated tenant/Site. The response returns stable Finding UUID/key, selected FindingRevision ID, linked dispatch revisions/run/model/cohort/window, episode relationship IDs, claim/limitations, evidence IDs, projection status and source/analytic watermarks. Omitted revision selects the latest permitted recorded revision, while exact `revision_id` freezes history after late evidence. Because the S3 clock cutoff is not a commit-ordered fence, advertise stored selected revision and exact IDs as the reproducible audit path; do not claim arbitrary `knowledge_at` replay. Preserve Site/window/exact revision in back-links. Distinguish `NOT_ASSESSED`, `PENDING`/`STALE`/`FAILED`, assessed `NO_FINDING`, current supported, unconfirmed prior, and closed/recurring; no Finding row alone is not a healthy verdict.

**Reviewable fixture and boundaries.** Through accepted S2 Evidence and selected S3 assessment revisions, prove: initial Candidate; overlap/adjacency within 20 minutes; cross-day extension; a separated recurrence; late earlier evidence changing the first-ON key without changing Finding ID; a changed Candidate duration/limit making revision 2; Indeterminate making an existing claim unconfirmed but not inventing a new one; a complete no-Candidate reassessment closing support; and one split (plus a bridge/merge if fixture cost remains bounded). Reload old/new FindingRevision URLs and walk one displayed value to exact accepted envelope, as-accepted binding and selected Foundation control. The Planner must give `D-finding-revisions` the case IDs and expected transitions, migration/read seams and focused checks. S4-01 detail/UI may show a concise evidence summary; S4-03 owns full Evidence/History child views, S4-04 the Site index/list, S4-02 financial consequence and S6 the Action/verification lifecycle. Cold-chain/EV reuse only the identity, revision/lineage, relationship and freshness contract; their domain match tolerances and positive fixtures are later decisions.

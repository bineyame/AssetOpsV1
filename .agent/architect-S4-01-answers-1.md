# Codex Architect — S4-01 phase-1 rulings (2026-10-12)

Authority: `D-2026-10-12-finding-episode-and-revisions`, the S4-01 packet and the technical design's Finding/Assessment lineage. These Q1–Q9 rulings are subject to the fresh phase-1 Claude review. They do not accept phase 1 or waive the S4-01 owner checkpoint.

1. **Q1 — accept the new uniqueness keys; amend the design's primary-assessment uniqueness for this episode type.** A cross-window Finding can change because a secondary supporting interval changes while the primary AssessmentRevision stays fixed, so `UNIQUE(finding_id,assessment_revision_id)` would discard a real revision. Keep that primary FK and the exact association to every supporting interval/window revision; unique `(finding_id,revision_no)` and `(finding_id,basis_sha256,transition)` with transactional idempotency are the S4-01 rule. Phase 2 must return the full supporting set and its basis digest, not imply that one primary FK is the entire claim.
2. **Q2 — accept observed modelling-only Indeterminate as a possible bridge, but tighten the coverage proof before phase 2.** An observed segment limited only by transition/minimum-runtime/headroom modelling does not represent missing source evidence and can preserve episode continuity beside observed Necessary segments. Require full gap coverage by such observed coherent segments, with no empty/vacuous span, missing measurement, contradiction or ambiguous cohort; `site.covered` only proves window coverage, so it is insufficient alone. Phase 2 must expose the exact bridging segments/reasons and a test for an empty or partially unobserved ≤20-minute gap that opens separate Findings.
3. **Q3 — accept OFF-proven recurrence only; amend the earlier shorthand.** A >20-minute separation opens a new Finding, but elapsed time without observed OFF cannot prove a second generator run or a recurrence of the same operational episode. Set `recurs_after_finding_id` only when public accepted OFF evidence establishes the break; otherwise leave the relation unknown/unlinked. Phase 2 returns the OFF evidence ID/time when linked, or an explicit unknown-relation reason; phase 3 uses “another Finding, recurrence not established” rather than implying recurrence.
4. **Q4 — overrule exclusion of the selected window AssessmentRevision from the Finding basis.** The revision cites that window as its selected assessment context; if the window selection changes, reusing a FindingRevision that still points at the prior window misstates current lineage even when interval minutes are unchanged. Include every relevant selected window revision ID in the canonical basis with interval revisions, cited evidence, controls/bindings, bounds/limits and matcher/model version; append an immutable provenance-only revision when only that basis changes. Phase 2 must distinguish the currently selected window ID from a pinned old revision, and phase 3 must show the newer provenance without claiming a changed physical duration. This is conservative; any later suppression needs a reviewed proof that the changed window cannot affect the Finding.
5. **Q5 — keep collateral revisions but rename provenance-only transitions `BASIS_REFRESHED`.** A backdated control that changes selected Foundation/Assessment revision IDs is a new auditable basis, so suppressing the FindingRevision would leave it citing an old selected result. `SUPPORT_CHANGED` suggests bounds, candidate minutes or limitations changed; use it only when those facts change. Phase 1 must add `BASIS_REFRESHED` to the transition vocabulary and F05 expectations; phase 2/3 show “assessment basis updated; supported candidate amount unchanged,” linked to old/new selected control and AssessmentRevision IDs. Do not report eight collateral revisions as eight new issues.
6. **Q6 — overrule all-fixture provenance for F01; keep labelled fixtures for fault cases.** The packet explicitly requires an ordinary registered-gateway, gateway-sealed Batch V2 and central-acceptance proof for the opening Candidate; S3's reviewed normal-path Candidate can be reused if the S4 producer verifies the same public IDs in its own database, or F01 can run its own registered Lab/gateway case. Phase 1 must add that F01 proof before its gate closes. Held, contradictory and bridge-specific F02–F06 reports may remain labelled authenticated Batch V2 fault fixtures under the registered credential; the artifact and phase-2/3 read must say they were not gateway-sealed, and no fixture label becomes central attestation.
7. **Q7 — accept derived closure with no mutable `finding.closed_at`.** Append-only FindingRevisions and merge relations retain both historical closure and reopening semantics more reliably than a mutable timestamp; the technical design's `closed_at?` is optional projection data. Phase 2 derives lifecycle/closed-at-as-known from the selected revision and recorded transition, keeps older URLs stable, and does not turn a `NO_LONGER_SUPPORTED` conclusion into proof of repair. Phase 3 shows the conclusion and its basis separately from workflow completion.
8. **Q8 — accept the internal minimum-runtime fixture publication.** S4-01 does not authorize a new product control-write route; a labelled FoundationService fixture publication into the copied tree is acceptable if it uses the normal revision/persistence validation and exposes the exact effective revision selected by S3. Phase 2/3 must label this as fixture setup and not imply the owner can edit generator runtime in the current UI. A product route requires its own later Foundation scope decision.
9. **Q9 — accept ordering labels only.** HTTP central acceptance is stamped by the server's real clock; the spec's `decided` values may specify procedural order but cannot be presented as accepted-at facts. The phase-1 run artifact and phase-2/3 detail must use actual accepted disposition/receipt times and identify the spec labels as instructions, not lineage; compare old/new order by actual IDs and server timestamps.

Q2's gap-proof, Q4's basis and Q5's transition vocabulary, and Q6's ordinary F01 proof are phase-1 corrections for independent re-review before the phase-2 read is treated as authoritative. Phase 2 must test exact root/revision selection, full multi-assessment lineage, fixture-vs-gateway provenance, recurrence uncertainty and derived lifecycle; phase 3 must present those distinctions in plain language and keep money/Action claims unavailable. No further owner product choice is needed; the existing S4-01 owner walkthrough remains required.

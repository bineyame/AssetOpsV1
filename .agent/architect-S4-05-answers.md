# Architect rulings - S4-05 stored demonstration provenance (2026-10-15)

Authority: `tasks/S4-05-stored-demo-provenance.md`, `I-stored-demo-provenance`, `.agent/architect-S4-02-batch-answers.md` Q3, `D-2026-10-15-lr01-source-time-cohort`, `D-2026-10-15-s501-finding-choice`, and the owner's absence delegation. These are implementation decisions, not owner approval of visible copy or pilot designation.

## Q1 - authoritative publication moment: accept with transaction detail

The only authoritative authored-demonstration designation is a server-authorized SYSTEM publication committed **before** admission of its exact Batch V2. Pin tenant/Site UUID, gateway/source, external batch ID, canonical payload SHA-256, immutable publication ID and fixture/spec ID/version. Resolve service principal, authorization basis, channel, trigger and recorded time on the server. An identical registration retry returns the same ID; changed content or reuse of a publication ID fails. A gateway credential, client text, `SIMULATED`, Site/day match or missing designation proves no authorship.

Registration and `open_batch` must take the same transaction-scoped lock on the scoped batch key and check for an existing batch while holding it. Registration after any batch admission fails, including a partially completed batch. `open_batch` binds at most the exact preauthorized commitment in its admission transaction; a matching-key but mismatched commitment fails rather than silently becoming unknown. Accepted IDs inherit that immutable binding, including after chunk restart. Duplicates retain their original accepted ID and provenance; rejected/conflict rows acquire none. Existing accepted rows remain unknown, with no retrospective spec/date backfill. The fixture command stays server-side with an explicit configured authority; no public designation route.

**Packet change:** spell out the shared lock key/transaction, registration-after-partial-admission refusal, and mismatch failure in the phase-1 contract/tests. Show the P01 positive path as fresh publication followed by upload of that exact new batch.

## Q2 - several publications in one Finding: accept with set definition

Several distinct authored publication IDs may support one selected FindingRevision if **every** cited accepted ID resolves within the requested tenant/Site to an `AUTHORED_DEMONSTRATION` publication with the same fixture/spec ID **and version**. Return all distinct publication IDs and per-ID provenance. Different fixture IDs or versions, or a combination of designated and undesignated IDs, is `MIXED`. An empty citation set, no designated IDs, or any missing, foreign-Site or broken accepted-ID/publication link is `UNKNOWN`; a broken link takes precedence over `MIXED`, and the read names the problematic IDs. An accepted ID with no designation is unknown authorship, not proof of a real source.

Compute a Finding from its selected immutable FindingRevision evidence set. Compute each consequence revision from the union of that selected FindingRevision set and that consequence revision's own quantified power-interval accepted IDs. Report the two sets and their IDs separately so a later consequence can have a different state; never inherit the current head's label for historical revisions.

**Packet change:** add a precise set-state truth table, including two publications with one fixture/version, differing versions, empty set, missing/foreign link and consequence-only mixed input. Require response fields for all publication IDs, per-evidence provenance, problematic IDs and exact selected revision IDs.

## Q3 - unknown source and money: accept with gate precedence

`MIXED` or `UNKNOWN` provenance blocks a **current displayed amount** on Finding Financials, consequence and S5 Overview, even if a stored consequence says `CURRENT PRICED` or LR-01 money eligibility says `ELIGIBLE`. Keep any old value reachable only as explicitly historical/audit material with its exact revision, source state and limitation; it is not a current amount. Source provenance is one independent gate: an all-authored set may show current money only when LR-01 eligibility, exact selected Finding/consequence basis, currentness, source-open and ordinary price/quantity gates also pass. If several gates fail, expose their typed reasons without hiding the source problem. Do not treat unknown as real measurements or as zero cost. Keep `Demonstration data` only for the fully authored case. Mixed/unknown copy remains proposed for the owner at the W1 checkpoint; this ruling does not approve wording or pilot designation.

**Packet change:** state the gate composition and audit-only historical behavior for all three money reads, add tests for `CURRENT PRICED` plus `UNKNOWN`/`MIXED`, LR `ELIGIBLE` plus source refusal, and S5 composition after its merge. Include the owner-visible copy and pilot designation in the checkpoint handoff.

## PostgreSQL writer and rule 8

This extends `evidence/adapters/postgres_evidence_ledger.py`, the existing ledger writer; it creates no new writer. Add the publication table and any separate binding table to the ledger's rule-8 ownership allowlist **for INSERT only**. If binding is instead a nullable `ingestion_batch.publication_id`, set it only in the batch INSERT during admission; never permit an UPDATE to add or change it. Rule 8 must reject UPDATE/DELETE/TRUNCATE/upsert/DDL on publication or link rows from the ledger and reject their writes from every other module. Preserve existing writer allowlists, reverse ownership and driver/write non-vacuity, including any independently merged writer when implementation starts. Back this up with database uniqueness, scoped foreign keys and immutability enforcement so direct SQL cannot change publication/link rows; static guard alone is insufficient. Migration owns DDL, not a runtime writer. If LR-01 or another merged slice takes migration 0014 first, re-chain and renumber on the actual single head.

**Packet change:** name the INSERT-only rule-8 and database immutability proof for whichever binding design is chosen. Add permitted-ledger-INSERT, forbidden-other-writer-INSERT, ledger/other UPDATE/DELETE, upsert, omitted-writer/import and client-route designation probes to phase 1. Do not weaken existing eight-writer protections; account for the Action writer if merged before this implementation.

## Follow-up (plan review M1)

The blanket `UNKNOWN` default is intentional for unbound historical rows and genuinely unknown or broken input, but not for every future ordinary simulated run. Separate source class from authorship. S4-05 must support two positive, immutable, server-authorized pre-admission batch bindings: `AUTHORED_DEMONSTRATION` for an identified authored fixture/spec version (P01 and the authored P02 late-power fixture), and `REGISTERED_SIMULATION` for ordinary simulator output with a server-recorded run ID, immutable run identity/digest and exact tenant/Site, gateway/source, batch ID and payload digest. The latter requires a registered `SIMULATED` gateway and proof that this exact batch was produced by that recorded run; `source_mode=SIMULATED`, a gateway credential, client text, Site/day match or a private manifest alone does not grant the designation. The server may keep private scenario truth outside product evidence; the public binding carries only run identity and provenance needed for the read. Extend the same ledger publication/admission lock, append-only binding, duplicate and no-retroactive-backfill rules to this class. Do not reinterpret `REGISTERED_SIMULATION` as authored fixture or physical measurement.

Resolve each selected FindingRevision's cited accepted IDs and each consequence revision's union with its own power-interval IDs. All IDs bound to one coherent authored fixture ID/version yield `AUTHORED_DEMONSTRATION`; all IDs bound to a coherent registered simulation run yield `REGISTERED_SIMULATION`. Multiple run IDs require an explicitly recorded compatible run basis; absent that, return `MIXED`. Crossing source classes, mixing bound and unbound IDs, or conflicting fixture/version/run bases is `MIXED`. No positive binding, an empty citation set, or any missing, foreign-Site or broken link is `UNKNOWN`; a broken link takes precedence. Return exact IDs and reasons. An authored or registered-simulation set may show a current amount only after the existing LR, exact-head, currentness, source-open, quantity and price gates pass, with a truthful `Demonstration data` or `Simulated data` label respectively. `MIXED`/`UNKNOWN` show no current amount and historical values stay audit-only. Existing unbound ordinary simulated and real rows therefore remain `UNKNOWN` with no current amount; new ordinary runs need the positive binding. A real gateway, even with `source_mode=LIVE`, has no positive source designation from S4-05 and cannot show current money yet.

Create follow-on registry node `I-attested-real-source-provenance` for a server-authorized, tenant/Site and source-scoped `ATTESTED_REAL_SOURCE` designation. Its contract must name the accountable authority, physical peer/device and capture channel, credential/identity binding, exact accepted batch/evidence lineage and revocation/correction behavior; a gateway credential or `LIVE` mode alone is insufficient. Only a fully attested, coherent real cited set may become current-money eligible, still subject to all ordinary gates. Planner must add this open node to `real_pilot_requires` and the pilot install gate's checked registry before marking `I-stored-demo-provenance` resolved or installing a pilot timer. S4-05 may resolve before this follow-on after its own review and owner copy checkpoint; its resolution alone grants neither real-pilot installation nor real-source current money. W1 exit remains tied to S4-05, while real-pilot money and installation wait for the real-source node and all other pilot gates. This follow-on does not waive the separate physical-source evidence requirement.

Amend S5-01's packet in whichever slice merges second. Replace the `demonstration_case`/unreadable-spec trigger at line 39 with the stored, exact-revision provenance resolver and add `REGISTERED_SIMULATION`, `AUTHORED_DEMONSTRATION`, `MIXED`, `UNKNOWN` and later `ATTESTED_REAL_SOURCE` to the money-read contract. `MIXED_OR_UNKNOWN_SOURCE` applies whenever the resolver returns `MIXED` or `UNKNOWN`, including unbound history, broken links and mixed consequence-only power inputs, regardless of spec-file readability; preserve exact IDs and all simultaneous limiting reasons. Update P01/P02 and ordinary-day walkthrough expectations to distinguish freshly published authored batches, positively bound ordinary simulation and old unbound rows. The S5 selected Finding and exact links do not change because source class must not influence Finding choice. The owner must review visible labels; this Architect ruling is not that approval.

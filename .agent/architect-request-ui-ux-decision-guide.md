# Architect request: UI/UX decision guide for builders

You are the AssetOps Architect. Owner, verbatim (2026-10-25): "i feel some of the questions by the builder should be resolved by itself because the look minior: the architect should provide a guide based on ui/ux best practices and the builder itself should also be well versed". Earlier the same day: "for UI/UX related question, it is important to take inspiration from modern UI guidelines and techniques, this is for the architect as well as the implementer" and "not just when there are questions but state of the art UI/UX should be used(within bounds of demo speed)" (see `.agent/owner-ui-ux-guidance-2026-10-25.md`).

Write `frontend/docs/architecture/ui-ux-decision-guide.md`: a concise, durable guide builders apply WITHOUT asking, grounded in WCAG 2.2 AA, Material 3 / Apple HIG / GOV.UK design system / Carbon, NN/g heuristics, and responsive data-table practice, and consistent with this codebase and its prior rulings. Distil the patterns the post-W6 rulings already settled so they stop recurring as questions (read the `.agent/post-W6-*-rulings.md` files, especially caps/closeout/build ones). Cover, with concrete defaults (values, copy templates, component/CSS hooks where they exist):
- Long content: wrap first; in-cell "Show full/Show less" disclosure; table-local scroll regions (role=region, label, tabIndex 0, cue text pattern, max-height conventions); never hide rows or silently truncate; caps per Lesson 15 (worst case five 160-char rows probe method, all-open exemption, cap = ceil(peak×1.15/50)×50 when unruled — builder proposes, Architect ratifies only if it exceeds a ruled cap).
- 390 px behaviour: reflow, tab rows wrap, horizontal scroll only inside tables, touch targets ≥24 px (WCAG 2.5.8).
- States: loading (status), empty, refusal/error (alert), copy keyed on error code not HTTP status, no raw server text or codes on screen, recovery actions only when they can succeed.
- Copy: plain language, sentence case, units, Site-local time via `sites/siteTime.ts` with UTC detail, fallback suffix wording, pluralisation helper pattern.
- Colour/status: semantic tokens, text never relies on colour (1.4.1), 3:1 non-text contrast, neutral for fixed labels.
- Focus/keyboard, headings and landmarks, link vs button, no nested interactive controls.
- Mock deviations: when a choice changes the v6.9 layout/content, label `MOCK DEVIATION Dn (Rnnn)` and register (D1 unavoidable data gap, D2 proposal for owner) — builder may do this for small D1/D2 within its register range and lists them in the packet.
- **Decide vs escalate:** builders decide and record (in the packet "Choices made" with the guide section cited) anything covered by the guide or a clear extension of it — minor copy where no product meaning is at stake, spacing, colour tokens, disclosure/scroll patterns, state copy, test approach. Escalate only: product meaning/claims, backend/API/schema changes, scope or ownership across cards, guard/test-policy changes, exceeding a ruled cap after the guide's fallbacks, owner-facing D2 layout changes of significant size, conflicts with a ruling.

Keep it short enough to read in one sitting (aim ≤ 250 lines). Also add a one-paragraph pointer to it in `.ai/ROLE_CONFIG.md` under the existing "Modern UI/UX Guidance For UI Decisions" section. Do not edit product code or `.gitignore`.

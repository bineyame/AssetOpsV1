**Codex Architect · 2026-10-08.** Responds to the owner's verbatim feedback in `.agent/owner-S1-ui-feedback-2026-10-08.md`: the current Foundation page is too much of a content dump for the owner to verify. This is a new presentation decision, not a reversal of the accepted-with-carries technical reviews of S1-01 and S1-02, and not owner acceptance. No tracked file, branch, or database state was changed for this decision.

**Pull forward a bounded `S1-03 — Foundation, Readiness and SLD organization` slice now, before S1 merge and before S2-01a.** Use the reviewed S1-02 tip `d8dd3e9` as its starting basis and a separate task branch. This is a corrective S1 owner-review gate; do not activate the broad `V-01` proposal, whose evidence, Lab and tier gates remain after S2-02. The Planner/coordinator should add S1-03 to `tasks/README.md` as the next executable slice and record the owner feedback as its trigger; the existing v6.9 ledger remains an overlay, not a claim that all three mock screens are complete.

## 2. Information architecture and D2 change

**Revise my D2 ruling for the supported imported Site.** Render a Foundation view row with three working destinations in the mock's order: **Site model**, **Single line diagram**, **Readiness**. `Readiness` here means S1-02 *configuration readiness*; Site > Evidence retains its separate claim/capability readiness. Use stable Site-scoped routes such as `/sites/{code}/foundation`, `/sites/{code}/foundation/sld`, and `/sites/{code}/foundation/readiness`, or equivalent explicit route names chosen by the Planner; all three must be direct-linkable, keyboard navigable, and share the selected `at` query value. The current `Definition | Topology | Controls` contents row must not remain as a competing tab-like row; details can use clear in-page headings or disclosure within the Site model. Do not render the mock's `Changes` destination, which has no supported intervention model.

Update `tools/checks/navigation-truthfulness.ps1`, `FoundationSubtabs.tsx`, their tests and any relevant layout guard to enforce **three supported, navigable Foundation views** rather than prohibiting a Readiness subtab. The old guard reflected a valid earlier distinction between Evidence claim readiness and Foundation configuration readiness, but its absolute prohibition now blocks the owner-verifiable mock organization. Retain the rule that no unsupported or disabled destination is shown. For unimported legacy Sites, preserve their current truthful behavior or limit the new view row to imported Sites; do not imply Postgres bindings or a snapshot exists for a legacy Site.

The mock supplies hierarchy, rhythm and visual treatment, not data authority. On **Site model**, put a concise persisted version/effective-period status strip first; then a primary configured-topology visual beside Site identity/obligations at desktop, followed by time-valid controls and the narrow reserve edit. Move long UUIDs, digests, import path, superseded versions and detailed inventory into clearly named secondary detail or disclosure sections that remain available for audit. On **Readiness**, lead with the configuration verdict and specific missing roles/controls, then group role coverage, source/binding details and the existing binding-change action; show snapshot availability and download with its hash in a labelled acquisition-details area. On **SLD**, make the registered electrical diagram the primary visual, with an adjacent or following explanation of what each configured part is and which channels are bound; keep detailed node/connection tables accessible as secondary detail. Avoid repeating the same full binding table on all three views. A version/period selector and clear historical label stay discoverable on every view, and the same selected Foundation/binding basis drives all three.

Preserve S1 semantics: displayed values come from the selected Postgres Foundation, binding set and registrations; the source YAML remains comparison input. Missing reserve, missing bindings, no selected period or no snapshot gets a named empty/Unknown state. A pending gateway is never shown as connected; no live flows, device health, commissioning confirmation, generator start/stop thresholds, mock Site code/timezone/version, illustrative load readings or Evidence claims are copied from v6.9. The mock's gateway-status, connected-sources and field-confirmation panels remain unsupported until S2 or a later explicit contract. The reserve and binding publication actions remain scoped to their existing validated APIs.

## 3. Visual acceptance the owner can perform

The owner must be able to open the three product views alongside `frontend/mockups/v69/index.html#/foundation`, `#/readiness`, and `#/sld`, respectively. Compare at **1440 × 900 desktop** and **390 × 844 narrow** viewports, with first-viewport and full-page captures keyed by manifest ID. The comparison should assess the visible page hierarchy, navigation, status strip, panel grouping/order, topology/diagram prominence, typography, spacing, table density and responsive stacking, and record each deliberate omission with its missing S1 data or contract. Pixel identity and mock values are not the goal; the owner should be able to find the version, reserve control, generator status and battery SOC bindings, missing-role explanation, snapshot hash/download, and configured SLD without scanning a long undifferentiated stack.

The review path uses the converted Kobo fixture plus the already supported missing-reserve/unbound variant. Change the selected period, traverse all three views, reload and share each URL, and verify the same historic basis remains selected; remove one required binding through the existing action and observe Readiness and SLD change at the new period while the earlier view remains recoverable. Check desktop and narrow overflow, visible focus, meaningful headings and links. A reviewer traces one visible binding and one control to the existing read API and stored revision IDs; this slice creates no new claim or SourceEnvelope. Run the changed frontend tests, typecheck/build, navigation and layout guards, architecture/workflow checks and the v6.9 ledger checker if the ledger is updated. Supply app browser evidence, not only mock screenshots. The owner then performs the side-by-side UI check and can accept, ask for focused corrections, or decline; a green test suite alone cannot resolve the reported organization failure.

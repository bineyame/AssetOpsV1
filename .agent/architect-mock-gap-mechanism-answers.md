# Codex Architect — proposed mock-gap closure mechanism (2026-10-12)

**Owner decision requested:** approve a complete, checked gap catalogue now; decide how non-core work competes for delivery at the W1 exit. The present W1 core scoring, K=10, active-task stop and owner checkpoints remain unchanged. This proposal makes every honest “not available yet” traceable without delaying the V-01a owner checkpoint or merge.

## 1. Register the missing claim, not merely its placeholder

Extend the dependency registry (versioned schema migration) with a `mock_gaps` catalogue. A gap is one stable graph node `G-<screen-or-shared>-<claim>` for **each distinct missing claim/interaction**, reused by multiple panels or text placements where the same underlying fact is missing. Every non-core manifest panel portion receives at least one gap node; each on-screen missing-data element references one or more such nodes. Do not generate a separate node for every repeated row, translation or responsive rendering of the same claim. Do not create a gap for normal zero results, loading, malformed input or store outage when the capability already exists; those are runtime states. The registry's existing architecture/implementation/data/product nodes remain the technical dependency graph; a gap node records the unmet product claim and its AND prerequisites, not an invented implementation task.

Each gap needs `id`, `screen_ids`, `panel_portion_ids` (or `element_ids` for content within a panel), `claim`, `boundary` (time/window, subject, source and what it cannot mean), `missing_kind` (`decision | data_source | contract | build | visual`), `status` (`open | resolved | owner_withheld`), `target_wave` (`W1`…`W6` or `unplanned`), `requires` (reviewed existing node IDs), `source_status` (`existing | absent | undecided`), `ui_placements` (stable placement IDs or explicit `unplaced_reason`), `owner_or_role`, `evidence` and `review_trigger`. `unplanned` means **unallocated pending owner review**, never silently dropped or indefinitely deferred; `owner_withheld` needs an owner decision and replacement/return trigger. A gap may point to a shared prerequisite and multiple consumers, but each distinct positive claim has its own closeout. In `w1_panel_mapping`, add `gap_ids` to every non-core/open portion; keep its `core`, `state`, `technical_requires` and `panel_status` semantics unchanged. In the screen ledger, add `gap_ids` or a keyed gap reference in `unknown_or_empty`/promotion notes so the manifest panel, registry claim and visible state can be joined. Do not encode prose-only free-text dependencies as scored paths.

**Example:** `G-readiness-gateway-signal-strength` is a `data_source` gap, boundary “reported gateway radio signal at a named gateway/time; not device health,” target `unplanned`, source `absent`, UI placement `readiness.gateway.missing_metrics`, and no eligible technical path yet. Once the owner chooses a source, an Architect contract decides units/clock/provenance and whether a simulated report is allowed; then separate producer or operator-capture, edge envelope/diagnostic schema, authenticated ingestion/persistence, selected read, UI and visual/test nodes are added as reviewed AND gates. `G-readiness-gateway-firmware` follows the same pattern but may share transport/storage with signal strength; it cannot be marked resolved because one transport exists. Commissioning records and policy documents are **operator-authored or imported records** needing identity, authority, version and read contracts, not simulator observations. Productive-use designation is a typed time-valid Foundation declaration, not a deduction from “Grain mill.” Gateway uptime and completeness need denominator/window/freshness contracts before a percentage. Never route private simulator truth into product Evidence or claim a physical capture because the simulator can produce a value.

Use the current graph where it genuinely covers a portion: Site identity/Foundation/bindings (`A-S1-foundation`, `A-S1-bindings`, S1 nodes), accepted Evidence and gateway contact (`A-S2-evidence`, S2 nodes), selected dispatch (`A-S3-dispatch`, S3 nodes), Finding detail (`A-finding-episode`, S4-01), Site FindingIndex (`A-finding-index`, `I-finding-index`, S4-04), Site Overview (`A-S5-overview`, S5), SourceHealth (`A-S7-health`, S7), and onboarding (`A-work-cases` is **not** an onboarding substitute; use the onboarding nodes). Reuse only a path that proves the exact claim. A gap without any current producer remains `data_source/absent` and unrankable, visibly owned for a wave allocation decision.

## 2. Orphan guard

Use a typed missing-state component/API, for example `<MissingClaim gapId="G-readiness-gateway-firmware">Firmware not available yet</MissingClaim>` or `missingClaim('G-…', text)`. The `gapId` is metadata (`data-gap-id` or an internal prop) and never appears in product copy. Static copy and translated keys are keyed by the same stable placement ID; dynamic/conditional branches use the component in each branch. The normal dependency-registry checker validates unique IDs, known panel/screen references, target-wave values, dependency DAG, technical-source status and no `resolved` gap without reviewed source/UI/visual evidence. A source/AST scan of the product UI checks the declared missing-state component calls against the catalogue and rejects untagged literal “not available yet”/equivalent missing-capability copy in the scoped product surfaces; a test renders the registered placements (including missing branches) and compares their `data-gap-id` set to the catalogue. Every open node must be referenced by a real UI placement **or** carry an explicit `unplaced_reason` such as “screen not built until W5”; every UI placement must resolve to a known open gap or a reviewed resolved transition. An unplaced entry is still in the planning inventory and is not a fake rendered state. Exclude docs, tests and unrelated runtime error/zero-result copy from the string scan. Rejected untagged strings yield a file/line and suggested registration, not a silent catch-all ID.

Hook the schema/graph scan into `check_v69_dependency_registry.cjs` and the UI orphan scan into `tools/check-all.ps1`; add focused frontend Vitest assertions for conditional rendering, reload and the known V-01a missing states. `delivery_next_work.cjs` must read the new catalogue but **ignore it for candidate scoring until the owner approves a scoring policy at W1 exit**. During migration the guard checks newly touched/explicitly scoped V-01a placements first with a dated baseline of legacy untagged occurrences; shrink the baseline in each reviewed backfill packet and prohibit new unregistered strings immediately. Do not make an unreviewed whole-repo string sweep a surprise blocker for V-01a.

## 3. Non-core ranking and per-screen completion — owner choice at W1 exit

**Recommended timing:** confirm proposals 1 and 4 now. At W1 exit, after the core W1 work and V-01a/b evidence establish actual gap counts and dependencies, ask the owner to choose 2 and 3 together. Before that decision, non-core gaps are visible and owned but not eligible in `next-work`; the current core formula, K=10 and owner-approved values are untouched. The W1 exit already stops for owner review, so this is the least disruptive scoring-change gate. Do not use a gap node's mere existence to inherit an active-wave demo value or become ready-now.

For **non-core ranking**: (A) recommended for the next wave, a **separate lower-priority non-core lane** after eligible active-wave core paths are exhausted or explicitly blocked, with its own owner-approved screen/panel list and value, reviewable S/M/L technical tasks, and the same `requires`, owner/review stops and ≤5% contested-ranking rule *within that lane*. This protects core delivery and makes eventual closure explicit; it does not alter K or the existing score formula. (B) mix non-core into the existing breadth term with a lower fixed panel weight; this is more responsive but changes `P`, score spread and K calibration, so requires a before/after ranking fixture, owner-approved weight/K and a scoring-change gate. (C) manual per-wave non-core quota/owner picks; simple, but weaker autonomous gap closure. Recommend A for W2 pilot, with an owner option to revisit B once measured backlog/score distributions exist. A non-core gap with no approved producer/contract is not an eligible candidate in any lane; the Architect/Planner first resolves its missing source and owner scope.

For **per-screen completion**: (1) recommended, create a `complete-to-mock` closeout record after its approved core panels and visual gate pass, containing every panel/element gap ID, disposition (`delivered`, `targeted Wn`, `owner_withheld`, or `unplanned pending allocation`), technical/visual evidence and the owner checkpoint. It is **an audit/owner-review item, not a scored technical node** and cannot turn a screen Real while positive gaps remain. At each wave exit, the owner assigns or confirms target waves for that wave's `unplanned` items; an explicit `owner_withheld` is possible only with recorded owner reason and revisit trigger. (2) a scored completion task per screen after core acceptance; clearer urgency but can double count the same technical gaps and create 110 large tasks. (3) no screen closeout, only gap rows; simpler but loses the owner's “when complete?” answer. Recommend 1. The screen reaches full Real only when all non-withheld claims/behaviors have source-to-claim lineage and visual acceptance, and any withheld content has the explicit owner disposition required by the delivery strategy; a conditional visual pass is not completion.

The current ≤5% contest and 5–10% notice apply to whatever eligible lane is active. No later-wave gap or unapproved value enters the active-wave score. Changing panel weights, K or cross-lane priority is a new owner-approved scoring decision, never an Architect-only switch.

# Codex Architect — S3-01 phase-2 rulings (2026-10-11)

These are phase-3 handoff rules for Q1–Q8, subject to the fresh phase-2 review. They amend the S3-01 packet through `D-2026-10-11-s3-phase-2-selection-and-read`; they do not accept the implementation or waive the owner checkpoint.

1. **Q1 — accept controls selected at the run's knowledge cutoff, with dual provenance.** The technical design permits a later time-valid correction to yield a new assessment without changing immutable accepted evidence. Phase 3 must expose both the reading's as-accepted Foundation/binding IDs and the selected control/binding revision IDs used by that run, and name a backdated correction when they differ; it must never describe the later selection as the reading's original acceptance basis.
2. **Q2 — accept Candidate-blocking minimum runtime only.** The public Foundation value and uncertain first-ON bound justify withholding Candidate while the constraint may apply, but a configured value alone is not an authenticated runtime/command record proving policy Necessary. Phase 3 must show “Candidate withheld: configured minimum runtime may still apply” with the selected control value/revision and bound; keep policy Necessary unavailable and never say an operator command did not occur.
3. **Q3 — accept UTC-day, six-hour bracket and first-ON ownership as `dispatch-3` rules.** They give deterministic window ownership and explicit open bounds when bracketing evidence is insufficient; a different calendar or bracket requires a new model version. Phase 3 must display the UTC assessment window, selected interval bounds and any missing-neighbour limitation, and must not create an empty neighbour assessment solely because a job reached it.
4. **Q4 — show the lone stream, with manifest annotation when available; do not hide it by epoch name.** The central ledger has no trusted fixture flag, so hiding it from a generic product read would require the prohibited name heuristic or private manifest authority in the analytic. The default read may show only the stored limited/Indeterminate result and its exact central provenance; in the demo, add a separate “labelled fault fixture in demo manifest” annotation matched by exact public IDs, visibly sourced to the manifest and never presented as central attestation. Do not promote a known manifest fixture to ordinary positive output. If a future fixture can yield a positive ordinary-looking result, a trusted S2 acquisition marker or an explicitly scoped demo selection must precede that claim.
5. **Q5 — accept the same-epoch ambiguity limits.** Sequence inversion and same-channel/time overlap are public contradictions, not grounds to reconstruct private Lab runs, and unusable spans must stay Indeterminate. Phase 3 must name those limits and affected spans/accepted IDs, with no interval claim where the generator series itself is ambiguous; an explicit epoch choice cannot repair same-epoch ambiguity.
6. **Q6 — accept no commit-ordered fence in this S3 slice only with a narrowed read contract.** A lease-time clock cutoff filters decided timestamps but cannot freeze a transaction that commits later; the new S2 job prevents loss and the immutable stored run/evidence set preserves the result actually assessed, yet rerunning the same timestamp can produce a different set. Phase 3 must pin historical drill-down to `analytic_run_id`, revision ID and stored exact evidence IDs/digests, label `knowledge_cutoff` as the worker selection timestamp, and must not offer arbitrary historical `knowledge_at` replay or promise that K alone reproduces a run. Test the in-flight-acceptance race so the prior selected revision becomes stale and the new job/revision wins; a commit-ordered acceptance fence and arbitrary-cutoff replay are a later, separately reviewed S2 acquisition-contract change.
7. **Q7 — accept a derived projection read conditionally; no table is required by name.** Phase 3 must derive the five stated statuses from a consistent tenant/Site/window read of selected run/revisions, the current accepted input basis and every overlapping PENDING/LEASED/FAILED job. `CURRENT` requires matching current basis and no outstanding/failed job; a prior revision remains inspectable as stale, and latest `completed_at` alone is not a selection rule, especially after a reverted input reuses an older run. If this cannot be proven transactionally and across the race, implement the atomic `site_window_projection` before Performance cutover and review it.
8. **Q8 — accept the first-ON-report interval key.** A newly accepted earlier ON report changes the observed physical anchor, so the new key is a new selected interval rather than revision 2 of the old key; immutable old revision URLs must still work. Phase 3's window revision must list only its current interval keys, with a visible supersession/history path for the old key when its anchor moves, and must not show both as active generator intervals.

**Phase-3 gate:** the selected-window/interval API and UI must make the above selection, provenance and limitations visible after reload; compare only supported public-record claims with the file-backed baseline before cutover. A fixture manifest is environment-local and may annotate exact matching IDs in the demo, never fill an analytic input. The fresh Claude phase-2 review may identify defects requiring a bounded fix before phase 3; this ruling does not pre-judge it. No new owner choice is needed for these technical boundaries. The packet's visual owner walkthrough remains required.

Analytics readiness port, and which database suits AssetOps

Two questions from the owner: how big is moving the "What we can conclude now" panel onto the stored Sites, and should AssetOps be on SQL or NoSQL. No code was changed.

In plain words
  1. The panel that says what each analysis can conclude from the records only works for old file-based Sites. All four demo Sites are stored Sites, so today it shows "not available yet" (SR-12b's honest wording).
  2. It only applies to the two mini-grids (Kobo, Kisiwa). The cold room and EV hub have no such panel in the mockup.
  3. Moving it is about 1.55 lane-units (estimate, range 1.3 to 1.9; corrected 14 Nov, D-SR.77). It reuses data and checks that already exist. It needs no new data build, so it would not touch the 3-hour demo prepare.
  4. It does not fit before the Sat 20:00 freeze without pushing something else out. It could fit if the freeze moves to Sun 20:00, or a lane runs out of work early.
  5. My advice: put it first in the deferral list. Without it the client sees an honest "not available yet" line. With it they see one row ("Generator support": Full or Limited, plus what is missing).
  6. Database: stay on PostgreSQL. AssetOps is a records-and-proof system: evidence, money, audit and assessments must agree with each other at one moment. That is exactly what SQL databases guarantee and NoSQL stores mostly do not.
  7. Today's speed is fine (stored range reads 0.3 s or less on the VPS, measured). When readings grow, add time partitioning, and later possibly TimescaleDB. Both are still PostgreSQL. No database change before 17 Nov.

Part A: porting the analytics readiness panel to stored Sites

A1 What happens today

The Site Evidence page asks GET /api/sites/{id}/analytics for the readiness of each analysis. That route (backend/assetops_backend/analytics_api.py) is given the LegacySiteGate (main.py:530, sites/cutover.py:122). The gate refuses every Site that has moved into PostgreSQL, so every demo Site gets 409 AWAITING_EVIDENCE_MIGRATION. SR-12b (in review, D-SR.74) turns that refusal into the plain line "What can be assessed from these records is not available yet for this site."

A3 Port design

Files and functions

  1. New backend/assetops_backend/analytics/stored_declaration.py
    • ROLE_OF_REQUIREMENT: each Dispatch requirement row mapped to its canonical role. Generator state → generator_state; Generator state and output → generator_power; each Load row → feeder_demand (per bound feeder asset); PV capability → pv_available_power; Battery state → battery_soc; Battery capability → pcs_discharge_capability; Reserve policy → the Foundation battery-reserve control. The optional rows (min runtime, stop threshold, operator overrides) map to their controls, or read "not observed" when the stored model has no such record (dispatch_read UNAVAILABLE already says so). A row with no mapping fails closed (not available), never "available".
    • stored_requirements(snapshot, tenant_id, site_id): one query per Site for whether each bound role has at least one accepted GOOD reading, and its latest source time. Use EXISTS/max, not a full count. device_id/signal_id are filled from the selected binding's public asset and signal ids.
    • v3_assessment_view(revision): turns one stored dispatch-3.2 interval revision into the dict that score_readiness reads. It uses claim_limit_read.segment_roles/role_coverage for coverage.inputs (usable vs evaluated segments per role), turns the generator-state missing spans into unobserved_generator_state, and keeps segments[].missing labels. It sets assessed_window so SR-12b's in_window works unchanged. A model other than dispatch-3.2 is refused, as in claim_limit_read.SUPPORTED_MODELS.
    • stored_site_declaration(...): the same output as site_declaration, read in one REPEATABLE READ snapshot.
  2. Store method in analytics/adapters/postgres_assessment_store.py: role_presence(c, tenant_id, site_id, roles) on the caller's connection. The selected intervals are read by the existing selected_intervals, with a range filter added for [from, to).
  3. Route analytics_api.py: build_analytics_router(..., scope=registry.ledger_scope, stored=..., gate=performance_gate). In get_declaration, a stored code takes the stored branch. Legacy codes are unchanged. A closed gate answers the existing 409, which SR-12b already shows as "not available yet". Cold/EV stored Sites answer analytics: [], which the panel already renders as nothing. That matches the mock: cold-evidence/ev-evidence use SiteEvidenceMatrix, not CapabilityReadiness.
  4. Sibling routes (/dispatch, /findings, /assessments/…, /api/findings) stay on the gate. Stored Sites already have their own Performance and Finding routes, and no client page calls these for a stored Site. Porting them would duplicate those routes.
  5. main.py: pass the scope, the stored read and the gate (about 3 lines).

Tests

  • Unit: role map completeness (every Dispatch requirement maps or fails closed); v3_assessment_view on fixture revisions (covered, a missing PCS span, an unobserved generator span, an unknown problem text that stays not covered); SR-12b's four edge cases through the stored path.
  • Route: stored mini Site → 200 with the T028 shape; legacy Site unchanged; closed gate → 409; cold/EV → empty list; store down → 503.
  • Consistency: on one fixture day, the panel's "missing" roles equal the gaps in the claim-limit section for the same revision. The page must not contradict itself.
  • PostgreSQL integration on a *_test DB fixture (imported mini Site with readings and a selected dispatch-3.2 run).
  • Frontend: one vitest that a stored-Site 200 renders the table (existing component, new fixture).

Parity against the file-backed version

Kobo has a legacy document and legacy evidence (W4-03 u9b, S2 comparison report), so a parity probe is possible. Run it on a scratch clone. Read the file-backed declaration directly from the file store (bypassing the gate inside the probe only) and the stored declaration, then compare:

  • Per-requirement available: must match. The S2 comparison already proved the evidence is the same.
  • Readiness level, ceiling and coverage gaps: may differ, because the stored side scores dispatch-3.2 runs and the file side scored dispatch-2. Each difference is classified (model change, cohort rule, record only in one store), as the S3-01 comparison did. An unexplained difference blocks the merge.

Kisiwa has no legacy evidence (NO_LEGACY_EVIDENCE basis), so there is no parity. It gets fixture expectations and one live read.

Part B: SQL or NoSQL for AssetOps

Recommendation: stay on PostgreSQL (relational SQL). Add time partitioning on the readings tables when they grow. Test TimescaleDB, a PostgreSQL extension, on a copy when readings reach the hundreds of millions. Do not move to MongoDB, a wide-column store or a separate time-series database. Each of those would weaken the one thing AssetOps sells: every conclusion traceable to accepted evidence, at one consistent moment, with money and audit that add up. Nothing changes before 17 Nov.

B1 What AssetOps stores, and why the links matter

What the current design relies on: 57 Alembic migrations; SQLAlchemy Core; append-only tables with insert-only writer rules; REPEATABLE READ snapshots so one page reads one consistent moment (about 110 places in the backend code refer to them); exact decimal money; joins across evidence, runs, revisions and findings for lineage ("why"); and stored period rows plus a response store for range reads. No table is partitioned yet.

B4 Recommendation and reasons

  1. The product is proof, not just storage. A Finding is only worth money if it points to exact accepted evidence and revisions that were true together. Relational transactions and snapshots give that by default. NoSQL makes it the application's job.
  2. The speed problem is already solved inside PostgreSQL. Stored period rows and the response store took reads from 8–21 s to 0.3 s or less (measured). The database engine was not the bottleneck.
  3. Growth has a PostgreSQL path. Time partitioning of the readings tables first. TimescaleDB later, if compression or aggregates are needed. Both keep SQL, Alembic, transactions and the existing code.
  4. A switch would cost months and add risk to exactly the parts (evidence, money, audit) that the client is being shown.

B5 Now, later, and what would change the recommendation

WhenDo
Now, to 17 NovNothing. No database change, no migration.
After the demoMeasure table sizes, readings per day per Site, index sizes and vacuum health on the VPS DB. Measure how the 3 h prepare splits between computing and database work.
When the readings tables near ~100 M rows estimateMonthly time partitions plus BRIN indexes on source time. Keep accepted evidence and everything to its right unpartitioned unless measured.
When raw high-frequency data arrivesTrial TimescaleDB on a scratch clone (hypertables + compression), compared with plain partitions on the same data. Optional: archive raw sub-minute data to files or object storage, keeping only accepted evidence in PostgreSQL.

Rough growth arithmetic estimate, not measured: 50 signals per Site at 15-minute cadence is about 4,800 readings a day, so 1,000 Sites is about 1.75 billion a year. That is comfortable for partitioned PostgreSQL. At 1-minute cadence it becomes about 26 billion a year, which is where compression (TimescaleDB) or a raw archive is needed.

Evidence that would change my recommendation:

  • Sustained ingest that partitioned PostgreSQL on suitable hardware cannot keep up with (measured on a clone, not assumed).
  • Stored range reads going over 2 s at the 95th percentile with correct partitions and indexes.
  • Hot readings past a few terabytes, where compression is no longer enough.
  • A product need for analytics over raw telemetry across thousands of Sites at once. A columnar store such as ClickHouse beside PostgreSQL could then serve that analysis. PostgreSQL would stay the system of record.

None of these points to a document or wide-column store as the main database.

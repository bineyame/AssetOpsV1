# S3-01 phase 2: open questions for the Architect (batched; fail-closed defaults are built)

Context: `tasks/S3-01-dispatch-assessment.md` phase 2, `D-2026-10-11-s3-dispatch-interval-assessment`, `D-2026-10-11-s3-phase-1-fixture-and-late-evidence`, `backend/tests/dispatch_3_decision_table.md`. Each item names the default that is built and what changes if the ruling differs. None of them blocks phase 3.

1. **Which Foundation revision supplies the controls.** Each reading keeps its as-accepted Foundation and binding revision IDs (provenance, hashed). The reserve and minimum-runtime controls, and the role coverage, come from the revisions selected per instant at the run's knowledge cutoff, using the bitemporal `valid`/`recorded` selection. A backdated publication therefore changes a later run, and the decision requires that. Review F5 asked for "the as-accepted revision, not today's". This default does not use today's revision: it uses the cutoff's revision, which equals the as-accepted one unless a later publication was backdated. *Alternative:* use only the as-accepted revision. Backdated configuration would then never change an assessment.
2. **Minimum runtime (row 2).** The Foundation `minimum-runtime` value (TEMPLATE source) is mapped as Candidate-blocking only: Candidate is withheld while `t - first ON report < minimum runtime`. The first ON report is the latest possible start. No policy Necessary is claimed from a configured value, because the decision limits policy-only Necessary to a supported record. *Alternative:* withhold the row entirely. That would allow Candidate claims inside a configured minimum runtime.
3. **Assessment windows.** UTC day windows, a 6-hour bracket, and an interval owned by the window that holds its first ON report. A job's source-time window, widened by the bracket, picks the affected and neighbour days. A neighbour with no reading in it is not persisted and stays UNASSESSED. *Alternative:* Site-local days, or a different bracket. Either is a new model version.
4. **Default cohort.** When a source has overlapping source-time spans under two epochs, the window is `INDETERMINATE` with `AMBIGUOUS_COHORT` and no interval is assessed. An explicit cohort choice is persisted under a cohort-suffixed key (`selection = EXPLICIT`); the S3 demo uses this for the separable 10-05 case. A fault-fixture epoch that stands alone in its window is assessed with the same series limits. It is not excluded by its name: there is no central marker (F4), and the decision forbids the epoch-name heuristic. Its readings only ever give named limits, never Candidate or Necessary. *Question:* should the phase-3 default read hide a lone stream that a manifest labels, or show it with the manifest annotation (F4)?
5. **Same-epoch overlap.** Same-epoch overlap is detected per channel as `SEQUENCE_ORDER_INVERTED` (a reading sequenced after another but placed earlier) and as `REPORTS_OVERLAP` (two readings at one channel-time). Those spans are unusable. On 10-04 this makes every interval Indeterminate. No split is made by sequence range or receipt order (Q3 ruling).
6. **Knowledge cutoff of a job run.** The cutoff is the worker's clock at lease time, filtering `ingestion_disposition.decided_at`. If an acceptance transaction is still in flight at lease time, its `decided_at` can fall before the cutoff while it commits after the query. It is not lost: S2 coalesces only into PENDING jobs, so it creates a new job. A later replay at that same cutoff would include it, though, so the run is reproducible only up to in-flight transactions. *Alternative:* a commit-ordered acceptance watermark on the ledger, which would be an S2 schema change.
7. **Projection table.** `site_window_projection` is not built in phase 2. The phase-3 read can derive `CURRENT`/`STALE_PROJECTION`/`PENDING`/`FAILED` from the latest default run per window plus overlapping PENDING/LEASED/FAILED jobs. *Question:* should phase 3 add the projection table, or keep the derived read?
8. **Interval key.** The interval key is `dispatch:interval:<generator asset>:<first ON report>`. If late evidence moves an interval's first ON report earlier, the new run uses a new key. The old key keeps its revision, and the new run does not select it. The window revision lists the current interval keys. *Alternative:* key by window and ordinal, which is less stable under late evidence.

## What phase 2 needs

1. **Credential verifier**: a `gateway_credential` table (selector, one-way verifier, issued/revoked) in a new migration, an operator provisioning step that issues the secret once into protected gateway config and enables the gateway and named sources (Q2; import leaves both disabled), and a `GatewayPrincipalResolver` adapter passed to `create_app(gateway_principals=…)`. Derive the principal from the credential row + gateway row only. TLS enforcement at the serving boundary. The ledger writer guard allows only the six ledger tables; credential writes need their own confined writer or a guard extension (keep rule 8a's confinement pattern).
2. **Gateway transport**: send exact sealed Batch V2 bytes with `Authorization: Bearer …`; parse the response with `parse_canonical_receipt_v2_text` and verify batch ID, payload digest, ordinal count and each message ID against the sealed batch before writing the SQLite `acknowledgement` rows (`gateway/assetops_gateway/ledger.py:142`). 202 / timeout = retry the same bytes. 245 batches for the Kobo run → bounded upload loop.
3. **Diagnostics**: `gateway_diagnostic` table and `POST /api/gateways/{id}/diagnostics`, `GET /api/sites/{id}/gateway-health` (not built here).
4. **Lab Commit**: replace the `REGISTERED_COMMIT_UNAVAILABLE` refusal with the release manifest path; it must not call the ledger in process with a privileged principal.

## Risks / open

- `received_at` per evidence row is the batch's first receipt instant (Q6). Receipt `received_at` likewise.
- `decide` returns message_id `""` for an envelope the strict batch parser would already have refused; unreachable through `submit`.
- Concurrent submits of the same batch serialize on the batch row lock; a large batch with `chunk_size=1` under contention is slow but correct.
- No `gateway_diagnostic` / credential rows yet; the network route is closed by construction (`ClosedGatewayPrincipals`).

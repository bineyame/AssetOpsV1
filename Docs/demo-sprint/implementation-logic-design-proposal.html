Review summary

In plain words. AssetOps promises one chain: outcome → drivers → evidence → lever → action → proof → status again. The build stores the facts of that chain well (evidence, Findings, Actions, verification), but it never stores or owns the chain itself. Each screen rebuilds it at read time, in its own way. The proposal adds a small chain core:
  1. per-Site-day snapshots (coverage, quality grade, measures and money per day), rebuilt when an event changes their inputs;
  2. Finding threads (one identity per recurring problem, opportunities included);
  3. one versioned chain catalogue that declares sources, measures, finding types, contributions, levers and verification (§5b);
  4. a lifecycle that verification feeds;
  5. one chain read model that every screen renders.

Facts and analytics stay as they are, and window status stays computed (AG-1). The cost is about 72 builder units: about 10 working days elapsed on two lanes before the demo-independent CH-10a/b, plus about 3 days for those. A demo-critical subset of about 21 units clears every High issue except the time and row-composition ones.

5b. The chain catalogue, demonstrated (AG-8, AG-13 to AG-15, AG-19)

In plain words. One file, B/chain/catalogue.yaml, declares how the outcome mechanism is wired: where evidence comes from, what is measured each day, which findings and opportunities can be raised, how they affect outcomes, which levers can be pulled, and how a lever is proven. 11. Trade-offs, risks and performance

  • Trade-off: rev 6 §5.3 is amended (OD-9). Identities and decisions are stored; derived values are not. Gain: the chain is one structure. Cost: four tables and a backfill.
  • Trade-off: Site-local days (OD-7). Gain: one calendar matching the operator's day. Cost: the Kobo board day and captures re-baseline. This is harmless in the demo, because runs are 03:00–11:00 UTC (days.json).
  • Risk: backfill identity. A wrong subject_ref would merge different problems. Mitigation: the subject comes from stored columns (generator_asset_id, cold and EV subject asset), the backfill runs twice to an identical result in a test, and the coherence check runs.
  • Risk: status rule change. outcome-status/4 touches every row test. Mitigation: a truth-table test per rule, then golden boards for each story day.
  • Risk: scope creep into the analytics. Rule: no change to matchers, money models or verification rules. Reviewers treat any such change as High.
  • Performance, tick. The chain stage runs only on days touched by drained jobs:
    • A1 is O(required reads) per day;
    • A2 is one indexed lookup per new revision;
    • A5 is one insert per new Action or verification event.
    It is bounded by the existing TickLimits pattern (B/scheduling/tick.py:57-76, 120 s per stage); expected cost is far below the s3 stage. Not measured yet: CH-0 adds per-stage timing to the tick log (§11b).
  • Performance, read. Per Site and window, ChainReader issues one query each for coverage, threads with occurrences, chain_action, objectives and prices, plus the existing adapter reads. The contract carries refs, not evidence id lists, so it is far smaller than today's portfolio body (278,215 bytes) and Finding detail (601,880 bytes). CH-5b enforces the budgets in §11b.

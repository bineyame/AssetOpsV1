Long-Running Simulation Proposal

How AssetOps can simulate 91 days of a site's history in a minute or two, inside a quarter of a gigabyte, without changing any result the product already shows.

AssetOps, 28 October 2026. Architect: Claude (.ai/ROLE_CONFIG.md, "Architect Is Claude By Default"). Branch plan/commercial-capability-assessment. Owner request, word for word: .agent/owner-long-running-proposal-2026-10-28.md. The design itself is ruled in Demo Data Strategy revision 4, §13; this document explains it and does not change it. Where they differ, §13 governs. Code claims were re-read at 069bcd61. This is a plan: no code, test or measurement was run for it.

0 The proposal in short

What we propose

Each 91-day history stays one simulation run, with one identity. Inside, the run is worked through a week at a time. Each week is written to disk as soon as it is finished, gets its own fingerprint, and hands its exact end state to the next week. When all thirteen weeks are written, a short index file is written last, and only then is the history published, week by week, through the publication path the product already uses.

The step that makes this possible is small: the new cold-room model keeps temperature to a millionth of a degree, and a rounding ledger records every millionth it rounds away, so the energy books still balance exactly.

1 The problem, measured

We assumed the barrier to 91-day runs was memory: every run path today keeps the whole window in memory. A short timing of the cold-room model showed a different cause. The model uses exact fractions, and those fractions get longer at every simulated minute.

1.1 Why the numbers grow

Each minute, the cold model updates the chamber temperature from the heat leaking in and the cooling taken out. With the default room values (heat leak 0.08, thermal capacity 1.2), the update works out to:

T_next = T × 899/900 + (a constant)

Because the arithmetic is exact, the fraction is never simplified away. Every minute, the bottom of the fraction (its denominator) is multiplied by 900, which adds about three digits. After one day the temperature is a fraction whose denominator has 4,254 digits. After 91 days it would have about 387,000. Every later step has to multiply and add numbers of that size, so each step is slower than the one before.

Technical detail: where this is in the code

FACT simulator/assetops_simulator/packs/cold.py:408-412: heat = (heat_leak × (ambient − T) + door × door_heat × 60) × 1/60 and t_next = T + (heat − cool) / thermal_capacity, all in Fraction. Defaults at cold.py:68-73: 0.08 / 60 / 1.2 = 1/900, so the coefficient on T is 899/900. heat_total accumulates the same growing terms. The kernel's own rule is that "nothing in this module limits a denominator" (kernel/execute.py:34). log10(900) ≈ 2.954 digits per step × 1,440 steps = 4,254 digits, which matches the measured value exactly.

1.3 Why memory was never the root cause

Memory and time were both symptoms of the same thing: very long numbers. Fixing memory alone (streaming) leaves the long numbers in place, so the run still takes hours. Fixing the numbers alone makes the physics fast, but the run still holds about a gigabyte of finished results. Only both together fit the laptop.

Technical detail: what each cell is made of

Measured with bounded precision: keeping every transition for 7 days peaks at 31 MB, about 1.2 KB per step; rendering the v1 private minute records and their canonical JSON adds about 6 KB per step (93 MB peak at 10,080 steps). Extrapolated to 131,040 steps: transitions about 160 MB, private rendering about 0.8 GB. With exact arithmetic the retained state runs to tens of GB and the private text to about 200 GB (§13.1). The other two models behave differently: EV v1 already rounds allocation to QUANTUM_KW = 1 (packs/ev_charger.py:38), and the mini-grid kernel's flows are additive with constant efficiencies, so INFERENCE its denominators are bounded by the constants. A guard test (§3.4) checks both, and DD-05a measures the kernel.

2 Conceptual foundation

None of the six parts below is new. Each is the standard answer that long-horizon simulation or time-series software already uses for the same problem. That is the point: the design is made of well-tested ideas, applied where AssetOps has the same shape of problem.

1 Fixed-point state with a rounding ledger

Precedent: deterministic lockstep simulation (networked games, physics engines that must replay identically on every machine) and accounting's rounding-difference account.

Idea: hold numbers on a fixed grid so they stay the same size forever, and write down every bit that was rounded away so totals still add up.

Why it applies: the cold model needs exact, repeatable energy books, not unlimited digits. A millionth of a degree is at least 1,000 times finer than any reading the simulated probe publishes, so no published value changes; the ledger keeps the balance check exactly zero.

2 Generator pipeline with bounded memory

Precedent: the Volcano iterator model used by database engines, Unix pipes, and keyed state in stream processors such as Flink.

Idea: each stage asks the stage before it for the next record, handles it, and passes it on. Only the small state each stage needs is kept.

Why it applies: the transform from physics to readings needs only the previous few minutes, never the whole history. Memory then depends on the state, not on how many days are run.

3 Indexed (cursor) series forcing

Precedent: EnergyPlus weather files, read hourly and held across shorter steps by position.

Idea: to find this step's weather, compute its position in the series. Do not search the whole list.

Why it applies: today the kernel checks every input against every step, about 229 million checks for a 91-day mini-grid run. With a cursor it is one lookup per column per step.

4 Append-only weekly segments, manifest last

Precedent: Kafka log segments; Zarr and Parquet chunked files with a metadata file; git's streamed object hashing.

Idea: write the data in closed chunks, and write a small index of the chunks last. If the index is missing, the write did not finish.

Why it applies: AssetOps already treats a run with no artifact as INTERRUPTED and writes artifacts by atomic rename. Weeks also line up with five-minute slots and with Mondays.

5 Incremental digests, byte-identical framing

Precedent: streamed hashing in git and content-addressed stores; any hash that is fed piece by piece.

Idea: feed the fingerprint the same bytes in the same order, piece by piece, and you get the same fingerprint as hashing the whole at once.

Why it applies: today's fingerprint is the hash of one compact JSON text, ["profile",[r1,r2,…]]. That text can be fed record by record, so the long path gives the same fingerprint the short path would.

6 Exact state hand-off at week boundaries

Precedent: checkpoint and restart in long scientific simulations; segment-by-segment integration in numerical solvers.

Idea: the end of one chunk is the start of the next, carried over exactly, so cutting the run into chunks changes nothing.

Why it applies: it is what lets the run be both one history and thirteen checkable weeks. A test proves it: seven 1-day pieces equal one 7-day piece, record for record.

2.1 The rounding ledger, pictured

Technical detail: the precision rules per model
  • Cold, new version cold-thermal/2: after each step, T is rounded half-even to TEMPERATURE_QUANTUM = Fraction(1, 10**6) °C. The quantum must be at least 1,000 times finer than the probe's declared output resolution, which the transform already applies half-even once (observation/transform.py:216-220). DD-06 checks this.
  • EV, new version ev-charger/2: any power that depends on state of charge (taper) is floored to QUANTUM_KW before it is applied, the v1 rule extended.
  • Mini-grid: no change expected; DD-05a measures whether its denominators grow, and stops if they do.
  • v1 profiles keep exact arithmetic. Their windows are at most two days, and their pinned fingerprints must not move.

3 The algorithm, step by step

3.1 In plain steps

  1. Register one run. The scenario names its real public input series and that series' fingerprint. The backend checks the step budget (at most 131,040 steps) and fixes the run's identity.
  2. Pass 1, week 1. The host starts the model from its initial state and pulls one minute at a time: model, then readings, then both fingerprints, then one line appended to the week's file.
  3. Close the week. The file is renamed from .partial to its final name. Its line count, fingerprint and the fingerprint of the model's end state are noted.
  4. Hand over. Week 2 starts from week 1's exact end state. Steps 2 to 4 repeat for all 13 weeks.
  5. Commit. The index (the "head") is written last, by atomic rename. Until it exists, the run reads INTERRUPTED, as today.
  6. Pass 2, publish week by week. For each week, the reports are grouped by their publication instant and released through the existing ordered release, which already resumes from the last admitted instant after a crash.
  7. Downstream, nothing new. The gateway seals admissions; ingestion accepts evidence; provenance sees one registered run; assessment, money and verification read it as they read any run.

3.2 Pseudocode

# Pass 1: execute and write every week (nothing is published yet)
state   = engine.initial_state(scenario)           # registry keyed by model profile
forcing = ForcingSeries(scenario.series)           # lookup = (offset - start) // cadence
whole   = IncrementalDigest(prefix='["<profile>",[')  # v1 framing, fed piece by piece
segments = []

for week in calendar_weeks(run.start, run.end):    # 10,080 one-minute or 2,016 five-minute steps
    seg = SegmentWriter(f"seg-{week.index:02}.partial")
    for record, reports in engine.iter_window(state=state, start=week.start,
                                              end=week.end, forcings=forcing):
        line = canonical_json(record)
        whole.feed(line)                           # same bytes as hashing the whole list
        seg.append(line, reports)                  # one line per record; week digest fed too
    state = engine.end_state()                     # exact hand-off, nothing reset
    segments.append(seg.close(end_state_sha256=digest(state)))   # rename .partial -> final

write_head_atomically(run_id, whole.finish(']]'), segments)      # commit marker, written last

# Pass 2: release by segment through the existing ordered release
for seg in segments:
    groups = group_by_published_at(seg.read_reports())
    _release(run_id, basis, schedule, instants=groups, target=seg.end)  # resumes at admitted_through
Technical detail: files, schema and what is held in memory

Files: var/executions/<run_id>.d/seg-NN.private.jsonl and seg-NN.reports.jsonl, one canonical JSON line per record. Head: var/executions/<run_id>.yaml, schema 8, long-run/1, with the projection fields, boundaries_total, the whole-run content_digest and series_digest, reported_count and segments: [{index, from, to, boundaries, private: {sha256, lines}, reports: {sha256, lines}, end_state_sha256}]. The framing ["<profile>",[r1,r2,…]] equals sha256(canonical_json([profile, records])) byte for byte, because canonical_json uses sorted keys and no whitespace (contracts/assetops_contracts/source_envelope.py:1076-1080; today's cold digest is host/cold_publication.py:228). Today's writer already writes .yaml.partial then renames (host/lab_execution.py:1888-1923).

Held in memory during the run: the model state, the transform's carried state, held reports, two hash objects, the open file handles and counters. In pass 2, one week of groups (cold: 10,080 instants, INF about 20 MB).

Extension seam: host/long_run.py defines a small LongRunEngine protocol (open(verified) → iterator of (private_record, reports), state_digest()) and a registry keyed by model profile; runs/service.py's freeze rule becomes a table keyed by profile. Each model adds one module and one row (long_run_cold.py, long_run_ev.py, long_run_mini.py), so the EV and mini-grid work can proceed in parallel lanes.

3.4 Exact state hand-off

Technical detail: the guarantees tested
  • Byte-identical v1. v1 run_window becomes ColdRun(tuple(iter_window(..., state=ColdState.initial(...), close=True))); schema 6 and 7 artifacts, the pinned digests and the W2 vectors do not move.
  • Digest equivalence. On a 2-day window with the v1 profile label substituted, the long path's private records, report texts, content digest and series digest equal the v1 path's.
  • No numeric growth (the regression oracle). Every long-run profile runs for 1,440 and 10,080 steps; the largest state denominator may grow by at most 8 bits and time per step by at most 1.5×.
  • Determinism at 91 days. Cold and EV take minutes, so DD-09 and DD-10 run the full 91 days twice and compare head digests and every end_state_sha256.
  • Crash behaviour. A kill during pass 1 leaves no head (INTERRUPTED); a restart rewrites every segment and yields the same head. A kill during pass 2 resumes from admitted_through with no duplicate admission.

5.4 The label

The run's scenario names its input series (ambient_series, session_series or forcing_series) together with that series' manifest fingerprint. Because the run is still one registered simulation whose scenario carries that reference, the server derives the label exactly as planned, with the same money terms as any registered simulation: Simulated with real public inputs. No new source class and no new money rule are needed (DD-12 is unchanged).

6 Risks and measurements still owed

The real remaining risk: publication time

Each reached minute that carries a reading is its own sealed admission at the gateway (host/gateway_publication.py:128-153). A 91-day cold run is up to 131,041 admissions; an EV run up to 26,209. Nobody has timed that yet. DD-05a times a two-day registered cold release and extrapolates. If the whole producer (model, gateway, ingestion, assessment) projects over 30 minutes, the builder stops and the Architect rules. The ordered-publication rule is not changed in advance.

6.2 Stop conditions

  • A shipped scenario or fixture changes its outcome, or any v1 fingerprint or schema 6/7 artifact changes.
  • The mini-grid's denominators grow with step count, or its time per step grows more than 1.5× from 2 to 7 days (DD-05 then needs a precision rule).
  • Memory grows with window length (more than 20% between 7 and 91 days), passes 0.25 GB as a target, or reaches the 1.5 GB hard stop; or pass 1 exceeds 5 minutes for cold.
  • Publication projects the whole producer over 30 minutes.
  • The resolver reads the weekly batches of one run as more than one source.
  • A v2 public reading differs from v1 at the published resolution on a W2-02 case; the Architect rules whether the quantum or the case changes.
  • Machine rules: keep-awake on, and a 2× wall-time cap that stops the host process.

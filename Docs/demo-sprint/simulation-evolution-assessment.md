# Simulation evolution and longitudinal histories

**Assessment, 26 October 2026.** Read with [commercial capability readiness](commercial-capability-readiness.md) and [integration baseline](integration-pilot-baseline.md). This evaluates the current runtime; it does not propose a general digital twin. The old [scenario options](scenario-options.md) and [five-day plan](five-day-plan.md) are earlier demo hypotheses, not long-run proof. No simulator, host, backend or test code was changed.

## Current behavior and actual limits

`simulator/assetops_simulator/kernel/execute.py` advances an interval to its declared end, with phased events, controller view/intent, physical acceptance, evolution, sampling and public projection. It holds evolving stocks and discrete state in a live `_World`; `packs/mini_grid.py` couples power/dispatch/fuel with step-aligned generator and policy transitions. `packs/cold.py` uses an exact one-minute thermal step and five-minute public slots for one room. `packs/ev_charger.py` models a bounded charger/connector world, not an entire bus fleet. `backend/assetops_backend/scenarios/execution.py` binds declared events and frozen inputs. `host/{cold,ev}_publication.py` maps public reports; `host/lab_execution.py` projects and stores completed/failed artifacts. The latter explicitly records a live run as `INTERRUPTED` after restart because it has no serialized world checkpoint. Gateway batch identity/queue can resume delivery (`host/tests/test_registered_gateway_publication.py`); that is **not** physical simulation resume.

There is **no universal 24-hour kernel limit**. The product run parser (`backend/assetops_backend/runs/parsing.py`, `MAX_INTERVAL_MINUTES`) allows up to **100,000 minutes = 69 days 10 hours 40 minutes**, requiring a positive whole-minute UTC interval divisible by the configured step. A 60-day interval (86,400 minutes) fits the parser; 90 days (129,600 minutes) is rejected. Parser acceptance does **not** demonstrate memory, storage or UI viability. Cold/EV shipped scenario paths in `runs/service.py` additionally require the scenario's frozen start/end and one-minute step; extending their date by changing only the request is refused. Cold pack `run_window` itself walks `[start,end)` minute by minute; its scenario and artifact integrations remain the effective restriction. Step-aligned mini-grid event deadlines and scenario/event limits also constrain arbitrary long histories. `host/tests/test_mini_grid_v2.py` includes deterministic replay and longer-step tests; `host/tests/test_lab_cockpit_window.py` contains restart-interruption proof. Both focused host test files passed here (43 tests together); this verifies their named cases, not a continuous multi-day mini-grid run.

| Time concept | Present contract | Needed longitudinal decision |
|---|---|
| Physical simulation step | Configurable run timestep within 1–1440 minutes in parser; cold/EV published scenarios use one minute; events/control follow step boundaries | Keep one-minute where thermal/charger transients require it. A five-minute step needs domain invariants and step-alignment tests before use. |
| Device observation interval | `observation/transform.py` and per-domain observation definitions sample/project after physical state; cold public slots are five minutes; gaps/quality can be injected | Define profile cadence per signal, with exact interval-mean vs point semantics and no fake interpolation. Do not infer service from sparse data. |
| Ingestion/replay delivery cadence | `host/lab_execution.py:advance_publication` and `gateway_publication.py` release boundary-ordered reports; delayed publication retains source time | Batch/replay can be faster or slower than simulated time; choose bounded batches and preserve both source and receive clocks. Never re-stamp old observations as fresh. |

## Smallest safe evolution

1. **Repeat and compose frozen scenarios with state continuity.** Provide a versioned multi-day schedule of exogenous weather/load/route/door inputs and declared maintenance/policy/fault events. Feed an ending state into the next window through an explicit public *simulation* run lineage, without resetting battery SoC, fuel, room temperature, charger state or counter epochs. Keep exact UTC half-open boundaries. First prove two adjacent days equal an uninterrupted two-day execution at the same step and publication profile. Existing day-window assessments should consume the resulting accepted evidence without seeing private state.
2. **Lift a product limit only after measurement.** If a 90-day single run is necessary, revise the 100,000-minute parser bound and associated document/output limits through a deliberate architecture decision. An alternate is 60–90 linked day/week segments with exact continuity; this may fit current selected-window analytics better and bound artifact size. Do not silently call disconnected day fixtures a continuous history.
3. **Use compact, declared longitudinal changes.** Gradual battery or compressor decline should be an explicit versioned law/parameter schedule only when needed for a chosen claim. Repeated fault/repair events must change future physical observations, not write Finding or Action outcomes. Current `finding_episode.py` can recognize a particular mini generator-support recurrence when accepted coverage/off proof exists; other vertical recurrence needs domain-specific evidence rules. Work performed, Finding no longer observed, `VERIFIED` technical outcome and verified commercial value remain distinct.
4. **Preserve comparison integrity.** Freeze the same exogenous load/weather/schedule/price basis and initial stock for baseline and intervention, change only the named intervention, and publish both through observation/gateway/ingestion. A paired simulated difference is a *modeled opportunity*. The existing `actions/verification_rules.py` later-window mini trial has narrow comparability bands and can be inconclusive; it is not general causal proof. Realized commercial value requires actual accepted before/after operational and customer business records, adjusted for confounders and approved by the beneficiary.

**Checkpoint choice.** Completed/failed artifacts are persisted; a running world's physical state is not. First measure 60-day runtime and failure frequency. If rerunning a frozen segment is cheap, deterministic segment boundaries plus manifests/checksums are simpler than serialized `_World` checkpoints. If a run is costly or must survive interruption, introduce an explicit versioned checkpoint at a step boundary containing stock/discrete state, pending events, RNG state if used, profile/source identifiers, publication watermark, and hashes of frozen inputs/code. Prove uninterrupted vs resumed public byte identity; never resume a changed model as the same run. Physical checkpoint and gateway outbox watermark must be separately reconciled to avoid missing or duplicated observations.

## Longitudinal story and evidence boundary

One credible validation story is: weeks of baseline with a recurring generator support or cold backup event → accepted episodes and bounded consequence → an investigation with alternative causes → recorded maintenance/policy change → later accepted observations → technical criterion evaluated as pass, fail or inconclusive → separate qualified business comparison. Recurrence needs an actual off/normal observation between episodes; a data gap is not recovery. Source-quality disturbances should include delayed upload, unavailable/stuck sensor, meter reset, contradictory second source and clock skew, with provenance and unknown states preserved through Site/Estate. Multi-site orchestration can initially be a manifest of separately registered runs and shared wall-clock/currency/tenant selection; a general scheduler is unjustified until a real portfolio benchmark demonstrates a need.

The physical world may project the **same state** into a canonical gateway report, a virtual Modbus register bank, a CAN BMS frame, an EV CSMS-style session export, or a room-controller/logger payload. Every interface projection has a versioned mapping and its own sampling/error behavior. An adapter then decodes that interface back into canonical observations and uses the existing gateway; product inference sees only accepted public evidence. Simulator truth remains an inaccessible oracle used to test physical accuracy and adapter loss. The first one or two emulations with the strongest reuse are a documented Modbus TCP register profile (mini-grid meter or cold controller) and a CSMS API/session fixture for EV. A CAN virtual-bus demonstration is warranted only if a customer signal depends on CAN; transport proof is not OEM compatibility. See the [CAN route and support classes](integration-pilot-baseline.md#can-to-host-lab-concretely).

## Focused benchmark and correctness gate

**Observed, 26 October 2026.** In the project virtual environment with `PYTHONPATH=backend;contracts;simulator;gateway;host;.`, two identical executions of each two-day pack sample completed well under five minutes and 2 GB. Timing includes pure pack execution, public projection and digesting; peak memory is the Windows process peak working set, measured in a fresh process per pack. Inputs were fixed and contain no faults, sessions or gateway upload. The packs have no seed parameter; the same fixed inputs were used twice. A same-seed mini-grid attempt is described below.

|---|---:|---:|---:|---|
| Cold, default parameters, 3 deg C start, 25 deg C ambient, no events; full DeviceReport V2 rendering | 4.259 / 5.280 s | 65.1 MB | 2,880; 4,074 | `ef31f2dc15a5dd6f51fe9b7c4e92c2f4453dde6c82a73aa166509981f00562fb` |
| EV, default charger, no sessions or faults; public record projection | 0.910 / 0.884 s | 38.4 MB | 2,880; 9,794 | `948e8f14d6b6f7331157f3e2b54e3b2411b96733f29a661120757575be945add` |

Cold also produced 4,074 device observations on both runs. The cold public digest hashes ordered serialized DeviceReport V2 bytes; EV hashes ordered public record identity/time/value tuples. A raw exact-fraction text conversion in an exploratory cold digest hit Python's 4,300-digit integer limit after two days; the normal observation/report projection above completed. This makes private artifact size and long-run exact-rational growth a specific risk to measure. Neither sample exercised the gateway, ledger, DB, analytics or UI, so queued envelopes, accepted rows, query latency and storage growth remain unknown.

**Observed mini-grid limit.** A two-day `kobo-mini-grid-prolonged` v2 Draft with five-minute steps and seed `20260929` was `READY` at setup but executed only 95 steps (475 minutes): `FORCING_NOT_AVAILABLE` for plane-of-array irradiance after the shipped forcing window. Two attempts produced the same 200 public observations and public digest `a0c3926cf994210f42e0561e816c60da70fe0e6c2308366765a3927d5df0199f`; the private trajectory digests differed because the generated run IDs differed. This is a failed two-day mini-grid run, not a throughput result. The focused mini/cockpit tests passed 43/43; they do not supply a multi-day forcing schedule.

**Extrapolated planning estimates, not observed 60-90-day performance.** Simple multiplication of these idle two-day samples suggests 60/90 days would have 86,400/129,600 one-minute steps, roughly 122,220/183,330 cold observations and 293,820/440,730 EV public records at these exact profiles. Multiplying sample time gives roughly 2-4 minutes for cold and 27-41 seconds for EV. These are lower-complexity baselines: exact fractions, event density, repeated sessions/faults, projection algorithms and artifacts may scale nonlinearly. Memory, envelopes, Postgres growth, ingest and query time cannot be projected responsibly from them. Mini-grid has no 60-90-day estimate until a frozen forcing schedule actually covers the interval. The 100,000-minute parser cap still admits 60 days and rejects 90 days; that is a syntax limit, not a performance gate.

Next, freeze representative multi-day forcings for each pack, then measure kernel, public projection, gateway/ingest, DB/index, analytics and Site/Estate reads separately. Correctness gates remain single versus segmented execution, same seed/input public digest, 60-day UTC/DST boundary, 90-day parser refusal or approved limit, repeated maintenance/fault, episode off proof, delayed/duplicate/out-of-order replay, source-only product rebuild and identical paired exogenous basis. Set performance acceptance from the measured pilot rate.

## Tradeoffs and deferred complexity

Segmented continuity is easier to audit and restart but needs exact stock/counter boundary state and cross-segment episode stitching. A single long in-memory run is simpler semantically but risks memory, artifact and restart cost. Sparse observations reduce ingest volume but can hide transient faults; sample by decision need and mark gaps. Higher-fidelity degradation laws can improve a story while adding calibration burden; defer until a measured claim depends on them. Defer adaptive physics stepping, generic checkpoint infrastructure, fleet-scale charger/vehicle physics, automatic multi-site orchestration and a broad protocol emulator suite pending benchmark or prospect evidence. The existing private-truth/public-evidence, time and immutable provenance contracts remain intact.

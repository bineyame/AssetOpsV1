## What the current pipeline proves

`simulator/assetops_simulator/observation/transform.py` creates a reported-device view separate from kernel truth. `host/{cold,ev}_publication.py` and `host/gateway_publication.py` stage canonical reports into a durable simulated gateway. `backend/assetops_backend/gateway_api.py` authenticates batch ingress; `evidence/ledger_service.py` records decisions and `evidence/{source_provenance,provenance_read}.py` provide source class and exact lineage. Focused `host/tests/test_registered_gateway_publication.py` and `test_registered_gateway_delivery.py` passed (19 tests), as did cold/EV publication and vector tests (39 tests) with this worktree's packages on `PYTHONPATH`. `backend/tests/test_s2_evidence_ledger_postgres.py` remains present but unexecuted because no DB was created. These results exercise the simulated canonical path; no real equipment, OEM API, MQTT broker, Modbus poller, CAN frame collector or OCPP server was identified in the inspected host/backend Python. A raw vendor sample must not be called accepted evidence until its authorization, identity, mapping and quality have passed the actual gateway/ingestion chain.

Support classes used below: **1** demonstrated working in the registered simulated canonical path; **2** configuration/mapping required; **3** bounded engineering required; **4** new adapter or hardware required; **5** unknown/unsupported. Class 1 does not transfer automatically to a field device. Separate acquisition from the existence of downstream analytics.

These are reference sites for discovery, not claims about installed fleets. Cadences are *proposed minimums* to validate with source retention and business decisions. Preserve source timestamps in UTC plus received time, stable device/source IDs, units, sign, counter epoch, mapping version and raw payload reference. Physical observations and commercial records travel as separate classes and may have different clocks.

## Acquisition routes and responsibilities

The reusable flow is **source → collector/adapter → versioned normalization → existing gateway queue → authenticated batch ingress → accepted/rejected evidence → domain assessment/Site/Estate**. Keep source bytes or lawful immutable references, source/received clocks, source record key and mapping version. On adapter failure, retain bounded local batches, retry idempotently with backoff, expose queue age/health and mark gaps. Clock drift, reset, wrong units/polarity, stale values, duplicate/conflicting source and cross-site identity require fail-closed controls. TLS, least privilege, outbound connection, credential rotation and site-scoped authorization are commissioning work; no OT write access is proposed.

| Route | Relevance and support now | Required engineering / failure boundary |
|---|---|---|
| **HTTPS API, webhook or scheduled JSON/CSV export** from EMS/OEM/logger/CSMS | Best first-pilot candidate; generic canonical HTTPS ingress is class **1** for registered simulation, vendor-specific API/export mapping is **2–3**, generic CSV importer is not proven | Read-only connector or controlled file loader; auth, pagination/rate limits, field dictionary, stable IDs, raw capture, timestamp/unit validation, 429/5xx retry. Existing gateway should own durable delivery; do not send vendor payload directly into analytics. |
| **Existing customer gateway / offline file feed** | Class **2–3** if it emits accepted canonical batch shape; historic backfill may need **3** engineering | Versioned mapping and per-file checksum, source time and counter epoch; staging/replay in event-time order; no invented freshness. Offline acceptance is not a live monitor. |
| **Modbus TCP/RTU read-only** | Class **4** until a real poller, test server, documented register map and wire proof exist. TCP may reuse across mini/cold; RTU adds serial/isolation | Collector near device polls only documented read functions; unit ID, register width/endian, scaling, sentinel, sign, rollover, polling cadence and failure state pinned to model/firmware. Never expose fieldbus to Internet. |
| **MQTT** from existing site broker | Class **4**; gateway queue is not proof of MQTT broker/client support | Broker/topic auth, retained/out-of-order messages, QoS/reconnect, payload mapper and replay. Avoid a broker in the first pilot if a suitable API/export exists. |
| **EV CSMS/OCPP-related** | Class **2–3** for authorized CSMS API mapping; **4** for new API connector; direct OCPP termination unsupported (**5**) | Map CSMS session, status and meter events, revisions/duplication and charger–vehicle identity. OCPP-shaped JSON fixture is not a wire-level OCPP server or billing certification. |
| **CAN/CANopen/J1939** | Class **4–5**; no identified decoder or field profile | Authorized frame definitions/DBC/PGNs, interface and isolated read-only capture, lost-frame and clock handling. CAN transport alone says nothing about a specific BMS/controller. |

**Priority.** Mini-grid: EMS/OEM read-only API/export first; fallback documented local Modbus TCP via a customer-approved collector or historical export. EV bus: CSMS API/export plus fleet roster/depot meter first; fallback scheduled CSMS export and fleet CSV, with vehicle readiness withheld if IDs do not join. Cold: existing independent logger API/export first; fallback approved probe/door/power sensor gateway or controller read-only Modbus where the manual and installer support it. These paths minimize field installation, reuse the canonical gateway, and can support a paid bounded diagnostic before hardware is fitted. They do not require building every candidate adapter.

## CAN to host-lab, concretely

For a *lab* demonstration, choose one authorized, versioned BMS frame map. On Linux, `vcan`/SocketCAN can carry a scripted frame replay; on this Windows host, a WSL2 Linux environment may support `vcan`, but native Windows and physical USB-CAN driver compatibility must be confirmed. Containers add device pass-through and clock complexity; no container is needed for an initial WSL2 virtual-bus proof. A replay process emits timestamped ID/DLC/data plus drop, invalid sentinel and reconnect cases. A small **read-only collector in the existing host-lab composition** decodes only pinned IDs/DBC signals (endianness, signedness, scale, offset, enum, units, validity/range), assigns source/device/observed times and mapping version, and produces the existing canonical report shape. It must not read private world state when acting as the adapter. `host/gateway_publication.py` then queues/retries through the same authenticated ingress. Disconnect the collector/network, verify queued original source times and one accepted disposition after reconnect; reject bad BMS ID, scale and stale SOC. The field migration substitutes an isolated USB/industrial CAN interface and customer-approved bus connection, retaining the decoder contract and commissioning checks. It still requires model/firmware mapping, OEM permission, electrical safety and on-site comparison to a trusted display. For demos, a Modbus TCP register-emulation route may be a more reusable first wire proof; CAN is compelling only when a prospect's critical signal actually resides there.

## Minimal runnable proof and gates

Recommend **one** external-interface proof: a documented Modbus TCP virtual meter or a mock EMS/CSMS HTTPS API, selected after buyer/source discovery. Feed realistic data through the production adapter → canonical mapping → existing durable gateway → authenticated ingestion → Site Evidence → one domain Finding or bounded consequence. A direct canonical fixture is the class-1 regression control. Acceptance: raw device/API payload and mapping version trace to exact accepted IDs; right-unit/normal, absent metric, wrong scale, duplicate, delayed, six-hour outage/reconnect and cross-site identity cases give expected rejection/unknown/replay; private simulator truth cannot be read by product; repeated upload changes no totals. Label proof layers **canonical fixture**, **vendor-shaped payload**, **protocol wire**, **physical equipment**. A wire emulator establishes only that documented test profile, not OEM compatibility.

First-pilot gates follow Pack 03, reconciled with current code: **demo/outreach** needs one rehearsed source-to-claim chain and explicit claim limits; **prospect feasibility** needs authorized 1–7-day sample, exact device/API/version and data dictionary, source rights, meter/probe topology, cadence/retention, buyer, financial hypothesis, security and support owner; **commissioning** needs observed modes, mapping/polarity/calibration, one reconciled operational day where feasible, outage/reboot/replay, identity isolation, credential handling, accepted data completeness and customer sign-off on exceptions. No aggregate score overrides missing authorization, safety or minimum evidence. The Hardware Pack's six-profile catalog and Modbus-first default should be ratified only after a prospect identifies the actual source. Do not claim a protocol, OEM, SoH, spoilage, verified saving or applicable certification from this assessment.

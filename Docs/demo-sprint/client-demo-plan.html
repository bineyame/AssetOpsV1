2.4 Finding → outcome link until CH-8, and how it converts (OL-1, agreed)

In plain words. Until CH-8, which findings affect which outcomes stays in one place in the code, written as plain data in exactly the shape the catalogue will use later. At CH-8 that data is exported to the catalogue and proven to give the same results, and the code table is deleted. Until then, adding a new kind of finding, or changing what it affects, is still a code change.

Before CH-8: one structured declaration

  • The table. B/outcomes/outcome_map.py is the only declaration of finding → outcome. Its ENTRIES table (lines 16–38) maps 4 Findings, 3 signals and 7 warnings.
  • CH-6 reshapes it into typed records, CONTRIBUTIONS: tuple[OutcomeContribution, ...]. These records are data, not logic, and their fields are exactly those of a future catalogue "outcome contributions" entry (design §5b.4). 
    OutcomeContribution(source,      # "FINDING:GENERATOR_SUPPORT_CANDIDATE" | "SIGNAL:…" | "WARNING:…" | "MEASURE:productive_kwh"

                    rank,        # 0 = primary
                    driver,      # e.g. "avoidable_generator_runtime"
                    direction,   # "ADVERSE" | "FAVOURABLE" | "CHECK"

  • Compatibility. Today's ENTRIES and the resolver functions are derived from CONTRIBUTIONS. A test asserts that the derived ENTRIES equals today's literal table, so the nine current importers do not change.

  • Guard. No finding → outcome wiring exists anywhere else. CH-6 adds a backend ratchet guard, the pre-demo part of AG-31's backend guard:
    • It fails on any new outcome-id literal (MG-n, CC-n, EV-n), or any construction of a map key, outside outcomes/outcome_map.py and outcomes/catalogue.py.
    • Today's literal sites (17, design §8b item 7) form a frozen baseline, each labelled with its owner, CH-6 or CH-10a. The baseline may only shrink.

  • Slices. CH-6 owns all of this. CH-1a and CH-2 declare no outcome link: their sheets say so.

At CH-8: conversion recipe

  1. Export. python -m assetops_backend.chain.export_contributions writes CONTRIBUTIONS to the catalogue YAML outcome_contributions: section, one entry per record with the same field names, sorted. The export is mechanical: no field is renamed or computed.
  2. Equivalence test. OutcomeEvaluator runs with each source, the code table and the catalogue. It must give byte-identical outputs:
    • on the CH-6 contract fixtures (all story days, three Site types, plus the synthetic fourth type);
    • on an L3 clone for every Site × story day.
  3. Delete. Remove CONTRIBUTIONS and the derived ENTRIES; the importers read the catalogue loader. The ratchet baseline drops the two allow-listed files.

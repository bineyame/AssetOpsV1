Build and Test Performance

Why a full AssetOps test run now takes hours and runs the machine out of memory, and a ranked plan to bring a full check down to about 20 minutes and an everyday check to under 10, without dropping a single test.

AssetOps, 28 October 2026. Architect: Claude (.ai/ROLE_CONFIG.md, "Architect Is Claude By Default"). Owner request, word for word: .agent/owner-build-test-performance-2026-10-28.md and .agent/owner-test-pipeline-review-2026-10-28.md. Code read at main e234bcd2.

Status

Recommendation only. Nothing has been implemented. No code, test, configuration or CI file was changed. The only things run were small timed samples (one test file at a time) and reads of earlier test reports. Every "after" number is an estimate, and section 6 says how each one will be checked. Measured numbers are marked measured.

0 In short

The test suite is not slow because there are too many tests. Two thirds of the tests take less than a tenth of a second each. Nearly all the time goes to about 550 tests. Each of them rebuilds a complete simulated site from nothing before it checks one thing: it creates a database, installs the site, starts a real gateway program and replays a day of readings into it. Then it throws all of that away. The next test builds the same site again. About 15 different site set-ups are rebuilt more than 900 times in one run.

The memory problem follows from this. Each rebuild starts extra Python programs and opens about 20 database connections, so running several tests side by side does not fit in the memory the laptop has free. On 28 October the suite therefore had to run in pieces, almost one test at a time. That took about five hours.

What we propose

Build each site set-up once, then hand every test its own instant copy. PostgreSQL can copy a whole database in about a second, and the test tools already use this for the empty database. We extend it to the built sites: build each one once, save it as a template, and give each test a fresh copy. Each test still gets its own private database, so tests stay independent.

Around that change: run full suites only inside Docker, where memory has a fixed ceiling. Use a separate test database server tuned for speed instead of safety. Put the few deliberately slow tests in their own tier. Run only the tests a change can affect on everyday slices. Make two small settings changes on the frontend.

What this says

The build is not the problem: type check and bundling take under 40 seconds together. Neither is the frontend: a few minutes, and it improves with one setting (section 5). The problem is the backend suite. It holds about 4 hours of work. Four workers in parallel turn that into an hour. When memory forces the run down to one worker, it takes most of a working day.

2 Where the time goes

2.1 A few tests carry nearly all the time

2.2 Which tests they are

We grouped every test by what its file does. The slow group is the tests that build a replay chain: a simulated cold room, EV charger or mini-grid site whose readings are replayed through a real gateway into the evidence store.

2.3 Inside one slow test: almost all of it is set-up

We ran one portfolio test by itself and timed it, and profiled a second one.

The clearest sign of repeated work is test_w206_ev_reads_postgres.py. It has 23 tests, and every one of them takes 25 to 30 seconds. That includes test_non_ascii_limit_is_422_ev_limit_invalid, which only checks that a bad page-size value is refused. It still spends 26 seconds first rebuilding a full EV charging site. The cold-room file test_w203_cold_replay_postgres.py shows the same pattern: 14 tests at 16 to 20 seconds each.

2.4 The same few set-ups, built hundreds of times

The replay fixtures are built from a small set of named cases. Cold room: normal, excursion, backup-failed, late-reading, missing-probe, contradictory. EV: complete, interrupted, fault, missing-meter, late-record, contradictory. On top of those: the four-site portfolio and the mini-grid power estate. That makes roughly 15–25 distinct set-ups. They are fixed: the clock is frozen and the IDs are pinned, so each build of a case comes out the same. Yet they are rebuilt for each of the 909 replay-chain tests, and in the 26 October run that cost about 10,000 seconds.

2.5 Smaller, real costs

  • Every database statement from Windows is a trip into Docker. We measured 1.95 ms per round trip and 29.5 ms per new connection from the host measured, against about 0.17 ms inside Docker's own network (OPS-01 record). One portfolio set-up issues about 15,000 statements, so on the host that is about 30 s of waiting on the network alone. The Docker test runner already avoids this, but the 28 October gate did not use it.
  • The test database server is set up for safety, not speed. It writes every change safely to disk (fsync=on, full_page_writes=on) and shares one server with the development databases. The earlier timing notes record disk-sync stalls of 22–25 s in a single step under load. They also show the same full run taking anywhere from 49 to 78 minutes.
  • Deliberate waits. A few tests wait on a real clock on purpose. Schedule health waits 120 s for a job to go stale. The tick-cost test runs 140–180 s, and the hung-stage test 137 s. Together that is about 450 s, 3% of the total. The TEL acceptance tests replay a field device at 60× real time, so each one takes 9–12 minutes.
  • Frontend set-up overhead. Each frontend test file starts its own simulated browser in a separate process. We sampled the 16 largest files (960 tests). In the default mode (forks) that took 92.7 s, with 152 s of browser start-up summed across workers. With threads it took 55.7 s, with 38 s of start-up measured. All 960 tests passed both ways.

3 Where the memory goes

The laptop has 16 GB. When idle, about 13.2 GB is already in use (Windows services 1.5 GB, Claude 1.4 GB, Chrome 1.1 GB, memory compression 1.1 GB, the Docker VM 0.9 GB, other programs about 7.2 GB). That leaves about 2.8 GB free. Claude Code stops background jobs when free memory runs low, and it stopped both whole-suite runs.

Two other facts matter here. First, the Docker VM is already capped at 4 GB (%USERPROFILE%\.wslconfig: memory=4GB), so a run inside Docker cannot grow beyond that. A run on Windows is not capped at all. Second, building a site starts three gateway programs and opens about 22 database connections, and every one of the 909 replay-chain tests does this. Building once and copying cuts both kinds of load roughly in proportion to the time it saves.

4 Root causes

  1. Each test rebuilds its world (about 70% of the time). The replay fixtures are function-scoped: each test calls pg_harness.fresh_database(), then installs the site, provisions credentials, starts python -m assetops_gateway serve, and replays and uploads a day of readings (backend/tests/test_w202_cold_replay_postgres.py and test_w205b_ev_replay_postgres.py, class Chain; test_w303_portfolio_fixture_postgres.py:build_portfolio_fixture). These fixtures were written one slice at a time, and the suite has grown from 2,128 tests to 4,138. Each new slice added more tests that rebuild the same few sites.
  2. Too little memory leads to serial runs, which take hours. Each test worker, with its gateway programs and database connections, needs a few hundred MB, and only about 2.8 GB is free. Runs on Windows were stopped, so the gate fell back to one worker in pieces: 4 hours of work run end to end, plus the network cost below.
  3. The host path pays a network toll. 1.95 ms per statement and 29.5 ms per connection through Docker Desktop's port forward, about 11 times the in-Docker cost. A faster runner already exists (tools/run-backend-suite-in-container.ps1, the default in .ai/ROLE_CONFIG.md), but the 28 October gate ran on the host.
  4. A database server tuned for safety. Tests do not need data to survive a crash. Synced writes cause the slow, unpredictable stalls, and they make timings vary from 49 to 78 minutes, which hides real regressions.
  5. A few tests use the real clock as their subject. They are slow on purpose, and they also tend to be the flaky ones under load. Each run, 3% of the time goes on them, and so does a share of the reruns.
  6. Everything runs on every change. Most slices touch one area, but the merge gate and the "safety net" both run all 4,138 tests. Nothing yet works out which tests a change can affect.
A hazard found while measuring (not about speed, but it wastes runs)

The shared virtual environment AssetOpsV1-plan2\.venv points its installed AssetOps packages at the stale AssetOPsV1 checkout: assetops_backend.__file__ resolves there. Any run without the right PYTHONPATH tests old code, or fails to import. Our first sample failed that way: No module named 'assetops_backend.cold_replay'. Recommendation R9 fixes this.

6 Phased plan and how each phase is proven

Phase 0: measure the baseline (0.5 day)

  • Add a memory sampler to the Docker runner. Every 5 seconds it records free Windows memory, the Docker VM size, worker sizes and the database connection count, alongside the connection sampler that already exists.
  • Record each test's set-up and check time separately (--durations=0 to a file). That turns the 85–95% set-up share from three samples into a measured number for every file.
  • Then do one full Docker run on a quiet machine as the baseline.

Proof: the baseline report (time, peak memory, peak connections, pass list) is saved under var/test-results/. It is the yardstick for every later phase.

Phase 1: quick wins (1.5 days): R2, R3, R5, R7, R9, R10

  • Full runs only in Docker; a separate fast test database server; a slow tier; vitest threads; the worktree-safe run command; memory guard rails.

Proof: two back-to-back full runs. The same collected test IDs as the baseline (a diff of --collect-only output). The same pass list from JUnit. Zero skips, and the slow tier run separately with its results recorded. The frontend gives the same pass count under threads.

Phase 2: build once, copy many (4 days): R1

  • Add a snapshot/restore pair to pg_harness: database template plus file folder, and a gateway restart when a test needs one.
  • Convert the replay families in order of payoff: EV reads and money (w206, w207), portfolio (w303), opportunities and work (w403), cold replay (w202, w203), estate (w301, w302), depth and intent (w5xx), then the mini-grid case fixtures.
  • Keep a named set of build-live tests that still check the replay itself.

Proof: after each family, compare that family's files old against new: same IDs, same pass list, and a stored-row fingerprint (row counts per table) of copy versus fresh build. At the end, two full runs with the same IDs and pass list as the baseline.

Phase 3: reuse between runs and test-impact selection (2.5 days): R6, R4

  • Name saved set-ups by fingerprint and keep them between runs (database names end in _test, as the rules require). Sweep the stale ones.
  • Add the tools script that maps changed files to affected test files, with an always-full list (migrations, conftest, pg_harness, scenario and fixture data, main.py/composition, guard scripts).

Proof: a change in a set-up's inputs must trigger a rebuild (a deliberate test of this). The selection script is checked against the last 10 merged slices: for each one, every failure the full suite found must sit inside the selected set.

Phase 4: virtual time (2.5 days, second lane): R8

  • A stepped clock shared by the TEL device emulator and poller. Use the injectable clock in the schedule and stale tests where the product already supports one.

Proof: the same observations arrive, with the same counts and fingerprints, under virtual time and under one real-time run. The real-time TEL run stays in the milestone tier.

9 Decisions for the owner

Nothing starts until you approve. The Architect's recommendation for each decision is given with it.

D1. Approve the plan and its order (phases 0 → 1 → 2 → 3, with 4 in a second lane)

Recommended: yes. About 11 builder-days in all (about 8.5 calendar days with two lanes). The plan goes ahead of the data lane, as your 28 October instruction says.

D2. Allow test fixtures to be rewritten to "build once, copy many" (R1)

This touches about 100 test files and pg_harness. It changes no product code and no assertion. Proof is an identical test list and pass list. Recommended: yes. This is the change that turns hours into minutes.

D3. Allow a second, test-only PostgreSQL server with crash safety turned off (R3)

The current rule says "server-wide settings are never changed by the tests". This would not change the existing server; it adds a new one used only by tests. Recommended: yes.

D4. Adopt the revised testing policy in section 7

Slices run only the tests the change can affect. Merges run the full fast tier. The slow tier runs at schema and plumbing merges and nightly. Recommended: yes, once phases 1–3 have passed their proofs. Until then the current tiered rule stays.

D5. Memory settings on your machine

(a) Lower the Docker VM cap from 4 GB to the measured peak plus headroom (expected 3–3.5 GB). (b) Close Chrome during full runs. (c) Whether to set CLAUDE_CODE_DISABLE_BG_SHELL_PRESSURE_REAP=1. These are your settings, and agents will not change them. Recommended: (a) and (b) yes. (c) not needed once runs stay inside Docker; leave it off so the machine stays protected.

D6. Frontend in threads now, and a later happy-dom trial

Recommended: threads now (measured −40% on the sample). happy-dom only as a separate trial, because some browser behaviour differs from jsdom.

D7. Whether phase 4 (virtual time) and R11 (screenshot audits by change) are funded now or deferred

Recommended: phase 4 now in the second lane, since TEL-08 will add more acceptance runs. R11 at the next audit round.

10 What could not be measured

  • Peak memory of a whole run. No sampler exists yet, and a full run was outside this brief. The per-worker and total figures in section 3 are built from single-test samples. Phase 0 measures it.
  • The real saving from R1. It is estimated from three samples and the JUnit timings. The set-up share for every file is measured in phase 0, and the saving itself in phase 2.
  • The gain from a speed-tuned database server (R3). It needs a second server, which is a configuration change.
  • Memory growth of a long-running worker over hundreds of tests (engines or caches left behind).
  • The guard script tools/check-all.ps1. It was not timed, because it starts PowerShell with an execution-policy override, which this brief forbids running.
  • The 1,414-pair screenshot recapture. No timing is recorded in the packets, so R11's saving is not quantified.
  • One unexplained outlier. test_w302_money_comparability_postgres.py::test_w302_money_persisted_ev_different_currency is reported as passing alone in 3,933 s (over an hour) during the CC-M gate. That is far beyond its peers and needs its own look; it may be a connection wait or the machine sleeping.
  • The TEL acceptance timing (9–12 min) is taken from the handoff and was not re-run.

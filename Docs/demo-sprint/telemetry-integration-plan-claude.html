Telemetry integration plan: customer data first, physical hardware early

The plan covers mini-grid, EV and cold-chain sites. It identifies what customers already run and the few integration patterns that cover most of it. It defines proofs that exercise the real adapter, the real gateway and the standard ingestion path. Two tracks run side by side. The customer’s own cloud or export is the most likely first source of real pilot data. A BeagleBone Black and ESP32 edge shows early, on real hardware, that we can also reach equipment that has no cloud.

0 · The plan in one page

What customers actually have

Most target customers already pay for a vendor or operator cloud that holds their data. AMMP, the closest comparable business, leads with cloud-to-cloud integrations that need “no extra hardware and no site-level configuration”, and keeps its edge box for “non-API equipment” fact. Mini-grid inverter makers (Victron VRM, SMA, Huawei, SolarEdge, Sungrow, Solarman/Deye, Growatt) all run clouds with APIs or downloads. Operator CSMSs such as Monta export charges as CSV or Excel. Logger clouds such as Monnit have an API. The equipment underneath (a Victron GX on Modbus TCP, RS-485 meters and refrigeration controllers) is what we need for sites, or measurements, that no cloud covers.

Two tracks, one gateway

Customer-data track (P1, P3): a collector reads the customer’s export file or pulls their cloud API, and feeds a hosted instance of the existing gateway. This is the shortest route to real pilot data: no site visit, no LAN access, no hardware. Hardware track (P2, P4, P6): a read-only poller on a BeagleBone, with an ESP32-S3 RS-485/CAN bridge where needed. This gives credibility, and covers what clouds miss. Both emit the same DeviceReport into the same IPC admit. Outbox, sealing, TLS upload, provenance and analytics are shared.

Proofs, in this order

B customer cloud or export collector: first a VRM-shaped installation export into the Kobo mini-grid roles, then a live API pull when a customer gives a token. A Modbus TCP from a Victron-GX-shaped emulator into the same roles, rehearsed on the BeagleBone. C EV: CSMS charge export first, real OCPP 1.6J traffic second. D Modbus RTU, virtual first, then a ~$13 probe for an R3 claim on our own bench.

Before 30 October (about three working days, one heavy job at a time)

Build the shared core once (profile, exact scaling, interval means, IPC publish). Then a thin export collector (proof B1), then the GX emulator and Modbus TCP poller (proof A). Both run end to end on the laptop, into two bench Sites from the same Kobo foundation. Then rehearse A on the BeagleBone. Order the ~$100 hardware kit now. The owner decisions needed first are D1 (how emulated and customer-supplied evidence is labelled) and D2 (the two bench Sites), in §14.

Bottom line on hardware

The BeagleBone Black can run the whole existing gateway. The gateway and contracts use only the standard library. The current Debian 13.7 IoT image for the BBB ships Python 3.13.5, which satisfies the gateway’s requires-python >=3.12, whereas Debian 12 ships 3.11 and does not. The BBB fills the same role as AMMP Edge for a prototype. The Waveshare ESP32-S3-RS485-CAN ($18.99–19.99 on Waveshare’s page, with isolated RS-485 and CAN and a 7–36 V input, all confirmed) is a good field-side bus bridge. It has no Ethernet, only Wi-Fi, so it should feed the Linux gateway and not replace it. A bench kit of about US$100 on top of the BBB enables every hardware test in this plan (§9).

Seven repository facts the earlier document did not state, and which change the plan

G1 · The gateway declares Python ≥ 3.12

gateway/pyproject.toml and contracts/pyproject.toml both say requires-python = ">=3.12". Both packages use only the standard library (sqlite3, ssl, http.client, multiprocessing.connection, fractions), which is good news for a small ARM board. The BeagleBone's Debian 12 image ships Python 3.11 (§7), so the BBB needs a newer image or a separately installed interpreter. Do not lower the declared version without running the gateway suite on 3.11.

G2 · LIVE already exists end to end, except at the two SIMULATED-only gates

LIVE is an allowed mode in the gateway ledger (ledger.py:41), in Batch V2 (ingestion_batch_v2.py:62) and in the central gateway/site tables (migration 0001). The central ledger compares the batch mode with the registered gateway's mode (ledger_service.py:200) and does not refuse LIVE. A LIVE gateway already stamps OBSERVED_DEVICE_REPORT instead of OBSERVED_SIMULATED_REPORT (service.py:1110). The blockers are: (a) snapshot activation (snapshot.py:263); (b) the pre-admission publication, which requires a SIMULATED gateway (postgres_evidence_ledger.py:395).

G3 · Without a publication, emulated data is accepted but its provenance reads UNKNOWN

Publications are optional for ingestion. source_provenance.py classifies any accepted ID without a publication binding as UNKNOWN, "never a real measurement and never authored". That is honest but not useful in a customer conversation. An emulated-interface proof needs its own source class. §13 asks for this decision.

G4 · Power signals are interval means, so the poller must aggregate

The Kobo mini-grid profile (backend/assetops_backend/runs/profiles.py, LAB_PUBLICATION_PROFILE from line 1411) publishes PV, battery and feeder power as INTERVAL_SIGNAL every 15 min, and generator power every 60 min. Battery SoC, fuel level and generator status are STATE_SIGNAL every 15 min. Modbus returns instants, so the adapter must compute an exact mean of polls over each [interval_start, source_time) and declare a coverage rule. With too few polls the interval becomes UNAVAILABLE / NO_COMPLETED_INTERVAL, and nothing is interpolated. The same applies to cold compressor-meter / power (INTERVAL_MEAN, kW) and EV connector power.

G5 · A real gateway has no clock-offset measurement

clock_offset_ms in GatewayDiagnosticsV1 is filled only by inject_clock_offset, which is SIMULATED-only (service.py:1148). The health_observation table already allows provenance MEASURED (ledger.py:286), and disk pressure already uses it (service.py:1134). An edge box needs a small measured probe, for example from chronyc tracking. Without it, F03 clock-drift evidence on real hardware is empty.

G6 · The edge ledger grows without limit

Envelopes, batches, batch items and diagnostics have never_deleted triggers (ledger.py:182-295). A canonical V3 envelope is about 620 bytes (from contract-fixtures/source-envelope-v3-vectors.json), and batch payloads store the same envelopes again. Kobo's 10 signals at 15 min generate about 960 envelopes a day, which is a few MB a day before indexes. That fits a 4 GB eMMC for a pilot, but faster cadences, the gateway's disk STOP threshold and archive or rotation must be measured (§7).

G7 · The central TLS boundary affects the bench network

gateway_api.install_gateway_tls_boundary returns 426 for any credentialed gateway request that is not HTTPS or that carries X-Forwarded-Proto/Forwarded. A reverse proxy in front of the backend therefore breaks gateway upload. The bench must use python -m assetops_backend.serve_tls directly. It binds 127.0.0.1 by default, so it needs --host 0.0.0.0 (or the laptop's LAN IP) and a certificate whose SAN names that address.

G8 · Every IPC client can call every op

The IPC credential authenticates a peer but does not scope it. A field adapter holding the key could call activate, release_run or deliver. read_credential (ipc.py:135) does not check file mode, so the key can be given to a separate adapter account. For least privilege, an adapter credential should be limited to identity, admit and diagnostics. This is a small change, and it is recommended before a pilot, not before the bench.

Why the customer’s cloud or export is the most likely first path to pilot data
  1. The market leader says so. AMMP’s default is cloud-to-cloud with “no extra hardware and no site-level configuration”. Its edge box is the exception, for “non-API equipment” fact H.
  2. The equipment makers already run the clouds. Of the inverter and battery brands AMMP lists, every one checked in §2 has a cloud with an API or a download: Victron VRM, SMA, SolarEdge, Huawei, Sungrow, Solarman/Deye, Growatt fact/inf M–H. EV operators’ CSMSs export charges (Monta, fact) or expose session APIs (Monta, AMPECO). Cold-chain logger clouds expose APIs (Monnit), and USB loggers produce files (Fridge-tag).
  3. It is the cheapest “yes” for a customer. An export emailed today, or a read-only token, needs no site visit, no OT network access, no IT approval for a device on the LAN and no installer. Hardware at a pilot site needs all four inference H.
  4. It reaches real data first. One genuine export is an R3 claim for that format. Our own hardware bench reaches R3 only for the probes we buy (§6, Figure 0).

Its limits are why the hardware track still matters. Clouds give 5–15 minute aggregates under tight quotas (SolarEdge 300 requests/day; Monnit about 1 data call per 10 minutes; SMA Live “not allowed for constant monitoring”). They miss cold-room controllers, feeder meters and gensets that have no cloud. They also make AssetOps depend on another vendor’s availability. Customers with older or mixed equipment have no cloud at all.

4 · Recommended integration architecture (deliverable 2)

The rule that keeps this cheap: no new path to the ledger. Every source, cloud or field, becomes a DeviceReport handed to GatewayService.admit through the authenticated IPC. The gateway then does what it does today: snapshot checks, holds, sequence, outbox, sealing and HTTPS upload with receipts. Central ingestion, provenance and analytics need no change for a new protocol. They change only for the labelling gates in §1.

Adapter anatomy, shared by every path

  1. Transport: export file (CSV/XLSX dropped into a watched folder, or uploaded), HTTPS client (cloud API), TCP socket (Modbus TCP), serial port (RTU), WebSocket log or REST (CSMS). The transport owns timeouts and backoff.
  2. Decoder: MBAP/CRC frames, JSON pages, OCPP-J frames. The Modbus FC allowlist {1,2,3,4} is enforced here, before the socket.
  3. Pinned profile: a JSON document with a source document ID and version, mapping each source field to (device_id, signal_id), type, word order, scale exponent, sentinel, unit, reading class and cadence. Its SHA-256 is recorded with every raw capture.
  4. Report builder: exact-decimal scaling, interval-mean aggregation with a coverage rule (G4), counter epochs, and a stable report_key. Output is DeviceReport V1 or V2 text.
  5. Gateway admit over IPC: unchanged on main. A hold returns its kind and field to the adapter’s log and to diagnostics.
  6. Raw capture: frames or response bodies with SHA-256 in an adapter-local, size-bounded store. The ledger is never used for vendor bytes.

What the export track proves

7.5 Time synchronisation

  • The BBB has no RTC battery. Every cold boot starts at a wrong time until NTP answers fact H. Modbus has no timestamps, so source_time is the gateway clock. A wrong clock would make plausible but wrong evidence.
  • Use chrony. The poller starts only after time-sync.target (enable chrony-wait.service or systemd-time-wait-sync), and it also checks chronyc tracking leap status before each publish cycle. If the clock is not synchronised, it publishes nothing and logs that state.
  • Large step corrections while running (offline boot, then network): the gateway already refuses future source times (SOURCE_TIME_IN_FUTURE). The poller must also treat a backward step as an interval break. The interval is discarded, not averaged.
  • Record the measured offset into diagnostics (G5) so F03 evidence exists on real hardware.
  • On a site without internet NTP, point chrony at the GX or the site router if either serves NTP. Otherwise, add a small I²C RTC module (inference; a DS3231-class part costs a few dollars). The Waveshare ESP32 board already carries a PCF85063 RTC.

7.6 Storage endurance and capacity

  • Put the ledger on the 4 GB eMMC, not on a microSD card. Keep the microSD as a recovery image. eMMC endurance figures for the BBB were not found (unverified), so measure, do not assume.
  • Reduce writes that are not evidence: journald Storage=volatile with forwarding, noatime, no swap on eMMC, and raw capture capped in size and kept on tmpfs during the bench.
  • Evidence writes are small: one WAL transaction per admission chunk, plus seal and receipt transactions. Kobo’s 10 signals at 15-minute intervals are about 960 envelopes a day, about 0.6 KB each plus batch copies and indexes. Estimate a few MB a day, to be measured.
  • The ledger never deletes (G6). For pilots longer than a few months, an archive-and-rotate procedure is needed: export acknowledged batches, verify receipts and start a new sequence epoch with reprovision-epoch. That is design work, not bench work. The existing disk WARN/STOP thresholds are the safety net and must be configured for 4 GB.

7.8 Networking, serial interfaces and security

Networking

The BBB has one Ethernet port. On the bench, use the USB gadget network (laptop is 192.168.7.1, BBB is 192.168.7.2) and keep eth0 free. On a site where the OT LAN and the uplink differ, add a USB Ethernet or Wi-Fi adapter as the second interface, or use the site router’s VLAN. Never expose :502 beyond the OT segment. nftables rules: default deny; outbound 443/8443 to the backend only; outbound 502 to the OT subnet only; inbound 22 from management only.

RS-485

Now: a virtual serial path (§7.9), no hardware. First hardware: an isolated USB-RS485 adapter, such as the Waveshare industrial isolated USB TO RS232/485/TTL at $19.99–23.99, which has power and signal isolation (fact H; its isolation voltage is not stated). The $7.99 USB TO RS485 (B) has surge and ESD protection but is not isolated, so use it on the bench only. Later, a cape: the Waveshare RS485 CAN CAPE is listed as discontinued and states no isolation. Prefer USB isolation or the ESP32 bridge.

Security

Remove the image’s default login and demo web services. SSH keys only. Separate accounts for gateway and poller. The upload credential is 0600 and owned by the gateway (checked by the code). The IPC key copy is 0400 for the poller. Read-only OT: the FC allowlist in code, a firewall limited to :502 on the OT subnet, and, where the customer agrees, a Modbus read-only account or a GX setting. Recommended before a pilot: IPC op scoping (G8) so a poller key cannot call activate or deliver.

8.4 Isolation and power

  • Isolation on both buses removes the most common field failure in modbustcp.html Figure 4 (ground loops), but the rating is not published. Ask Waveshare before claiming it for mains-adjacent cabinets.
  • 7–36 V suits 12 V and 24 V DC systems and many 24 V control supplies. A 48 V battery bank exceeds 36 V, which is common in mini-grids (inference, H). Feed the board from a 48→24 V DC-DC converter or the site’s 24 V control supply.
  • On the bench, power it from USB-C 5 V. No mains wiring is needed for proof D’s probe.

8.5 What it enables

Cold chain

RS-485 temperature probes and refrigeration controllers via role 1. Door contacts and 1-Wire probes on GPIO1/2 via role 2. One DIN-rail box per cold room at about $20, with Wi-Fi back to the edge.

Meters

Several RS-485 meters on one bus behind one bridge. The poller reads them as Unit IDs. Same profiles as on USB-RS485.

CAN-based BMS

Many batteries broadcast state on CAN with vendor-specific IDs (inference, M). It is feasible with role 2, but every BMS needs its own pinned frame map, and there is no AssetOps channel for it yet. Defer until a customer names a battery.

14 · Prioritised plan, architectural recommendations and decisions

  1. Customer data first: proof B1 now (P1, a thin export collector through a hosted gateway). Most customers’ data already sits in a vendor or operator cloud (§2 callout). One export or one read-only token is the cheapest yes we can ask for, and the fastest route to real pilot evidence.

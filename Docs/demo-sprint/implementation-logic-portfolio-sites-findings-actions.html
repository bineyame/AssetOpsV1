The ten most important gaps

In plain words. The Findings-to-outcome link is real: an open Finding changes a row's colour. The Action and verification side barely feeds back. A verified Action never changes an outcome's state, never closes its Finding, and is not even recognised as "the action for this Finding" on Portfolio. Most other confusions come from two sources. Each Site and page uses its own time window. The productive-use opportunity is built as a separate object, not a Finding, so Portfolio cannot see it.
  1. I-01, I-02, I-03 Verification does not feed back. ACT-001 is Verified, but:
    • its Finding stays open (SUPPORTED);
    • the Kobo cost row still reads Needs attention on 31 Oct, the trial's own baseline day;
    • the Portfolio row for that Finding says "No action agreed yet", because Portfolio joins Actions on the exact Finding revision and the Finding has been refreshed since.
    See Actions.
  2. I-04, I-05 Portfolio "week" is not a week per Site. Each Site is judged on a different slice:
    • Kobo: the last UTC day of the window;
    • Cold lab: its latest event hour (31 Oct 16:00–17:05);
    • EV depot: its latest event hour (27 Oct 08:00–09:00).
    So the Grow card's "4.50 USD estimated" is one EV hour on 27 Oct, and Kobo's 42.08 USD on 30 Oct never appears on Portfolio.
  3. I-06 The productive-use opportunity is not a Finding.
    • The Kobo board shows an "Opportunity" chip and "25–31 kW of daytime solar unused".
    • Portfolio's productive-use value is hard-coded "Not established" (server) and its opportunity panel is fixed copy (frontend).
    • The Findings "Opportunities" tab can never list anything.
    The v70 mock has it as Finding F-109.
  4. I-07 The Kobo Grow row mixes three things.
    • The state comes from the monthly target (MG-1, 673.3 kWh month-to-date, Met).
    • The headline is the day's estimated sales when there are any, otherwise the 5-day spare-solar figure.
    • The subline is the day's measured use.
    On 31 Oct the state reads On track, the headline is spare solar, and the mill used 0 kWh.
  5. I-08 Cold and EV boards link Findings to API URLs (/api/sites/…/cold/findings/…), not to screens. From code, a click lands on the "route not available" page.
  6. I-09 Cold ACT-002 and EV ACT-003 exist but no board or Portfolio row shows them. Probable cause: they were created at build time (2 Nov), outside the event windows the boards read. Domain Actions are also never "applied", so they cannot change a state.
  7. I-10 Recurrence is not established. Kobo has three separate, identical generator Findings (17, 24 and 31 Oct, each 04:35–07:55 UTC). Cold has two separate start-failure Findings (28 and 31 Oct). Each stands alone, and only the 31 Oct one has an Action.
  8. I-13 The Kobo Assure line hides "missed". It reads "1 of 3 declared objectives met · 1 not checked yet". The third objective (MG-2, missed that day) is not mentioned, because the text template has no "missed" part.
  9. I-14, I-15 "Checked day" means three different things.
    • Portfolio: a day with an assessed dispatch result.
    • MG-1 month: a local day with any good reading.
    • Spare solar: a fully observed local noon hour.
    A day with no data (21 Oct) still shows "25–31 kW of daytime solar unused" from the 5-day look-back.
  10. I-11, I-24 A verified result is not a saving. ACT-001 was judged on one hour (06:00–07:00 UTC, 31 Oct against 1 Nov) and its cost check says "no lower supply cost per kWh". The Assure card always reads "Not known yet" for recovered value.

1. End-to-end data flow

In plain words. A simulator produces one run per story day. A real gateway process delivers it to the ingestion API, which stores accepted readings and queues recompute work in the same transaction. A scheduler tick, every 120 seconds in the demo, assesses the queued work, matches Findings, prices consequences and builds the spare-solar study. Every screen is computed on request from the stored results; nothing is cached. A new day therefore shows after the next tick plus a page reload.

2. The outcome mechanism: outcome → drivers → evidence → lever → finding → action → verification

In plain words. A row's colour (its state) is set by three things, in a fixed order of precedence: open Findings and warnings, then the declared target's verdict, then an open opportunity. The figures you read on the row (headline, contributors) are computed beside the state, not from it. An Action changes the state in one narrow case: a Kobo Action that has been applied softens its Finding from Needs attention to Watch. Whether the Action was verified changes only text: the "Earlier interventions" list, the Assure line and the Portfolio verified count.
computes the value or state changes state only in a narrow case link is only text or an href no link (absent)

2.1 The state rule, exactly

For each outcome on a row (B/outcomes/status.py:55-102), the first match wins:

  1. Outcome not measured in the catalogue: Not measured yet.
  2. Inputs not settled (stale schedule, Site not visited, required read failed): Unknown.
  3. An open primary Finding with no applied Action, or a warning whose effect is Needs attention: Needs attention.
  4. Declared target MISSED: Needs attention.
  5. Any other open Finding (secondary, or primary with an applied Action), or a Watch warning: Watch.
  6. Evidence outcome only: readiness Limited or None gives Watch.
  7. Target verdict:
    • MET or ON_PACE: On track;
    • BEHIND_PACE: Watch;
    • TOO_EARLY or NOT_JUDGED: Unknown.
  8. An open opportunity signal: Opportunity. Since Addendum 2 this step sits below a declared target, so it only shows where no target exists.
  9. Objectives read failed: Unknown. Otherwise: No target for this outcome (wire NO_OBJECTIVE).

The row state is the "worst" of its outcomes, in this precedence: Needs attention > Watch > Unknown > Opportunity > No objective > On track > Not measured > N/A (status.py:34,105-113). Rows are never combined into a score.

2a. Grow revenue: how it is computed

In plain words. Kobo: declared price (0.25 USD/kWh) × the grain mill's measured kWh for the board's day gives "estimated productive-use sales". The row's colour comes from the monthly target (300 kWh a month). The spare-solar study adds the Opportunity chip. EV: declared tariff (0.30 USD/kWh) × metered kWh of completed or observed-aborted sessions gives "estimated charging income". Cold lab: not measured. No Finding is ever Kobo's Grow driver, and no Action targets Grow.

Kobo detail

  • Sales estimate (B/site_outcomes/mini.py:726-764, B/site_outcomes/productive_use.py:37-81):

    • Amount = kWh × price, rounded half-up to 0.01.
    • The price is read at the UTC day start (B/site_outcomes/read.py:281-283).
  • Monthly target MG-1 (B/outcomes/objectives.py:127-143, judge_month), first match wins:

    2. value ≥ target: MET;
    3. month complete and every day checked: MISSED;

    • The month is the Site-local calendar month (mini.py:549-596).
  • Spare solar:
    • Per noon hour: headroom = max(0, capability − used − margin) (B/mini_depth/rules.py:359-372).
    • The board shows min low – max high over ELIGIBLE days in the last 5 local days (rules.py:395-411, mini.py:496-528).

    • money if any, else the spare-solar headline;
    • a zero-use day reads "No productive-use sales on this day…" unless a spare-solar headline exists (mini.py:451-453,761-762).

5. Findings

In plain words. There are four kinds of Finding, each produced by a fixed rule:
  • Kobo: generator on longer than needed;
  • Cold lab: temperature excursion, and backup failed to start;
  • EV depot: charging session interrupted by a fault.

A Finding keeps one identity and gains revisions when its evidence changes. The outcome category it belongs to is fixed by its kind, not judged case by case. A Finding is linked to an Action only through the Action's record of which revision it came from. The Finding itself never learns about the Action.

6. Actions and verification

In plain words. Only Kobo has a complete Action loop. A recommendation (lower the battery reserve by 5 points) is accepted and applied as a Foundation setting change. A verification plan then freezes two one-hour windows, one before and one after the change, and judges them by a fixed rule. The Cold lab and EV depot have "domain Actions" that only declare an intent. They are never applied or verified. A verified result changes labels and counts. It does not close the Finding, does not change any outcome state and does not produce money.

6.1 Creation and states

  • Eligibility (reserve-trial-1, B/actions/reserve_trial.py:31-74):
    • the latest Finding revision is SUPPORTED and current;
    • SOC is above reserve + 10;
    • the reserve is within 15–90;
    • the proposal is reserve − 5.
  • Accept: POST …/findings/{id}/recommendation/accept (B/action_api.py:152). It is a SYSTEM demonstration command; no human approval is recorded (B/actions/lifecycle.py:43-55).
  • Events: ACCEPTED, APPLIED, FAILED, OBSERVED, RESOLVED, RESOLUTION_WITHDRAWN.
    • Application: NONE → PENDING → APPLIED.
    • Outcome: PENDING, then the RESOLVED outcome, or REASSESSMENT_PENDING after a withdrawal (lifecycle.py:22-104).
  • Codes:
    • stored ACT-000001 from action_code_seq (shared with Cold and EV domain Actions), shown as ACT-001 (B/actions/adapters/postgres_action_store.py:283-298, B/outcomes/display_code.py:11-21);
    • the estate action index still shows the title "Action ACT-001" and the code "ACT-000001" live.

6.2 The verification window and how it is judged

  • Plan reserve-trial-verification-1 (B/actions/verification.py:137-270, verification_rules.py:28-40):
    • two 60-minute windows at the same UTC clock hour, each 12 five-minute slots;
    • the baseline ends at or before effective_from; the later window starts after it;
    • the baseline must have positive Candidate seconds (here 3600);
    • the later window must have no readings yet when the plan is frozen.
  • Target: 4 × later ≤ 3 × baseline Candidate-avoidable seconds. Here 0 ≤ 3 × 3600.
  • Guardrails:
    • unserved critical kWh later ≤ baseline;
    • below-reserve seconds later = 0 (five-minute sampled);
    • terminal SOC later ≥ baseline.
  • Comparability: demand and PV energy within ±10%, initial SOC within 2 points, coherent source class.
  • Results: VERIFIED / INEFFECTIVE / INCONCLUSIVE. Only the first two append RESOLVED. Evaluation is API-driven only; no scheduled job runs it (verification.py:750-866, verification_rules.py:715-790).
  • Live outcome: VERIFIED, reasons TARGET_AND_GUARDRAILS_PASS, recorded 2026-11-01 13:00Z. The cost check is MODELLED_NO_IMPROVEMENT, 0 USD work-dir.

B. Root causes

In plain words. The 25 issues trace to five root causes. The deepest is that the outcome chain was never built as one thing. It was assembled late, in about two weeks of slices, as a presentation layer over reads that each part of the product had built for itself. Each screen therefore re-derives the chain its own way: which Finding, which Action, which days, which window. Each slice was accepted on its own screen, so nothing checked that the screens agree.

B.2 Where I agree and disagree with the coordinator's hypothesis

  • H1 "no shared domain model; composers and the aggregator each redo the joins": agree, with one correction.
    • The composers do not re-join raw tables. They consume per-domain read APIs whose shapes and link conventions differ.
    • The defect is a missing canonical read model, not duplicated SQL.
    • It was a deliberate rev 6 choice ("built first from what exists"), made by the Architect (Claude). It traded coherence for speed and was not revisited when the chain became the product's spine.
  • H2 "never a rule for what verification changes": partly wrong.
    • There was a rule (OUT-E, rev 6 §4.4): verification is read back as text, and money is credited only on VERIFIED.
    • What was missing was the state side: the Finding lifecycle and the outcome state. Rev 6 named that gap and the roadmap scheduled only its text half.
    • So the cause is "specified as read-back, transition deferred", not "never specified".
  • H3 "opportunity, declared prices and the KPI split bolted on under demo speed": half right.
    • Declared prices and the KPI/potential split (WALK1-3/3b/5) were added to the board composer under demo speed (mini.py:451-453,726-764). That is where I-07 comes from.
    • The opportunity was not a demo-speed bolt-on. W4-03 deliberately kept it out of the Finding store because the Finding schema could not hold it. The planned union read was never built. That is RC2, a schema-shape cause.
    • "No owner for recurrence identity" is right, and belongs to RC2.
  • H4 "acceptance per slice; 23/23 checks values, not coherence": agree. It is RC5. I add RC4 (time model) as a separate cause: it explains I-04, I-05 and I-14 to I-16, which the other four causes do not.

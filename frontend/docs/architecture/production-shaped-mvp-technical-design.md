# AssetOps MVP technical design

**Architect proposal · 2026-10-06.** Implements [the system architecture](production-shaped-mvp.md). This is a target contract for the first vertical slices, not a description of tables already deployed. Examples use short aliases (`t1`, `s1`, `g1`) for UUID values solely to keep the tables readable; real IDs are UUIDs. All money is decimal, never binary float. Times are UTC `timestamptz`; presentation uses the Site timezone.

## 1. Central PostgreSQL model

### Conventions and migration rules

- Use UUID primary keys generated by the writer, `created_at` on identity rows, and explicit tenant scope. Every Site-owned row carries `tenant_id` and `site_id`; composite foreign keys to `(tenant_id, site_id)` prevent cross-tenant references. `site` has `UNIQUE(tenant_id, id)`. Child tables additionally validate a referenced row belongs to the same site in one write transaction; add composite uniqueness/FKs where a row can be reached directly by API ID.
- Natural identities (`site_code`, `gateway_external_id`, `source_external_id`, `device_id`, `signal_id`) are site-scoped. A gateway is never silently reassigned to another site. `source_mode` is immutable registered provenance (`LIVE` or `SIMULATED`), not caller-provided authority.
- For public configuration use valid time `[valid_from, valid_to)` and recorded time `[recorded_at, superseded_at)`. A correction inserts new rows and closes only the replaced rows' recorded-time intervals; their content and old validity ranges are never edited. At a requested **source instant and knowledge instant**, select a row whose both intervals contain those instants. Publishing a new effective version that splits an open interval inserts a new row for the unchanged earlier segment (same content, new revision ID/version) and a row for the changed later segment, then supersedes the old open row. Enforce no overlapping *currently recorded* valid ranges for the same site/configuration key with a GiST exclusion constraint (`btree_gist`), or with a transactionally locked validation query until the extension is enabled. A backdated correction schedules recomputation; existing evidence retains the version used on original acceptance and can be reinterpreted only in a new derived revision.
- Immutable rows are append-only: database privileges and repository methods allow `INSERT`, not content `UPDATE`/`DELETE`; `superseded_at`, lifecycle pointers and job leases are the few named mutable columns. Status derived from event history is a projection. Use `jsonb` only for versioned domain payloads, not identity, time, joins, amount or evidence lineage. Add `schema_version` where payloads are JSON.
- Application writes operate at `READ COMMITTED` with row locks and unique constraints for identity/idempotence. Time-valid configuration publication uses a serializable transaction or locks the Site row. Use DB migrations; never infer schema from YAML files. Scope queries by tenant at the repository boundary and test tenant isolation before external pilots.

`foundation_revision` holds the public Site definition, not simulated world inputs. `signal_binding_revision` is both the server's registered gateway mapping and the semantic role binding; gateway downloads an immutable signed/versioned snapshot. A mapping set must reference an effective Foundation revision and every bound asset/channel must exist at publication. The raw envelope still states its mapping set/version for audit. A batch is homogeneous in mapping and Foundation reference; the gateway closes one batch and opens another when either changes. Ingestion checks that the **referenced registered versions' original valid ranges** cover each envelope's source time, even if a later configuration correction superseded them while the gateway was offline. It records the accepted-as basis and flags an outdated mapping/configuration; it rejects unregistered versions or times outside the referenced range. Analytics at a later `knowledge_at` may rebind and renormalize the immutable original reading under a corrected time-valid version, recording those new revision IDs in its input set. This never edits accepted evidence. A record dated before any configured period is rejected with a specific reason; it is not assigned current configuration.

For a complete batch refusal before parsing, store a `batch_refusal(id,tenant_id,site_id?,external_batch_id,payload_sha256,kind,detail,received_at)` row only when tenant/site are authenticated and resolvable; otherwise return a structured error without a Site ledger write. This keeps malformed batch attempts visible without pretending they were accepted batches.

## 2. Edge SQLite schema

Use `PRAGMA journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout`, one writer, and a migration table. SQLite is an acquisition ledger, not a product database. Store UTC instants as ISO text. A source stream means `(gateway_id,source_id)`; `sequence_epoch` changes only on explicit reprovisioning, preventing accidental sequence reuse after restore. Local primary keys can be text UUIDs. Example values below correspond to the central examples.

| Table | Key, columns and example | Constraints / write rule |
| --- | --- | --- |
| `gateway_identity` | PK `gateway_id`; `site_id`, `external_id`, `source_mode`, `credential_locator`, `sequence_epoch`, `configured_at`; `g1 / s1 / SIMULATED / epoch-1` | Singleton local row; site/mode fixed after first envelope; no secret in DB. |
| `device_signal_mapping` | PK `(binding_set_id,version,device_id,signal_id)`; `source_id`, `role`, `asset_id`, `source_unit`, `canonical_unit`, `conversion_json`, `valid_from/to`, `snapshot_sha256`; `v3 / generator-controller / status / generator_state` | Immutable signed/registered snapshot; switch active set atomically. | `sequence_state` | PK `(gateway_id,source_id,sequence_epoch)`; `next_sequence integer`, `updated_at`; `g1 / src1 / epoch-1 / 43` | Increment in same SQLite transaction that inserts outbox row. INTEGER is 64-bit; overflow requires reprovisioned epoch. |
| `envelope_outbox` | PK `message_id`; `gateway_id`, `source_id`, `sequence_epoch`, `sequence`, `source_time`, `envelope_text`, `sha256`, `state`, `created_at`, `last_attempt_at?`; `msg42 / seq42 / PENDING` | `UNIQUE(source_id,sequence_epoch,sequence)`; append bytes once; state `STAGED,READY,IN_FLIGHT,ACKED,DEAD_LETTER`. **Crash sequence:** device report → map/validate → `BEGIN IMMEDIATE` → read/increment sequence → derive message ID from `(site,gateway,source,epoch,sequence)` → insert canonical envelope and bytes → commit → select READY rows and seal homogeneous batch in a second transaction → POST → verify receipt digest/IDs/count → persist ack and state in one transaction. On restart, reset `IN_FLIGHT` batches to retryable; never recreate a sealed payload. `ACKED` may be compacted after configured retention and backed-up receipt checkpoint; `DEAD_LETTER` and unacknowledged rows remain. Disk pressure stops acquisition visibly rather than dropping evidence silently. If a device provides a durable event ID, store it in the report metadata and use it for duplicate suppression **before** sequence assignment; otherwise repeated physical samples are distinct events and never silently conflated.

## 3. Core data structures and wire contracts

Python `dataclass`/Pydantic and TypeScript interfaces may mirror these shapes. Names below are logical contracts; JSON wire names use `snake_case`. Strict boundary parsing rejects unknown fields, unsupported schema versions, non-finite numbers and ambiguous local timestamps. Canonical JSON has sorted keys, UTF-8, exact decimal strings and a documented hash algorithm. Do not hash a reformatted request body after receipt.

```text
SourceEnvelopeV3 {
  schema: {id:"assetops.source-envelope", version:3},
  message: {message_id:sha256hex, sequence_epoch:string, sequence:int64},
  source: {site_id, gateway_id, source_id, device_id, signal_id},
  mapping: {binding_set_id, version:int},
  timing: {source_time:UTC, published_at:UTC, interval_start?:UTC, interval_end?:UTC},
  payload: {family:MEASUREMENT|POLICY|OPERATIONAL_RECORD,
            value:decimal-string|enum|null, unit:string, measurement?:string,
            quality?:GOOD|SUSPECT|UNAVAILABLE, unavailable_reason?:string,
            record_detail?:versioned-object}
}
IngestionBatchV2 {
  schema: {id:"assetops.ingestion-batch", version:2},
  batch_id, site_id, gateway_id, source_id,
  source_mode:LIVE|SIMULATED,
  configuration: {foundation_version:int, foundation_valid_from:UTC},
  mapping: {binding_set_id, version:int, snapshot_sha256},
  envelopes: [canonical-envelope-text...], payload_sha256
}
BatchReceiptV2 {
  batch_id, payload_sha256, status:IN_PROGRESS|COMPLETED|REFUSED,
  decisions:[{ordinal, message_id?, decision:ACCEPTED|DUPLICATE|REJECTED|CONFLICT,
              evidence_id?, rejection_id?, kind?, detail?}], received_at, receipt_sha256
}
```

The existing v1/v2 envelope and v1 batch parser remain read-compatible for stored demo history. V3 **changes identity semantics**: `message_id = SHA256(length-delimited(site_id,gateway_id,source_id,sequence_epoch,sequence))`, with the tuple durably allocated once. Exact byte framing and test vectors are part of the contract task; do not concatenate without separators or trust a sender-supplied digest. Sequence scope is `(gateway,source,epoch)`; monotonic arrival is not required. `published_at` is when gateway seals publication, not a second measurement time. Source clock uncertainty is expressed as quality/diagnostic metadata, never correction of `source_time`. Batch V2 is homogeneous in source/mapping/Foundation reference; each envelope is still checked against effective configuration at its own time. The batch hash is over canonical bytes excluding the `payload_sha256` field; the receipt hash similarly excludes `receipt_sha256`. Batch `source_mode` is compared with authenticated gateway registration and is only provenance after that check. Wire IDs for site/gateway/source resolve registered UUID rows; device/signal IDs remain scoped source strings. A production batch must not carry Lab-private cause or truth; keep any Lab run reference in a private manifest keyed by batch ID.

## 4. Transaction and processing contracts

1. **Register configuration.** Publish Foundation and SignalBinding versions together under Site lock. Validate site type, role vocabulary, units, asset ownership and non-overlapping current valid periods. Persist signed snapshot hash for gateway download. Backdated publication enqueues affected windows for recomputation; do not change accepted evidence bytes.
2. **Receive batch.** TLS and gateway credential establish tenant/site/gateway/source. Enforce size/count limits before parsing; resolve external batch ID and digest. Identical retry returns stored receipt; conflicting retry records/refuses without touching prior decisions. A batch with wrong registered mode or configuration reference is refused as a whole.
3. **Decide records.** In one Postgres transaction, lock batch row; for each unprocessed ordinal parse strict envelope, verify identity/sequence and referenced mapping/Foundation validity at `source_time`, normalize with the registered as-accepted conversion, and insert acceptance or rejection plus disposition. Unique message key arbitrates concurrent duplicate deliveries. Equal digest is `DUPLICATE`; changed digest is `CONFLICT` and points to first accepted evidence. Update watermark and create/coalesce recompute jobs in the same commit. Chunk a large batch into short committed transactions; receipt exposes `IN_PROGRESS` until all ordinals are durable. A client retries the same batch/bytes and resumes from the persisted watermark. Return a terminal receipt only after all decisions commit.
4. **Assess.** Worker leases dirty site/domain/window jobs, selects accepted evidence by source time plus interval overlap at a declared knowledge cutoff, resolves the exact public configuration, builds `AnalyticInputSet`, and runs the versioned pure analytic. In one commit insert `AnalyticRun`, immutable assessment/finding/consequence revisions when basis changed, update projections and mark job done. Retry of same input hash is a no-op. Late or out-of-order evidence recomputes the affected and neighboring continuity window; it never mutates old revisions. Model deployment schedules explicit re-evaluation of supported windows.
5. **Verify.** ActionEvent records work. After a later closed window exists, evaluate the frozen plan against accepted evidence, target and each guardrail. Missing coverage is `INCONCLUSIVE`; worsening service prevents `VERIFIED` even if cost falls. Link outcome to exact analytic run/evidence and surface any later superseding outcome.

**Initial API contract:** `POST /api/ingestion/batches` returns terminal `200` receipt or `202 IN_PROGRESS` receipt; `GET /api/ingestion/batches/{id}` returns the same durable state. `409` is reserved for same batch ID/different bytes or registered identity conflict, `422` for malformed contract, `401/403` for authentication/authorization. Normal reads use `GET /api/sites/{id}/evidence`, `/evidence/records/{id}`, `/overview`, `/performance/{view}`, `/findings/{id}` with `from`, `to` and optional `revision_id`; list reads paginate by stable `(source_time,id)` or `(created_at,id)` cursor. All responses include scope/window, revision IDs, evidence coverage and projection watermark. The UI treats a lagging projection as pending, not healthy. Lab Commit calls this same HTTP boundary with a registered simulated gateway; no privileged product-write endpoint exists.

**Demo-to-Postgres cutover:** create Tenant/Site/Gateway/Source registrations from existing Site records, import immutable Foundation and mapping versions, then replay sealed committed batch bytes through the new ingestion service using the legacy parsers. Preserve original batch/message IDs, envelope text, source times and mode; assign new database UUIDs only to internal rows. Compare accepted/rejected/conflict counts and representative evidence/dispatch claims against the file-backed baseline. Keep `var/sites`, Lab runs, stages and committed artifacts untouched and read-only during verification. Switch product reads to Postgres only after the comparison passes; new Lab Commit posts the V2 batch/receipt path. Do not import private world trajectories into the product database. An existing batch whose required public configuration cannot be registered is reported as a migration exception, never guessed into a new Foundation version.

**Acceptance checks for the first slices:** power loss after SQLite enqueue and after server commit; duplicate batch with identical bytes; same ID with different bytes; partial batch crash/retry; reordered and late samples; two same-timestamp samples with different sequences; mapping/Foundation version change during offline period; wrong gateway/site credential; one rejected sibling among valid samples; simulated and captured physical fixture with equivalent envelopes producing identical assessment/consequence/read model aside from provenance. Test lineage by opening a visible claim and resolving every evidence and assumption ID, rather than asserting only rendered text.

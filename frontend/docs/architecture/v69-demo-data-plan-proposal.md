# Proposed demo-data dependency for screen fidelity

**Architect planning proposal.** This is a fixture contract for later Planner packets, not a seed implementation or permission to claim the mock's illustrative events occurred. The S1-S7 spine starts with one Kobo Site and one assessed window. Multi-site, multi-window, cold-chain, EV and Portfolio screens require their own source-to-claim fixtures through normal ingestion.

| Gate | Minimum fixture set | Required proof | Blocks |
| --- | --- | --- | --- |
| Registered Lab and edge delivery (S2) | Imported Kobo Postgres Foundation/binding snapshot, simulated report only, gateway outage/queue growth/disk pressure and a central diagnostic report | S2-01a run records registered basis; S2-01b sealed V3 identity and canonical Batch V2 bytes survive restart; S2-01c proves local faults; S2-02 records authenticated TLS receipt, digest and central diagnostic receive time. No batch signature or physical protocol equivalence is claimed. | Lab Commit, Site Evidence provenance and later source-health claims |
| S3/S4 first claim | Kobo Foundation/binding revisions, one complete and one missing/contradictory dispatch interval, late accepted sample, one price assumption revision | Stable IDs; old/new assessment and Finding/consequence revisions; exact accepted envelope set; Unknown when role/quality absent | Dispatch/Finding/Financials screen claims |
| Mini-grid breadth | Distinct comparable service, renewable opportunity, fuel-balance and backup windows; separately attested load request/fuel delivery/backup test where needed | Domain rules and human/device provenance; repeated opportunity is not inferred from one hour; service demand is not delivered power | Service/Renewable/Fuel/Backup/Opportunity screens |
| Action verification | Kobo baseline run under old effective policy, applied-change event, separate later run under new persisted policy, guardrail-fail and insufficient-evidence variants | Fixed plan revision predates evaluation; activity and outcome remain distinct; both windows resolve evidence; no mid-run kernel policy switch is assumed | Verification and completed-action mock state |
| Cold-chain Site | One Site Foundation/role set, simulated and captured physical adapter report, excursion/backup disturbance and missing sensor variant | Same ingestion contract, domain-specific temperature/backup assessment, incident/work links only after their architecture gate | Cold-chain Overview/Performance/Findings/Work |
| EV Site | One Site Foundation/role set, session/connector/energy records, interrupted and missing-session variants | Same ingestion contract, session service and availability rules, no invented revenue | EV Overview/Performance/Findings/Work |
| Estate comparison | At least one supported Site in each included domain with aligned declared windows, currency/price basis, coverage, source mode and consequence overlap groups | Deterministic cross-site indexes and Portfolio roll-up; unlike money/periods remain separate; no verified recovered amount from Action completion | Portfolio/global Financials and comparable root claims |

Each fixture manifest should name Site code and UUID, tenant, source mode, gateway/source identities, Foundation/binding versions, source-time interval, batch bytes/digest, expected dispositions, analytic/formula versions, assumption revisions, expected claim ceiling and screen IDs. Seed twice without duplication; reload every read; leave private Lab truth outside product storage. **Source in effect for S2–S7 is simulated input.** At the first real pilot, choose a real-device capture if available or a labelled synthetic wire fixture from vendor protocol documentation, then prove protocol frames, scaling, units and device clocks before claiming physical-adapter equivalence.

Fixture source ownership is explicit: S2-01c produces outage/retry/disk-pressure cases, S3-01 produces the complete/missing/contradictory/late mini-grid reports, and S6-02 produces two-run later-policy and guardrail variants. S7-01 produces/reloads central gateway-health cases; battery stress remains Unknown unless a causal simulator observation exists. `I-sim-battery-cases` is a follow-on producer rather than assumed S7 data, and captured battery replay is not an S2-demo fallback. Cold-chain and EV waves each need a new simulated world/device model and a captured physical-adapter peer, as well as role sets and multi-Site windows. All product records still enter through the shared gateway/ingestion path. Gateway diagnostic records are operational health input and must not be counted as AcceptedEvidence.

The Planner must make each gate an explicit dependency of its corresponding follow-on packet. Global/root visual polish may start earlier, but the named product claim cannot be accepted without the matching fixture and lineage demonstration.

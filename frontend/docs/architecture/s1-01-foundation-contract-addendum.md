# S1-01 Foundation contract addendum

**Architect decision · 2026-10-07.** This narrows the accepted [architecture](production-shaped-mvp.md) and [technical design](production-shaped-mvp-technical-design.md) for the first Site slice. It is a contract for the Planner's S1-01 packet, not a claim that the target storage or gateway exists yet. The three Site-first documents are current implementation authority in project routing; their original “proposal” headers do not by themselves record owner sign-off. The decision record must distinguish this Architect resolution from owner slice acceptance.

## Runtime and database

- Use PostgreSQL 16 in a pinned local Docker Compose service. Add `psycopg` 3, SQLAlchemy Core and Alembic to the backend. Versioned Alembic migrations own DDL; application startup never creates tables. `DATABASE_URL` is required for the product Postgres path, with a documented local default only in the development Compose configuration. No database credential is committed. A separate disposable test database on that service runs migrations from zero and is never the developer database. Tests use PostgreSQL, not SQLite as a stand-in.
- The first migration enables `btree_gist` and installs the technical design's exclusion constraint for nonoverlapping currently recorded Foundation valid ranges. Use a Site row lock while publishing; the database constraint remains the final concurrent-write guard. The migration fails clearly if the configured database role cannot create the extension. Do not silently fall back to an application-only overlap check.
- S1-01 may publish Foundation before a binding set exists. This is an explicitly incomplete configuration state. S1-02 adds the first atomic Foundation-plus-binding snapshot; from then on a mapping-affecting publish follows the technical design's joint-publication rule. No gateway can upload S1-only evidence.

## Import identity and content

- Import `var/sites/kobo-001.yaml` explicitly into one configured development tenant (slug `demo`), preserving `site_id: KOBO-001` as `site.site_code`, `Kobo mini-grid` as name, `MINIGRID`, `Africa/Addis_Ababa`, `PLANNED`, and the fixture's original `foundation.valid_from` and v1 values. UUIDs identify database rows internally. Product URLs and existing API route `{id}` use the stable site code within the authenticated tenant; responses also expose the UUID. The mock's MG-DEMO-01, Africa/Nairobi and v4 are layout examples, not import values. Re-import with the same code and fixture digest is idempotent; a different digest/code collision is an explicit conflict, not an overwrite.
- This is a **declared migration of the existing YAML record**, so the source file with the same normalized code is the expected input, not a duplicate to reject. Record its canonical document digest and source path with the import registration. At initial import, reject any *different* YAML record, tenant or Postgres Site using that normalized code; a rerun against the registered same file/digest and same tenant returns the existing UUIDs and revision. If the source YAML subsequently changes, stop with a migration conflict and require an explicit reconciliation; never silently re-import it or let it shadow the Postgres Site. Keep its bytes untouched for comparison. Code comparison remains case-insensitive as in the current Site repository.
- Register all ten fixture `foundation.components` as assets: PV array, inverter, battery, PCS, generator, fuel tank, AC bus, and the three loads. `component_id` becomes `asset_code`; preserve type, name, rating and properties in asset attributes and in the immutable Foundation content. The AC bus and loads are physical topology/work anchors, even if they never get their own analysis in S1. Devices are acquisition endpoints, not extra assets; their `component_id` links to those assets. No synthetic controller asset is invented.
- `foundation_revision.content` holds summary, components with typed ratings/properties, topology nodes/connections, device inventory with declared signals, control assumptions and site controls. Keep the source document's values and provenance. Reserve is the battery's `reserve-state-of-charge` property (30%); source and critical-load priority are typed site controls. The `signal_mappings` array is legacy import input and comparison evidence, **not** an active `signal_binding_revision` and not a gateway-downloadable mapping. S1-02 converts it with explicit canonical role, units and conversion decisions. Until then Foundation reports bindings incomplete. Do not infer a role from a mapping label or treat legacy mappings as accepted evidence authorization.
- The YAML `source.mode: SIMULATED` authorizes only a proposed provenance for import. S1-01 explicitly registers one disabled/pending simulated gateway `edge-kobo-001` and one source per fixture device, with `source_external_id = device_id`. A source is the stable owner of **one device report stream beneath a gateway**, not the gateway aggregate; all signals on that device share its `(gateway, source, epoch)` sequence scope. A replacement physical device or a move to another gateway gets a new source identity. The gateway's `credential_ref` points to a provisioned secret or remains null/pending until S2; it is never a placeholder accepted for ingestion. S1-02 may add the Site controller channel as a separately registered source only if needed and justified. The gateway and sources are registration metadata in S1, not a running edge process.

## Tenant, cutover and read honesty

- Before product authentication exists, backend configuration resolves one fixed development tenant, `demo`, at the request boundary. A client-supplied tenant ID/header/query is not authority. All repositories require the resolved tenant UUID and apply it to lookup and mutation; tests cover same-code sites in two tenants and cross-tenant UUID references. A later authentication task replaces only tenant resolution, not repository scope. Gateway credentials in S2 bind tenant/site/gateway/source separately.
- S1-01 is a **Foundation-only cutover** for explicitly imported product Sites. Today `main.create_app` injects one `CompositeSiteRepository` into product Site routes, evidence/analytics and Lab; it cannot simply be left in place as the product read authority for an imported code. At composition, introduce an explicit tenant-scoped cutover registry/read router: for a registered imported code, `GET /sites` and `GET /sites/{id}` return the Postgres identity and selected current Foundation summary; list it **once**, suppressing its matching YAML row. For every unregistered code, continue the existing YAML product listing/detail so the other current Sites do not disappear. A code collision without the registered same-source import digest is an error, not an arbitrary store precedence. The Foundation version list/detail and publish routes for an imported code read/write Postgres only. For an unimported code they return an explicit migration-required response, not a fabricated Postgres version. The product router must preserve tenant scope and existing route code identity.
- Existing file-backed Overview, Evidence and dispatch are legacy comparison surfaces. For an imported code, their product reads and legacy writes/Commit path must show a clear “awaiting evidence migration” state or refuse with a specific transition code, rather than render or mutate YAML/JSON state beside a newer Foundation revision. The configured SLD portion may read selected Postgres Foundation, with no operational status. S2-02 switches Evidence after comparison; S3 and S5 respectively replace dispatch/Performance and Overview reads. Unimported codes retain their current legacy behavior until separately cut over, labelled as legacy where the distinction is visible.
- Lab Site creation currently writes through the same YAML Site repository, and run setup reads that same repository. Keep the imported Kobo YAML document read-only for comparison and historical Lab/run inspection; do not call it a separate namespace. Refuse new Lab Site creation with an imported code, and from the moment that code is registered in Postgres refuse **new Draft setup, start, step, run-to-end and Commit for existing Drafts** against it until Lab can use a registered Foundation and gateway snapshot. Stage envelopes are generated by execution; those controls cannot generate more after import. The current `GET /runs/{run_id}/stage` is read-only and may remain available for historical inspection, visibly labelled with its frozen YAML basis and unable to release or seal anything. Commit is the sealing/release path and is blocked regardless of whether the stage was produced before import. This unconditional gate is simpler and safer than comparing only current reserve values: version and binding authority are already split at initial import. Apply it at the shared service/composition boundary, not only by hiding a button. No file-backed writer may mutate an imported Site.
- Foundation reads resolve `at` (valid time) and optional `knowledge_at` (recorded time) on the server. Default both to server now, while returning the resolved instants and revision ID. The S1 UI selects among persisted Foundation periods using a version-list API and carries the selected `at` instant in the URL query so reload/share preserves the view. `knowledge_at` is API-only for S1 audit; the reviewer exercises it by API. A selected historical view is visibly labelled with its effective period. Empty/invalid periods return explicit not-found/validation states, never current data silently.

## Required Foundation gaps

For `MINIGRID` in S1, report missing/invalid Site code, name, site type or timezone; no effective Foundation revision; missing typed component/rating for generator, PV array, battery, battery PCS, fuel tank, AC bus, or declared load; broken topology references or no path to the AC bus; missing battery reserve, source priority or critical-load priority; no registered gateway/source for a declared device. These are **configuration** gaps, not observed source health or analytic readiness. The incomplete signal role/binding state is reported as pending S1-02 separately. Validate no component, control or topology member refers outside this Site. An intentionally incomplete Site can persist but cannot download an acquisition snapshot or claim operational health. For the missing-gap demonstration, remove the battery's `reserve-state-of-charge` property from a separate import fixture (leaving the other battery properties and controls valid); the legacy parser permits an absent property. Do not damage `var/sites/kobo-001.yaml` or omit a member from `critical-load-priority`, which the legacy parser rightly refuses as an invalid priority ordering. Import uses the existing strict Site document parser to validate the source snapshot, then adds Postgres/domain completeness checks; the latter may accept an incomplete-but-well-formed Site and report gaps.

## Planner handoff and deferred screens

The Planner should specify a one-shot import command for the existing fixture, a narrow publish API and one Foundation control to change **only battery reserve SOC** in S1-01. Validate its unit and value against the existing typed property rule, publish a new effective revision and preserve old validity/recorded-time reads. `source-priority` and `critical-load-priority` stay read-only this slice; reordering them would need separate invariants and an honest Lab execution contract. The mock's 35% generator start and 90% stop settings are not in the Kobo fixture and must be omitted or marked unconfigured, never imported from the mock. The fixture **does** declare `minimum-runtime: 30 min` on the generator; it may be shown as a declared property, not an observed runtime or editable S1 control. Do not build the mock's full Site-creation form, template choice, batch upload or setup history in S1-01: plan these later as named deferred surfaces. A version list and historical selection are required now even though the static Foundation mock only shows a version badge. Put the fixture-to-Postgres comparison (identity, ten assets, topology, controls, version/time and omitted binding authority) in the S1-01 review packet or a checked-in fixture report, with command and digest. The Planner should update the configuration-persistence guard for the split: Postgres is the sole writer for imported product Sites, while the existing YAML adapter remains the legacy writer for unimported Sites/Lab until migration; neither may write an imported YAML file. Retain storage-import bans above adapters and non-vacuity. The gateway/source identity rule and Foundation-only cutover must be carried into S1-02 and S2 packets. S3-S7 mock tabs beyond each task's named persisted slice remain planned outlines, with renewable/service/fuel/backup Performance views and global Site Findings list explicitly scheduled or deferred during refinement.

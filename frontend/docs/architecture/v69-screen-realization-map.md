## Reading the ledger

`bounded` means the named S task plans a **portion** of that screen backed by its stated objects; it does not promise every example card, interaction or pixel. `partial` means only a cross-cutting shell/list or one subsection is covered. `deferred` means no S1-S7 product claim is authorized. `task` points to the current packet; `follow_on` is a planning lane, not an executable task. Each `visual_reference` is the mock's `#/id` state. `product_destination` is the intended navigation owner, not a promised React route; only task packets may fix URL contracts. The manifest remains the source for named read models, reference text and mock-specific preserved/adapted/deferred notes.

**Proposed fidelity tiers, pending owner approval:** `Real` means the screen's supported claims, navigation, interactions and panels have passed a source-to-screen review; `Real with honest gaps` means its named usable portion is real and missing/unsupported panels or claims are visibly withheld; `Deferred` means no implementation commitment yet; `Dropped` means an owner-approved removal from the intended product. The current proposal assigns 21 screens `Real with honest gaps` and 89 `Deferred`; none is yet `Real` or `Dropped`. These are planning tiers, not implementation status or owner acceptance. The owner may change any tier before the Planner uses it as a completion target.

Each ledger row now has `promotion_dependencies`. For a **Deferred** screen, `to_candidate` names the model decisions, shared projection contracts, fixture/record proof and task gate that must be met before the Planner can propose it as an executable slice. For a proposed **Real with honest gaps** screen, `to_candidate: null` means an S task already names its bounded portion, not that it is built; `to_real` names its unresolved mock panels and further work before full fidelity can be claimed. Deferred screens also carry a `to_real` panel/acceptance gate for use after candidacy. The model names resolve to exact decision requests in [model homes](v69-model-homes.json), and panel names resolve to [panel contracts](v69-panel-contracts.json). A tier change must update these dependencies and pass the validator; no status advances merely because a future task title exists.

## Architecture decisions required before follow-on packets

These are **decision requests for future Architect passes**, not proposed table definitions. A shared name in the mock manifest does not make two lifecycle objects equivalent.

| Gate | Named models and screens | Existing substrate that may be reused | Decision that must precede implementation |
| --- | --- | --- | --- |
| Work case identity | `Incident`, `IncidentIndex`, `MaintenanceWorkRequest`, `MaintenanceRecord`, `MaintenancePlan`, `WorkEvent`, `MaintenanceIndex`; incident, maintenance and Site Work screens | `Action`/`ActionEvent` may link to work; `VerificationPlanRevision` and accepted evidence may verify outcomes. | Define incident case versus work request versus performed maintenance, each identity/status/event owner, Site/Asset linkage, chronology and close/reopen rules. Do **not** store an Incident or MaintenanceWorkRequest as an Action merely to fill the screen. Indexes follow these entities. |
| Asset registration and cover | `AssetRegistration`, `WarrantyRecord`; asset register/config/edit/warranty screens | Existing `asset` row and binding revisions anchor an asset. | Define audited registration edits, replacement/retirement, warranty terms, vendor identity, effective coverage, claims and valuation limits. `AssetRegistration` can be a workflow over `asset`; warranty cannot be inferred from an asset rating. |
| Human operational inputs | `OperationalRecord`, `FuelBalanceWindow`, `ServiceWindow`, `LoadRequestEvidence`, `BackupEventChain`; fuel/service/backup and operational-record screens | Accepted device evidence and asset/source IDs provide one side of reconciliation. | Define attested fuel deliveries and load requests, author/time/provenance, reconciliation windows and confidence; define service deficit and backup event rules. A delivered-power reading is not demand and a generator run is not a witnessed backup test. |
| Renewable opportunity | `RenewableOpportunityWindow`; renewable and opportunity Finding screens | Accepted PV/load evidence, Finding and consequence revisions can carry supported results. | Define repeat-window eligibility, curtailment/headroom versus unmet demand, opportunity claim ceiling, tariff/price basis and recurrence identity before pricing productive use. |
| Policy and scenarios | `PolicyVersion`, `FinancialScenario`; Settings policies, temperature and financial Scenario screens | Foundation/control and financial assumption revisions can be referenced. | Define whether policy is Site, tenant or domain scoped; version/effective time and authority. Define scenario inputs and `Scenario` basis separately from observed/measured consequence. No mock what-if value becomes an actual outcome. |
| Site onboarding | `SiteDraft`, `SiteTemplate`, `SiteImportBatch`, `SiteSetupEvent`; creation/form/template/batch/history screens | S1 Postgres Site/Foundation, existing strict YAML template parser and import comparison are reusable. | Define draft versus published identity, template provenance and version migration, per-row batch refusal/rollback, audit events and tenant authorization. Existing Lab `POST /sites` does not become the product flow by renaming it. |
| Tenant settings | `TenantConfiguration`; Settings tenant screen | The technical design has `tenant` identity and S1 fixed development tenant resolution. | Define users/roles/auth, editable tenant configuration, policy permissions and audit before exposing settings controls. |
| Cold-chain/EV analytics | `TemperatureExcursion`, `CoolingRecoveryWindow`, `ChargingSession`, `SessionServiceWindow`, `ConnectorAvailabilityWindow`, `ChargingEnergyWindow`, `SitePowerLimit`, plus related context/energy models | Reuse gateway, typed evidence, revisioned assessment, Finding, consequence and verification mechanisms. | Define domain-specific required roles, intervals, quality, episode matching, limits and causal alternatives before the corresponding screens show classifications. |

Shared read models also need explicit **projection contracts** when their first real consumer lands. `CapabilityReadiness` appears on 9 screens, `FindingIndex` on 8, `SourceHealth` on 7, `AssetHealthSummary` on 7 and `MaintenanceIndex` on 7. S1/S2/S4/S7 can establish the first four for a bounded Site use, but that does not make their estate-wide or cross-domain versions automatic. `MaintenanceIndex` waits for the work case decision above. Every projection must name source rows, scope/window, sort and pagination, freshness, missingness and drill-down IDs.

The [technical design's proposed section 5](production-shaped-mvp-technical-design.md) now sketches entity identity, immutable revision/event and lineage rules for each missing family. Those rules are a follow-on proposal, not accepted S1-S7 scope. The [panel contracts](v69-panel-contracts.json) deliberately say `GAP` where a panel-specific model, role or table is not established; a manifest model name alone does not prove an analytic can support the panel.

## Pre-S3 planning gates

Keep S1-01, S1-02, S2-01 and S2-02 on their current path. **Before S3-01 is activated**, the Planner should put three reviewable planning artifacts in the queue: (1) owner review of the proposed screen fidelity tiers, including any `Dropped` decision; (2) an Architect decision/refinement packet for the model gaps and shared projection contracts that S3/S4 actually need, with broader domain gates held for their own follow-ons; and (3) the [V-01 visual fidelity task proposal](v69-visual-fidelity-task-proposal.md). The [demo-data plan](v69-demo-data-plan-proposal.md) is a named dependency: its Kobo first-claim fixture gates S3/S4, its later-window fixture gates S6, and its multi-site/domain fixtures gate cold-chain, EV and estate roots. None may be replaced by copying the mock's illustrative values.

## Screen-outward sequence after S7

1. **Close mini-grid Site gaps after S7.** Resolve service/renewable/fuel/backup role and analytic decisions; seed distinct multi-window fixtures; then activate Site Findings, those Performance views, contextual Finding alternatives/history, and fuller Action detail. Product Site/Asset onboarding follows its own draft/registration decisions. Show only supported capabilities and keep Unknown where required input is absent.
2. **Establish work-domain identities where needed.** Incident, maintenance and operational-record contracts precede their first Site or domain screen. Link their cases and attestations to, but do not collapse them into, Action and accepted device evidence.
3. **Extend the shared path to cold-chain and EV.** Give each domain a Foundation -> Evidence -> assessment -> Finding/consequence -> Work/verification journey and an explicit fixture gate. Cross-domain shell structure and lineage stay shared; claim rules and language remain domain owned.
4. **Add roots and estate comparison.** Build global Sites/Findings/Actions/Assets/Evidence indexes from durable Site records. Portfolio and global Financials wait for the multi-site demo-data gate plus currency, period, coverage and overlap rules. Settings, warranty and scenarios follow their own contracts and owner-approved tiers.
5. **Check fidelity throughout.** For each activated screen, compare the actual rendered state to its `visual_reference` at desktop and narrow widths; exercise navigation, selected time/window, keyboard interaction and reload; verify every visible value from API to persisted source and every link to its exact ID. Capture one complete, one missing and one conflicting/late-evidence state. Record deliberate omissions beside the manifest ID. A screenshot can prove layout, but cannot prove a claim or a usable interaction.

The Planner can turn these lanes into a follow-on queue after the preceding owner/reviewer checkpoints. Until then the only executable work remains S1-01, followed by refinement of each existing S packet at its planned handoff.

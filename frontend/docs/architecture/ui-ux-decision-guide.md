# UI/UX decision guide for builders

Apply this on every screen-affecting slice, including when the card has no UI question. The v6.9 [screen manifest](../../mockups/v69/screen-manifest.json) and named mock screen set the layout and content reference; the active card and rulings set product meaning. Make cheap, local improvements within demo speed. Record the choice and this guide's section in the review packet under **Choices made**. Do not pause for an Architect answer to a choice this guide covers.

This guide draws on [WCAG 2.2 AA](https://www.w3.org/TR/WCAG22/), [Material 3](https://m3.material.io/), [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/), [GOV.UK Design System](https://design-system.service.gov.uk/), [Carbon](https://carbondesignsystem.com/), [NN/g usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) and [NN/g mobile table guidance](https://www.nngroup.com/articles/mobile-tables/). Use the existing app primitives and semantic HTML; these sources guide a choice where the mock and a specific ruling are silent.

## 1. Long values, tables and height caps

- Show the complete stored value by default. Wrap prose and codes with `overflow-wrap: anywhere` where needed; let the containing grid item shrink with `min-width: 0`. For long key/value entries use `KeyValues`' `wide` row in `frontend/src/ui/V69Layout.tsx` when the value needs its own full-width line. Do not silently ellipsize, clamp, drop or conceal a row to meet a cap. Keep exact IDs available in a labelled technical disclosure if the main wording uses a short human label.
- If a table cell must keep a two-line closed preview, show a visible **Show full** button *inside that cell* only when the full value overflows. Give it a row-and-column-specific accessible name and `aria-expanded`; open inline to the unchanged full value, then offer **Show less**. The closed control fits in the existing row height. A title attribute, hover-only popover or truncated value without a disclosure does not suffice. Keep cell links and the button as siblings, never nested controls. This is the [WCAG keyboard/focus](https://www.w3.org/TR/WCAG22/#keyboard-accessible) and progressive-disclosure treatment ruled in `post-W6-W6-caps-rulings.md` §4.
- Keep two-dimensional overflow inside the **table**, never on the page. Use the existing `.data-table__scroll` pattern (`frontend/src/ui/primitives.css`), semantic table headings, a visible phone horizontal-scroll cue and a focusable wrapper. When vertical containment is needed, wrap the entire table, including its header and every row, in one element with `role="region"`, a specific `aria-label` such as `Action history entries`, `tabIndex={0}`, `overflow-y: auto` and a measured `max-height`. Show `Scroll history to see every entry` / `Scroll versions to see every row` only when `scrollHeight > clientHeight`; keep count and status outside the region. Existing ruled examples: Action history 480 px desktop / 500 px at ≤640 px; Fuel cost versions 480 / 900 px; Finding revision history 400 / 1000 px. These are examples, not global caps. Preserve keyboard and touch access on both axes, every row and full value, and zero document horizontal overflow.
- For every named **closed** panel cap, measure at 1440 and 390 px using each producible indexed case and a worst-case stress case: five rows, with **every variable visible text field at 160 characters**. Keep fixed typed values and true row counts; if five rows cannot be produced, probe the largest real shape and explain it. Where producers cannot make the stress case, first capture the unmodified mounted app, then use a labelled capture-only DOM clone of real rows without persistence or mutation. Assert all intended fields were changed; record the fixture, viewport, row and panel heights, clipping, table client/scroll size, and document width. Synthetic layout evidence is never product data.
- Follow the ruled cap for that panel. On a miss, improve wrapping and column width, then supported paging or disclosure, then an obvious labelled and focusable inner scroll region, recapturing each change. User-opened **all-disclosures-open** or **Show all** states are exempt from closed-height caps, but must still be readable, reachable and unclipped. If no cap was ruled, propose `50 × ceil(peak × 1.15 / 50)` px from the worst closed peak and record the calculation in the packet. The builder owns this provisional cap without a separate question. Escalate for Architect ratification only when the result **exceeds a ruled cap** after these fallbacks, with the measured evidence. Never silently raise a ruled cap. See `.ai/ROLE_CONFIG.md` Lesson 15 and the post-W6 caps rulings.

## 2. Phone layout, navigation and controls

- Check 390 px and desktop at the same revision. Reflow page columns and cards; let Site and Work tab rows **wrap with complete labels** (the ruled Work breakpoint is ≤760 px). Avoid a tab scroller and document-level horizontal scrolling. Only genuinely two-dimensional content such as a data table or diagram may scroll horizontally inside its named container. Keep a visible scroll cue and no clipped labels. This follows [WCAG reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html) and the post-W6 W6 tab ruling.
- Make pointer targets at least **24 × 24 CSS px** for [WCAG 2.5.8 AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum). Prefer roughly 44 px touch areas where the layout permits, following Apple HIG. Do not use tiny adjacent text buttons to meet a dense mock. Keep focus indicators visible and unobscured.
- An `<a>`/router `Link` navigates to a real destination; a `<button type="button">` changes the current view, expands content or retries. Unavailable destinations are plain text with an honest state. Do not put a button inside a link or make a whole clickable row contain other interactive controls.

## 3. Loading, empty and refusal states

- Give loading content one `role="status"` per active area and keep its heading or table context. A small skeleton or `Loading {thing}…` is enough; do not show invented values. Empty is also `role="status"`: `No {records} in this period.` Add the next useful action only if the user can actually perform it. Distinguish no records from unavailable, unassessed and denied.
- Give a refusal or failed read one `role="alert"`, plain heading and concise reason. Map known **error codes and proven input causes** to copy, never HTTP status alone; a 422 may mean different corrections. Examples already ruled: `ACTION_FOUNDATION_STALE` → `The site configuration changed before this was applied`; invalid reversed window → `The end must be after the start.` Unknown code → `The attempt was refused.` Do not print raw server messages, stack text or internal codes in the main UI. Exact codes may live in a labelled technical disclosure when the card permits it.
- Offer **Reload** only for a recoverable read failure such as a 503 with a loaded view; do not offer it for denied access, missing resources or invalid input. For invalid input, name the correction and preserve the user's selection. Preserve the screen's ruled refusal structure; do not invent a success state. This applies NN/g visibility of system status and GOV.UK error guidance.

## 4. Words, time, colour and hierarchy

- Use sentence case, plain nouns and verbs, and the unit beside each number: `12 kWh`, `3 minutes`, `2 requests`. Avoid unexplained acronyms and mock-only claims. Use a local plural helper of the existing pattern `count === 1 ? one : many`, including verb agreement; check 0, 1 and 2. Do not create a shared module for one or two nouns.
- On Site-scoped reads, use `frontend/src/sites/siteTime.ts` (`siteTime`, `siteZoneLabel`) for the Site-local time and zone, with the exact stored UTC instant in `title` or a labelled detail disclosure. Keep stored instants and URL/API bounds in UTC. If the Site zone is missing or invalid, label the visible value **`UTC (Site time zone unavailable)`** or use an equivalent explicit suffix; never imply it is Site-local. For an absent value, say `Time not recorded`, not a fabricated instant. Follow a more specific screen ruling where one exists.
- Use existing semantic tokens in `frontend/src/ui/tokens.css` and `frontend/src/ui/primitives.css` for status, text, borders and focus. Fixed labels such as `Lens: Opportunity` are neutral; green, amber and red express an actual stored semantic state only. Pair every colour with a word, symbol or pattern ([WCAG 1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html)). Check UI boundaries, chart marks and focus indicators at **3:1 non-text contrast** against adjacent colours; check ordinary text at **4.5:1** unless a WCAG exception applies. Check the rendered colour against its real background, including chart tracks, not just the token value.
- Keep one page `h1`, ordered headings for the mock's panels, a main landmark, named navigation and correctly associated table headers. Use `V69Layout.tsx` primitives (`MetricCards`, `KeyValues`, `V69Notice`) where they match the mock. Make keyboard focus follow reading order, keep visible `:focus-visible` styling, and make disclosures announce state with `aria-expanded`. Avoid redundant nested live regions.

## 5. Mock deviations and decision ownership

- Preserve the v6.9 panel, row, column and chart form. For a changed layout or content choice, first check `.agent/mock-departure-register.md` and the active ruling. An unavoidable missing data or feature gap is **D1**; a proposed improvement to organisation, precision or clarity is **D2**. Label the affected view visibly and adjacent to the change as `MOCK DEVIATION D1 (Rnnn)` or `MOCK DEVIATION D2 (Rnnn)`, and register the screen, mock element, shown alternative, reason, owning unit and owner status. Use the slice's assigned register range; never reuse or self-allocate outside it. Small D1/D2 choices may be made by the builder within that range and listed in the packet. D2 remains an owner proposal until accepted. A missed mock element is D3 to correct, not a D2; illustrative false mock copy follows the register's D4 rule.
- **Builder decides and records** guide-covered choices and clear local extensions: spacing, responsive wrap, semantic token, disclosure or scroll treatment, small copy with unchanged product meaning, loading/empty/error presentation, and focused test approach. In **Choices made**, cite the guide section, the relevant mock element/ruling, and the proof at 1440/390 where applicable. An ordinary covered choice needs no Architect request, even during pre-flight.
- **Escalate only** a change to product meaning or claims; backend/API/schema contracts; scope or ownership across cards; guards or test policy; a cap that still exceeds a ruled cap after the fallbacks above; a significant owner-facing D2 layout change; or a conflict with an existing ruling. Send the smallest concrete option, affected mock element, alternatives and measurement. Continue independent covered work while the decision is made.

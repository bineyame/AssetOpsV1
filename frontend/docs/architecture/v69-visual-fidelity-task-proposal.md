# Proposed V-01 - v6.9 visual and interaction fidelity track

**Planning proposal, not executable or owner accepted.** The Planner should add a small visual-fidelity packet **before S3-01 activation**, after S1/S2 evidence-path review. This track then becomes a check within every later screen slice. It must not delay S1-01, S1-02, S2-01a/b/c or S2-02 or turn static mock values into product facts. The [tiered screen ledger](v69-screen-ledger.json) is pending owner approval.

## Outcome

The real app's supported Kobo Foundation/Evidence/Dispatch path uses a coherent v6.9 layout and interaction vocabulary: rail, Site header, tab/subtab row, date/window control, status/coverage badges, panels, tables, evidence drawer and missing-state panels. Unsupported root/tab destinations are absent or clearly unavailable under the project's presentation-honesty rule. The UI keeps selected Site/window/revision in links and reloads. A reviewer can compare the same supported state at desktop and narrow viewport against the [mock route](../../mockups/v69/index.html) and its reference image, while tracing every displayed claim to a read API.

## Implementation boundary

- Inventory the mock's CSS variables and recurring components in `mockups/v69/mockups.css`, `portfolio.css`, `index.html` and preview PNGs. Map them to existing `frontend/src/ui/tokens.css` and UI primitives; change tokens/components once instead of restyling every Site panel separately. Record intentional differences where the real app's accessibility, responsiveness or supported data requires them. The current tokens derive from earlier `ScreenMockups.png`, so visual equivalence to v6.9 is not assumed.
- Define one root/tab/subtab inventory for actual capabilities. Site/Findings/Actions ownership follows the technical design: Site lists are scoped projections; detail changes root to stable Finding or Action identity. Hide unsupported tabs and roots until there is a truthful destination. Preserve supported direct links and keyboard focus; empty/Unknown is an in-page state for a real capability, not a placeholder route.
- For each activated manifest ID, exercise three fixture states: supported populated, missing evidence/configuration, and conflicting or late evidence where relevant. Check displayed units, dates/timezone, version/coverage labels, links and action affordances against the same read model. A screenshot is visual evidence only; API/lineage checks remain required.
- Capture the mock and app at matching viewport sizes, compare panel order, spacing, typography, color tokens, table density, responsive behavior and focus/hover states. Document intentional differences by screen ID. `frontend/mockups/v69/review-browser.mjs` currently tests the **mock itself** and can seed navigation/overflow/interaction expectations. `frontend/mockups/v69/render-reference.ps1` renders a PDF page to an image, not a live React comparison; use it only for PDF reference pages. A new or adapted app browser review must perform the app side of the comparison. Do not report those existing scripts as proof of real-app fidelity.

## Acceptance and handoff

The first V-01 review covers supported S1/S2 `sites`, `foundation`, `readiness`, `sld`, `evidence`, `evidence-analysis` and `lab` states. `dispatch` joins only when S3-01 switches its Postgres read. Store a route/viewport/state comparison with screenshots and explicit omissions; run frontend checks and the screen-ledger validator. The Reviewer traces one displayed evidence value through the API to its accepted envelope and checks a missing state. S3-S7 packets add their manifest IDs as each slice lands. The owner approves proposed fidelity tiers before any screen is marked `Real`, `Dropped` or accepted as a full mock match.

# Site-first execution plan

**Planner handoff · 2026-10-06.** The accepted [system architecture](production-shaped-mvp.md) and [platform technical design](production-shaped-mvp-technical-design.md) are frozen inputs. This plan sequences implementation; it does not amend those decisions or revive the old T0xx queue. The seven rows are **product milestones**, each possibly split by the Planner into a few small tasks. A milestone closes only when its named Site mock surface shows real persisted data and the cited evidence can be opened.

## Site product spine

```text
Site Foundation
  → accepted Site Evidence
  → Site Performance / Dispatch
  → Site Finding + Financials
  → Site Overview
  → Site Work / Action / Verification
  → Site Health

simulated or physical report → edge SQLite → SourceEnvelope → shared ingestion
→ Postgres accepted evidence → typed analytic input → revisioned claim
→ Site read model → screen
```

Start with **one mini-grid Site and one assessed window**. Use the existing causal simulator as the main producer and a captured real-device adapter fixture as a contract peer. Retain the static v6.9 mock screens as interaction/content references; a slice implements the supported portion with honest missing states, not a full static screen filled with invented data. Existing JSON/YAML data stays available for migration comparison, but new product writes use the target stores. The Site shell can keep its current routes and reusable components where they help.

## Shared implementation rules

- **Immediate demo scope versus target design:** S1–S2 need crash-safe SQLite enqueue, stable identities, authenticated batch ingestion, durable per-record decisions and Postgres Site/evidence storage. Build the minimal diagnostics needed to inspect delivery. Detailed queue retention policy, elaborate backpressure controls, multi-protocol drivers, broker transport, full bitemporal editing UI and generic streaming infrastructure can follow when pilots require them. Database/wire schemas should leave room without falsely claiming those behaviors are shipped.
- **Typed analytic boundary:** `EvidenceQuery` returns typed normalized readings/records with quality, time, asset/role, configuration basis and accepted-evidence IDs. The dispatch analytic consumes this plus a typed public configuration view. SQL rows, `jsonb`, canonical envelope text, Lab world records and source adapters stop at repository/normalization boundaries. Contract tests compare simulated and captured real inputs after this boundary.
- **Episode identity:** decide continuity tolerance, episode anchor and recurrence linkage in S3/S4 domain design, with a short decision table before coding the first Finding. `Finding.id` names a durable operational episode; `FindingRevision` describes reassessment of that episode. A new separated episode is a new Finding, linked as recurrence if relevant. Do not use a changing model output hash as Finding identity.
- **Domain algorithms:** dispatch thresholds, cold-chain excursion detection and EV session logic are domain-design work. The platform plan requires their inputs, revision/lineage outputs and claim limits, not more universal framework or algorithm prose. S1–S7 cover one mini-grid Site; later domains add role sets and analytics through the same seam.
- **Verification gates:** each slice exercises the screen at its selected window, the read API, storage/reload, a missing/contradictory evidence case, and lineage back to an accepted SourceEnvelope. S2 adds loss/retry/duplicate/conflict; S3–S4 add late evidence and revision preservation; S6 adds guardrail failure. Tests should assert behavior, not mock labels.

## Handoff beyond Site

After S4, a **Findings index** can already list real Finding objects, but build the global root only when the Site detail and lifecycle are useful. After S6, **Actions** and **Sites** become filtering/indexing over durable Site/Action summaries; **Portfolio** aggregates comparable consequences and priorities with currency/window/coverage boundaries; **Evidence** aggregates Site capability/readiness; **Assets** indexes Site Asset/Health/work records after S7. These are later product roots, not prerequisites or empty screens for the Site spine. Cold-chain and EV are later Site-domain passes using the same ingestion, revision, work and shell contracts; neither should be built by copying mini-grid screens with different labels.

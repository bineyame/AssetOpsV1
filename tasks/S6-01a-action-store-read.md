## Creation, authority and state (L1, P1, P2, P7)

Use L1 model (a): a versioned server recommendation is PROPOSED for a reviewed FindingRevision; an Action is created **on acceptance**, so Action has no PROPOSED state. Recommendation key is `(tenant_id,site_id,finding_revision_id,foundation_revision_id,rule_id,rule_version,asset_id)`; server acceptance key is a canonical digest of that tuple plus `ACCEPT`, unique within tenant/Site. The pinned FoundationRevision ID is also in the acceptance payload digest. Identical accept returns the same Action/event; same key with altered payload is 409. Allocate `action_code` with a tenant-scoped DB sequence and preserve `UNIQUE(tenant_id,action_code)`. Distinct revision/Foundation basis/rule/asset keys permit several Actions per Finding. Each event has `UNIQUE(action_id,idempotency_key)` and payload digest; identical retry returns the original event, conflicting reuse is 409.

Rule `reserve-trial-1` is a server-computed policy-sensitivity trial. Require a reviewed, `SUPPORTED`, current `GENERATOR_SUPPORT_CANDIDATE` FindingRevision. Its pinned assessment must cite at least one Candidate segment whose **accepted analytic input** contains a usable numeric battery-SOC reading strictly greater than that segment's pinned effective reserve plus the dispatch model's 10-point headroom. Read the numeric SOC, segment/assessment/evidence IDs and digest from that persisted accepted analytic input, not Finding prose, a mock number or private Lab truth. Its cited Foundation must have one unambiguous percent battery reserve on the same battery asset, and the current Site Foundation reserve must equal that pinned reserve. For reserve `r` in [15, 90], propose exactly `r - 5` percentage points in [10, 85]. Serve a typed unavailable reason for non-current or unsupported revision, absent Candidate, missing/conflicting/non-numeric SOC, SOC at or below `r + 10`, missing/conflicting reserve or unit, asset mismatch, stale Foundation basis, reserve outside [15, 90], or unchanged result. Pin all input IDs/digest, rule/version, old/proposed values and limitation. Boundary tests cover SOC exactly `r + 10` versus just above, reserves 15/90 and just outside, missing/conflicting inputs, asset and current-basis mismatches. This experiment does not diagnose the Finding cause or predict runtime, saving or safety; never derive it from the mock generator-stop narrative. An S4 money consequence is shown only for its exact basis, labelled consequence.

Before acceptance, recommendation proposal or unavailability is **served from persisted inputs**, with no recommendation row. On acceptance, store an immutable accepted-recommendation snapshot on `action` or an append-only Action-owned child: canonical key, rule ID/version, assessment/evidence IDs and digest, pinned FoundationRevision ID, asset, exact reserve field, percent unit, old/proposed numeric values and stable limitation text/code. After an Action exists for the key, `GET recommendation` returns this accepted snapshot and Action link even if the current reserve has changed; a separately labelled live recomputation status may then be stale/unavailable. The accepted proposal never disappears or changes on reload.

The exact SOC source is the accepted analytic input role `battery_soc` in percent, with `SOC_HEADROOM_POINTS = 10` (`backend/assetops_backend/analytics/dispatch_v3.py:44,53,166-194,255-259,287-300`); carry its selected reading/evidence IDs through the pinned assessment and Candidate segment.

| Command | Precondition | Event / reduced state | Refusal |
| --- | --- | --- | --- |
| accept | reviewed persisted revision; valid recommendation; scoped server-authorized SYSTEM demo capability | ACCEPTED / application pending | missing auth 401, denied authority 403, unknown/wrong-Site Finding or revision 404, invalid proposal typed 422; no Action/event |
| apply | ACCEPTED; expected current Foundation ID; same Site/asset/value; prospective effective time; scoped capability | APPLIED only with committed new Foundation; outcome pending | authorized same-Site domain/publish failure appends FAILED after rollback: stale 409, invalid/no-change/backdate 422; unknown/wrong-Site Action/change 404, missing auth 401, denied authority 403 append nothing |
| apply on APPLIED Action with a new key | already APPLIED | no event or new publish | typed `ACTION_ALREADY_APPLIED` 409; no FAILED because publish was not attempted |
| retry after FAILED | application remains ACCEPTED/pending | old identical key returns its FAILED event; a fresh attempt uses a new key and can become APPLIED | conflicting reuse 409 |
| repeat successful command | identical command key and payload | return original Action/event/artifact before no-change validation | same key, different payload 409 |
| observe demo note | ACCEPTED exists; scoped SYSTEM capability; fixed `DEMO_REVIEW_NOTE` code | append state-neutral OBSERVED; application and verification state unchanged | missing/denied authority 401/403, unknown/wrong-Site Action 404, time bounds typed 422, conflicting key 409; no event on refusal |

FAILED is an attempt event and never claims an effective change. Reduce by `(recorded_at,id)`. Accept/apply use server time. `OBSERVED` alone may carry an explicit earlier `occurred_at`, displayed separately; it never reorders state. Do not infer Verified or human approval. With no verified operator principal, only labelled server-authorized SYSTEM demonstration commands run, carrying stable service principal and triggering job/command/fixture. No client, gateway or OS name becomes a human author.

## New storage and publish (P3-P5, P10)

New migration under `backend/migrations/versions/`: `action` has tenant/Site, immutable origin finding/revision, primary assessment, evidence/configuration basis IDs/digest, accepted-recommendation snapshot (or append-only Action-owned child), action_code, created time and acceptance key. `action_event` has ID, tenant/Site/Action, kind, occurred/recorded time, actor_kind/id, source_channel, authorization_basis, triggering service/job/command/fixture, payload digest, idempotency key and typed failure code. New append-only `action_policy_change` has Action, authorized command and APPLIED event, asset/field/unit, old/new value, expected/superseded/new PUBLISH Foundation IDs, optional SPLIT ID, **every** superseded/inserted binding-set revision ID, effective/recorded time and validity. Use append-only child rows for written IDs if arrays cannot prove same-Site FKs. Same-Site composite FKs and uniqueness; no simulator private truth. These tables/columns are **new**. S6-01a branches from main's migration head. LR-01's `0014_source_clock_attestation` and `0015_finding_returning_basis` are unmerged and held for the owner; if LR-01 merges first, re-chain the S6-01a migration onto main's resulting head and run slice review and the full suite on that re-chained revision.

`backend/assetops_backend/actions/adapters/postgres_action_store.py` (**new**) is the sole runtime SQL writer for `action`, `action_event`, `action_policy_change` and any Action-owned append-only snapshot/ID children. Acceptance inserts Action and ACCEPTED there without a Foundation publish. For apply, this adapter opens the outer transaction, locks the same-Site Action row first, checks idempotency and authority, then calls a narrow caller-owned-connection form of S1 `publish_configuration`. That form uses the supplied connection without opening or committing another transaction; it locks Site `FOR UPDATE` next, checks the expected current covering Foundation ID under the lock, writes Foundation/SPLIT/binding rows, and returns **every** written and superseded ID. Its Action-adapter callback then inserts the change artifact and APPLIED event on that same connection, after S1 writes and before the Action adapter's sole commit. No Action SQL goes through the Foundation adapter. Keep the existing S1 entrypoint's own transaction when no connection is supplied. Any exception rolls back Foundation, bindings, artifact and APPLIED together. For an authorized same-Site failure, append FAILED with expected/current IDs in a separate transaction after rollback; no effective new ID. Stale basis is typed `ACTION_FOUNDATION_STALE` 409. Action effective time must be >= server recorded time and > ACCEPTED time; ordinary S1 historical publication is unaffected. Identical applied retry returns its committed artifact before `FOUNDATION_NO_CHANGE`; a new no-change command is typed 422 with FAILED. Prove Action-before-Site lock order, rollback and concurrent applies (identical and distinct keys) publish once.

Extend rule 8 in `tools/checks/configuration-persistence.ps1:678-699,829-838`: register the ninth path in `$pgWriters`, `$pgWritesSeen` and `$pgDriverSeen`; require its real driver import and SQL write; permit only INSERT into its named Action tables. Reject its UPDATE, DELETE, upsert, TRUNCATE and DDL, and reject Action-table writes from **every** other module, explicitly the Foundation adapter. Preserve all eight existing writer/table restrictions and driver isolation. Add guard cases for Action adapter forbidden mutations/other-table writes, Foundation adapter Action-table write, another module Action-table write, missing new writer/driver/write and valid ninth-writer INSERT.

## New API, stored proof and phases (P6, P8, P9)

Under `/api/sites/{site_code}` add `GET /findings/{finding_id}/recommendation?revision_id=`, `POST /findings/{finding_id}/recommendation/accept`, `POST /actions/{action_id}/apply`, `POST /actions/{action_id}/observations`, `GET /actions/{action_id}?event_id=|recorded_at=`, `GET /actions/{action_id}/events?event_id=|recorded_at=` and `GET /foundation/changes/{change_id}`. Accept/apply require server-issued recommendation key or Action identity, idempotency key and expected Foundation ID as applicable; apply value/effective time are revalidated. The read contract exposes a tenant/Site/fixture/command-scoped server-authorized `system_demo_capability` with `allowed`, `command`, `fixture_id` and an unavailable reason; POST checks the same authorization again. A client flag grants nothing. Reads return canonical/selected IDs, origin FindingRevision **beside** latest revision/episode notice, assessment/evidence/configuration pins, exact actor/event/cutoff, Site/Finding/Action/change links and pending outcome.

`event_id` selects the exact event and returns its `(recorded_at,id)` ordered prefix. `recorded_at` selects all events with server `recorded_at` through that instant, ordered by `(recorded_at,id)` and including every ID tied at that instant. Neither is a client-time or `occurred_at` cutoff. Both selectors together return typed HTTP 422 `ACTION_SELECTOR_CONFLICT` on Action and event reads, with no silent precedence; preserve the selected selector in child links and reload. Test tied timestamps, exact event, cutoff and conflict. Unknown or wrong-Site Action/Finding/revision/change IDs return 404 without event; missing auth returns 401 and denied command authority 403 without an Action attempt. No Site ActionIndex dependency.

`POST /actions/{action_id}/observations` accepts only fixed `DEMO_REVIEW_NOTE`, explicit `occurred_at` and idempotency key after ACCEPTED, with tenant/Site/Action-scoped SYSTEM demonstration capability. The server sets `recorded_at`; require `accepted_at <= occurred_at <= recorded_at` and no more than 30 days of backdating. Future/out-of-bounds time is typed 422. Identical retries return the same OBSERVED event, conflicting key reuse is 409. OBSERVED is state-neutral and claims no effective policy or benefit; there is no general note-writing route.

New versioned `D-action-records` fixture/loader runs through real accepted Finding/Foundation records with manifest IDs. Include a genuinely eligible pinned Candidate under `reserve-trial-1` and an ineligible missing/conflicting case. If existing S4 demonstration cases lack an eligible Candidate, author accepted evidence through the normal input/ingestion path and keep its demonstration label via `demonstration_label.py`; do not hand-insert an effective claim. Serve pre-accept proposal/unavailability from persisted inputs; store accepted pending, applied pending, stale 409+FAILED, invalid/no-change/backdate, retry, concurrent apply, newer FindingRevision/episode, reload, wrong-Site 404 **without** FAILED, and a valid backdated OBSERVED. Prove exact-event and recorded-cutoff reads preserve server order despite OBSERVED's earlier `occurred_at`.

Commit a versioned API contract fixture under `backend/tests/fixtures/s6_action_api_contract.json` (**new**) keyed by `D-action-records` manifest IDs (`recommendation:1#a`, `action-overview:1#a`, `action-execution:1#a`, `action-history:1#a`, `changes:1#a`).

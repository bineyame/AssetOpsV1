## Outcome and authority

An environment-owned, bounded tick runs S3 `process-jobs`, then S4 `match-findings` for every active tenant/Site, then the existing S4-02c consequence drain. S5-01 cannot mark a selected window CURRENT while relevant upstream work or an unobserved/stopped worker could leave it behind.

## Schedule, state and S5 contract

1. **Owned Site inventory and cadence.** One timer per environment invokes a server-side tick, initially every minute. An active Site is a persisted, tenant-scoped imported Site with registered evidence or explicit schedule enrolment, whose lifecycle is neither `DECOMMISSIONED` nor `ARCHIVED`; `PLANNED` qualifies (including KOBO-001). A Site with live S3 or pending consequence work remains selected until that work is resolved, even if its enrolment changes. Report excluded Sites that still have work; never silently discard it. Enumerate by stable IDs from the persisted Site registry on every tick; “newly activated” in proof means newly imported/enrolled, not a lifecycle transition. Bound Sites, Site-scoped S3 leases, and consequence items per tick with a durable fair cursor. Extend the assessment store's currently global `lease_job` to filter by Site inside the existing assessment writer; its global FIFO cannot provide Site fairness. Run `reconcile_all()` each tick and reconcile every selected Site, including never-assessed Sites; measure its global unbounded cost, without silently omitting it. For each selected Site run S3, then S4 match **every tick**, even with due, leased or FAILED S3 work. The matcher's CURRENT-window rule leaves those windows' episodes unchanged; unrelated current windows can advance. Drain consequence work after Finding commits. A bounded tick may leave work for later ticks.
2. **Concurrency and recovery.** Use database claims for the environment tick and Site stage sequence across hosts; local timer overlap prevention is insufficient. Never overlap S3 leasing/processing and S4 matching on the same Site, including a second host. The matcher fence includes Site recompute-job statuses; report `FindingFenceMoved` as retryable typed S4 `FENCE_MOVED`, not a generic success. Preserve S3's five-minute lease and retry and S4-02c's Site claim/append idempotency. An expired/crashed claim resumes without duplicate output. Bound tick and Site wall time with server-side `statement_timeout` and `lock_timeout`, plus a killable child process per stage for a Python hang. The Site S3 stage bound must be shorter than the five-minute lease; after a killed job, expose its lease expiry and retry, never assert immediate completion. Both DB stall and nonreturning-stage injections must yield typed `TIMEOUT` and retryable work. Give schedule-level discovery/stage failures retry/backoff without advancing success; do not add an independent retry to S3 or consequence rows. A terminal FAILED S3 job stays live and will not be re-enqueued by `reconcile`; expose its ID and `last_error`, alarm, and provide `assess_dispatch requeue --tenant-id --site-id --start --end` through the existing `AssessmentStore.enqueue` path for an operator to re-enqueue that default window after fixing the cause. Document the command and confirm the new DEFAULT selection supersedes the old failure; `assess` creates an EXPLICIT run and is not recovery.
3. **Durable state and health.** Migration `0013` adds `schedule_tick_head` (mutable environment owner, last tick start/success/failure, heartbeat, retry due and claim age), `schedule_site_head` (mutable per-Site claim/stage, selected/processed/deferred counts and last failure), `schedule_cursor` (mutable fair position), and `schedule_enrolment` (mutable explicit Site enrolment). Use DB claims or equivalent expiring ownership in these records; do not add unbounded tick rows by default. A new `backend/assetops_backend/scheduling/adapters/postgres_schedule_store.py` is the sole writer for these tables. Amend `tools/checks/configuration-persistence.ps1` rule 8 to name this eighth writer, its exact tables and allowed updates, with a reviewed S4-02d guard comment; this guard change is in scope and awaits Architect ratification, not pre-approved. Keep durable heads bounded; if attempt history is added, set a retention policy while preserving the latest failure and aggregate counts. Derive S3 backlog from live jobs, S4 backlog from existing `PostgresFindingStore.match_state` / `finding_match_pass` versus `analytic_run_selection.seq`, and consequence backlog from `ConsequenceStore.pending_work` with attempt count/age. Also count pre-0012 latest consequence heads whose read says `STALE` plus `NO_WORK_RECORDED` as distinct `STALE_NO_WORK` entries with Finding/revision IDs. This slice reports those discrepancies and blocks CURRENT; it does not backfill them. A read-only operator report gives each Site and aggregate `RUNNING`, `BACKLOG`, `RETRY_DUE`, `FAILED`, `STOPPED` or healthy idle. Only a completed zero-work tick advances heartbeat; claimed/skipped, failed and timed-out ticks do not. Repeated Site-claim skips, stale in-flight claims, old failures and growing uncapped consequence attempts trigger alarms and documented recovery.
4. **S5-01 consumption.** Add a backend Python scoped read/port taking `(tenant_id, site_id, [window_start, window_end))`. Return the S3 `UNASSESSED|PENDING|CURRENT|STALE_PROJECTION|FAILED` read status and limits, accepted input/source basis, relevant live S3 job IDs/status/errors, selected `analytic_run_selection.seq` and run/revision IDs, `match_state` pass ID/matched-through seq and matched Finding revision IDs, consequence head/work IDs, status/attempts/age (including `STALE_NO_WORK`), schedule state/heartbeat, DB `clock_timestamp()`, and a derived upstream eligibility status with stage/reason. The accepted-source watermark is the selected S3 input basis plus its `analytic_run_selection.seq`; do not use disposition timestamps or a later heartbeat as a commit-order fence (`D-2026-10-11-s3-phase-2-selection-and-read`). Acceptance transactionally creates/widens a job. For each window and its six-hour continuity bracket, CURRENT eligibility requires no intersecting live S3 job, current S3 basis, `match_state.matched = true`, no relevant outstanding or stale-without-work consequence, and a healthy observed schedule; a stopped/unobserved schedule blocks it even with empty queues. Use DB time for heartbeat/STOPPED threshold and avoid app-clock assumptions. First build with work is `PENDING`; an old result with advanced basis/work is `STALE_PROJECTION`; failed with no usable prior result is `FAILED`, preserving typed stage/error. The existing S3 read status, matcher pass and pending-work derivations are authority; S5-01 consumes this seam and applies its separate F1 money rule and same-basis `CURRENT/PRICED` test. Historical IDs remain readable.

## Risks and carries

- S3's existing global `reconcile_all()` can be expensive as Sites grow; measure a multi-Site tick and keep bounded scheduling truthful. Do not omit reconcile to meet a timer budget.
- The matcher fence aggregates all Site recompute-job statuses; its `string_agg` can grow without bound. Track it alongside global reconcile cost. Serialise S3 and S4 for a Site even across hosts.
- S4 matching currently scans a Site's selected reads. Large Sites may require a reviewed bounded cursor or dirty-window selection to meet the tick limit; do not mark a partially matched Site caught up.
- S4-02c retries have no terminal cap: a deterministic failed row can append about 90 attempts/day. Keep the growing count and backlog observable and alertable; do not hide it by reporting only due work.
- A hung consequence runner can hold a Site claim while later ticks report skipped. Treat repeated skips/claim age as a stopped-progress alarm, with operator recovery; do not count skipped as success.
- Backdated configuration/model changes can dirty assessed windows without a fresh evidence job. The S3 reconcile and S4 basis comparison must detect them before CURRENT is possible.
- Do not install the schedule on an owner-visible host before `I-late-reading-series-and-money-limit` lands: it would automatically move late evidence to the run-1 too-low consequence on the S4-02b money panel.
- S4-02c I3/I4 remain open: clock skew now affects heartbeat/STOPPED if application time is used, and concurrent ingestion chunks can move a basis while a tick runs. Use database time and live-job/selection/match comparisons; carry I4 to the independent review rather than treating this schedule as its resolution.

Registry comparison: `queue_baseline_nodes` already contains `I-analytic-finding-worker-schedule`; keep it there and map its `task` to S4-02d. S5-01's `I-site-overview-read` remains gated on this node and the separate F1 node. No baseline node moves.

Out of scope: F1 late-reading sequence semantics (`I-late-reading-series-and-money-limit`), new cohort or fuel model, new owner UI/copy, S5-01 implementation, real gateway source-time attestation, and a general estate scheduler for unrelated domains.

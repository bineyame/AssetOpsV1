## Outcome and authority

A genuinely accepted late generator-power mean that can alter an existing Site FindingRevision's `fuel-cost-1` technical input creates durable consequence work atomically with acceptance. Before drain, the old consequence is `STALE/TECHNICAL_INPUT_CHANGED` (or `PENDING` without a head) with a real queued work ID. Draining that **same** FindingRevision yields a current `QUANTITY_UNAVAILABLE/POWER_NOT_IN_ASSESSMENT_INPUTS` revision: the late reading was not an input to its cited analytic run. S3 `process-jobs` and S4 `match-findings` must re-evaluate the Finding and append a revised FindingRevision before a new `CURRENT/PRICED` consequence can become S5-01 eligible. All revisions remain inspectable. A stale read alone does not complete this slice.

## Acceptance, work and worker contract

1. **Migration 0012 and constraints.** Add `EVIDENCE_ACCEPTED` and a tenant/Site-scoped FK to exact `accepted_evidence.id` on `financial_consequence_work`. An evidence row records accepted ID, Finding ID, selected FindingRevision ID and half-open affected interval. Drop `financial_consequence_work_finding_revision_once`; replace it with a partial unique index on `(finding_revision_id) WHERE cause = 'FINDING_REVISION_APPENDED'`. `CREATE OR REPLACE FUNCTION financial_consequence_dirty_on_finding_revision()` with `ON CONFLICT (finding_revision_id) WHERE cause = 'FINDING_REVISION_APPENDED' DO NOTHING`. Keep assumption uniqueness. Add a partial unique index on `(accepted_evidence_id, finding_revision_id) WHERE cause = 'EVIDENCE_ACCEPTED'`. Replace `financial_consequence_work_cause_shape` with an explicit three-arm CHECK: assumption has only assumption locator; Finding append has only Finding locator; evidence has exact accepted ID plus Finding and revision locators, with other cause locators null. Preserve range and scope checks; index pending selection by tenant/Site and attempt lookup by `(work_id, attempt_no DESC)`. Add nullable typed `no_op_reason` to `financial_consequence_work_attempt`: present only on a `SUCCEEDED` attempt with empty `consequence_revision_ids`; normal success or failure has it null. Keep append-only tables and one-success index. Upgrade preserves 0011 work and bootstrap rows. Downgrade restores the original 0011 trigger body, two-arm CHECK and unique constraint, but **refuses with a clear error if any `EVIDENCE_ACCEPTED` work row exists**; prove both refusal and empty-case downgrade. It never deletes append-only evidence or work.
2. **Transactional enqueue.** Migration 0012 adds an `AFTER INSERT` trigger on `ingestion_disposition` for `decision = 'ACCEPTED'`, joined to its stored `accepted_evidence_id`. It runs inside `decide_chunk` only for a genuine accepted disposition; duplicate, conflict, rejection and exact replay do not enqueue. Filter on the stored, binding-derived `accepted_evidence.role = 'generator_power'`, never a client role. Select existing tenant/Site Findings by strict half-open overlap with their latest revision's episode; zero-width episodes do not overlap. Here and in the worker, **latest eligible FindingRevision** means the Finding's highest `revision_no` in the same tenant/Site; lifecycle/source gating is left to `quantify` and the read, not the selector. Insert one row per accepted ID and selected revision using the evidence partial unique index. Coarse selection may no-op later but must not omit a possibly affected Finding. Trigger failure rolls back acceptance and disposition. Retain the 0011 FindingRevision-insert trigger so new/revised Findings enqueue independently. Before either trigger selects/inserts work, both take the same transaction-scoped Site advisory lock keyed by `financial_consequence_enqueue:` plus `site_id`. At READ COMMITTED, select after acquiring the lock so acceptance racing a FindingRevision append cannot miss its committed revision. Prove with two Postgres connections. Rule 8 remains unchanged: no Python module inserts `financial_consequence_work`.
3. **Scoped drain.** Explicitly dispatch all three causes; an unknown cause records a typed failure (or is skipped) and never falls through to assumption-range recompute, including if phase 1 deploys before phase 2. For `EVIDENCE_ACCEPTED`, queued revision is a locator. Recheck tenant/Site, accepted disposition, bound role/asset, strict interval overlap, Candidate episode/window and latest revision. If queued revision has been superseded, record a typed successful no-op for its work row; the new revision's 0011 insert work derives its consequence. Irrelevant role, asset or window also no-ops without consequence append. A transiently missing/closed source records a typed FAILED attempt and remains retryable; wrong-Site scope fails without fallback. Derive only from that revision's accepted public analytic inputs. The same-revision late reading becomes `QUANTITY_UNAVAILABLE/POWER_NOT_IN_ASSESSMENT_INPUTS` after drain; never substitute it into the old analytic input set. Existing basis uniqueness and per-revision append lock return the existing consequence ID on unchanged/repeated work, concurrent runs and append-then-crash retry. A work item succeeds only when every selected target appended, replayed or no-opped.
4. **Run plan and retry.** Extend the server-side CLI as a **one-shot** bounded `run --tenant ... --site ... --limit N` under an external one-minute timer (document a Windows Task Scheduler or systemd timer invocation, owner, cadence and recovery). Use an explicitly configured tenant and Site; the current development-tenant-only CLI is not an active-Site iterator and must not silently claim production all-Site coverage. For each scoped run, acquire `pg_try_advisory_lock` keyed by `financial_consequence_runner:` plus `site_id` and hold it through selection and processing; if held elsewhere, report the skipped Site. Existing per-item `record_attempt` locks remain. No mutable lease or due-time column is added. Retry eligibility is derived from the last FAILED attempt's `finished_at` and `attempt_no`: use a fixed exponential schedule (1, 2, 4, 8, 16 minutes, then 16 minutes for later failures); there is no terminal cap, and pending work remains visible. Use an injectable clock so due/not-due and later scheduled retry tests do not sleep. One run processes each selected ID at most once and reports selected, appended, replayed, no-op, failed, deferred and backlog counts with Site scope. Price/Finding work uses this runner too. Test two runners, restart, bounded batch, failure, retry and append-then-crash without duplicate basis.
5. **Reads and S5 gate.** Extend `PostgresConsequenceStore.chain()` pending SQL to match unsucceeded `EVIDENCE_ACCEPTED` rows for the selected Finding ID (with revision locator retained for diagnostics), as well as existing Finding and assumption causes. Show queued only when an actual unsucceeded work row touches the selected read; if stale with no work, expose typed `currentness.reasons` code `NO_WORK_RECORDED`, retaining the reviewed `REASONS["STALE"]` sentence. Add no new `REASONS` copy. S5-01 uses money only for a `CURRENT/PRICED` consequence on the same Site, window, FindingRevision and basis after re-evaluation. No new UI copy or panel is authorized here.

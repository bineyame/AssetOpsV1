## Outcome and authority

An accepted late generator-power mean that can alter an existing Site FindingRevision's `fuel-cost-1` input creates durable consequence work in the same database transaction as acceptance. The Site read shows the old consequence as `STALE` (or `PENDING` if no consequence exists) with real queued work, then a scheduled, retryable worker derives and appends the new exact-basis consequence. The S5-01 selected-window read may use money only after that consequence is `CURRENT` and `PRICED` for its selected FindingRevision and window. A fresh stale read alone does not complete this slice.

## Acceptance, work and worker contract

1. Add a migration to extend `financial_consequence_work` with an `EVIDENCE_ACCEPTED` cause and a tenant/Site-scoped FK to the exact `accepted_evidence.id`. Keep existing assumption and FindingRevision causes and rows valid. Each new row identifies the accepted evidence, target Finding and latest eligible FindingRevision at enqueue time, and its half-open affected interval. Constrain cause shape, range, scope and a unique `(accepted_evidence_id, finding_revision_id, cause)` key; duplicates and conflicting evidence create no second row. Index pending selection by Site and due time. Preserve append-only evidence, work and attempt history. Migration upgrade/downgrade and pre-existing rows must be proved.
2. In the S2-02 acceptance transaction, after a genuinely new accepted evidence ID is returned, select potentially affected existing Site Findings by coarse half-open interval overlap with the accepted interval and the **server-bound** `generator_power` role (`fuel_cost.POWER_ROLE`). Insert scoped work before commit. If the insert fails, acceptance and its disposition roll back; it must never leave a committed accepted reading with a lost required work row. Exact replay, duplicate, conflict and rejected decisions do not enqueue. If the transaction contains several accepted intervals, each exact accepted ID is deduplicated against its target. Do not trigger on a client-declared role or from a later read. Broad selection may queue a candidate that later no-ops, but must not omit a possibly affected Finding. FindingRevision insertion retains migration 0011's own trigger so findings first created after acceptance also get work.
3. The worker treats the queued revision as a locator, then rechecks tenant/Site, accepted disposition, bound role/asset, half-open interval overlap, candidate episode/window and the **latest eligible FindingRevision** for that Finding at processing time. Derive against that exact current revision and its accepted public inputs only. A superseded or irrelevant target records a successful typed no-op; if a newer eligible revision exists, process that revision once (its insertion trigger may also queue it). No-op on unrelated roles/assets/windows without appending a consequence. A missing or closed source stays typed and retryable when transient; wrong-Site scope never falls back. Price and technical basis selection remain the reviewed S4-02b contract; no extra amount or quantity shortcut is introduced. The existing unique consequence basis and append lock must make unchanged or repeated work return the existing ID, including concurrent workers and an append-then-crash retry.
4. Make the run plan operational: extend the server-side CLI to drain a configured tenant/Site (or a scoped active-Site iterator) on a documented one-minute recurring service/timer, with bounded batch size, a database claim/lease or equivalent single-consumer lock, persisted retry eligibility/backoff, and a restart-safe failure record. A failed item remains visible but cannot hot-loop inside one run; a later scheduled run retries it. Print/record selected, appended, replayed, no-op, failed and backlog counts with Site scope; document deployment invocation, ownership, cadence and recovery. The scheduler must not rely on a user opening Financials. Existing price/Finding work uses the same runner. A work item becomes succeeded only after all its selected targets have safely appended/replayed or no-opped; crash and concurrent-run tests must prove eventual drain without duplicate consequence basis.
5. Keep the consequence read's `CURRENT`/`STALE`/`PENDING`/`HISTORICAL` and typed reasons. Show queued/pending status only when a real unsucceeded work row touches the selected revision; if currentness is stale but no work exists, report that discrepancy explicitly and do not claim queued. S5-01 uses only a `CURRENT`/`PRICED`, same Site/window/FindingRevision/basis consequence after work finishes. No new UI copy or mock panel is authorized here; a necessary owner-facing copy change reopens `USER_REVIEW_REQUIRED` and its checkpoint.

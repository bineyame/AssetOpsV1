## Result and boundary

An imported KOBO-001 Draft can be created and run from one selected effective, registered Postgres Foundation plus SignalBinding snapshot. The Lab shows the exact frozen Foundation revision, binding revision, snapshot schema/hash and selected source time after reload. A later configuration publication affects a new Draft, never an existing one. Existing unimported YAML Sites retain their current Lab path. Imported Commit remains unavailable until S2-02; this slice creates no accepted Evidence, receipt, durable gateway queue or V3 identity.

S1-02 stores canonical combined snapshot bytes and SHA-256 in each binding revision. The S1 download (`GET /api/sites/{id}/foundation/snapshot?at=&knowledge_at=`) is development-tenant scoped, not gateway authenticated. S2-01a uses the same immutable contract through a server-side read; do not claim a credential boundary that S2-02 has not built. Select the basis at the run's declared source interval start and optional `knowledge_at` (API-only for S2-01a; default server now, resolved and frozen at setup). Both the Foundation and binding set must be valid at that start and recorded at that knowledge instant. A snapshot superseded by the time of setup may be selected only by an explicit earlier `knowledge_at` at which it was registered; pin that pair, the two resolved instants and the verified stored bytes/hash. Never silently substitute a currently known correction for the requested historical basis.

For a selected historical basis, validate original registration identity from its stored snapshot and immutable publication references; a later edit to current gateway/source rows must not make those pinned bytes unavailable. Report current registration gaps separately and continue to refuse an incomplete new/current acquisition snapshot. Selected Foundation content gaps still block Lab setup. A selected revision that was never registered for the requested time, has missing bytes, a bad hash or unsupported schema remains unavailable with the actual reason shown. Do not fall back to the YAML Site or another Foundation. This closes S1-02 carry n5 for historical selection, without adding gateway authentication or permitting current gaps to claim readiness.

One immutable basis must cover every public report's `source_time` in the run, or setup refuses before allocating a Draft. The run interval is half-open, but the current kernel/observation path can emit a public reading at its final boundary (`end_time`); therefore check that instant as well as the interval interior. When the selected registered validity ends at the run's `end_time`, refuse that setup with the boundary named. Do not produce a reading that S2-02 must reject knowingly. Crossing a Foundation or binding boundary requires separate runs; multiple bases in one run are outside S2-01a.

## Acceptance criteria

1. **Registered selection.** Imported KOBO-001 appears in Lab setup with its available effective Foundation/binding basis. Setup reads the S1 Postgres registry and pinned combined snapshot, verifies its stored SHA-256 and schema, and validates all possible public source times against the selected pair's original valid periods. It refuses a mismatched requested version, knowledge instant or period with a specific reason and no Draft. S1 configuration Readiness remains about declared mappings, not live telemetry.
2. **Kernel input.** Map the selected public Site topology, reserve control, registered device/source and signal roles to the existing Lab run input. Preserve scenario and model-profile resolution and private Lab causes/oracle inside Lab storage. The public device report boundary may contain only observations available to a device and public registered identifiers; it cannot read or serialize world causes, controller intent or oracle. The S2-01b adapter will consume that report boundary.
3. **Frozen run.** Persist the exact selected Foundation revision ID/version, binding-set ID/version, snapshot schema/hash, resolved source-start time and `knowledge_at`, and canonical snapshot bytes or a durable immutable reference on the Draft. Reopen Draft, execution and Stage reads after process restart and show the same basis. If a later Foundation or binding publication changes the current basis, the old run keeps its original basis and a new run selects the new one. An explicit earlier source time with default knowledge selects the now-known correction valid then; an explicit earlier `knowledge_at` can recover a superseded-as-of-now basis that was registered at that knowledge time. Neither selection silently uses today's valid-time version.
4. **Controls and history.** Imported registered Draft setup, start, step and run-to-end operate through the frozen basis. A missing or unavailable basis keeps those controls blocked with a useful reason. `GET /runs/{run_id}/stage` and run history for pre-import YAML Drafts remain read-only and visibly labelled `LEGACY_FILE`; a pre-import Stage cannot be stepped, reinterpreted or Committed under a new registration. New imported-run Stage inspection is labelled as registered but makes no accepted-evidence claim. Both the UI Commit control and server Commit route refuse every imported run until S2-02 delivery exists, including a newly completed one.
5. **Failure integrity.** A Postgres outage, unsupported snapshot schema, missing bytes or digest mismatch fails closed and leaves no partial Draft or run advancement. Current registration edits cannot rewrite the pinned bytes or deny a verified historical selection solely by changing current identity rows. Keep current configuration gaps as a refusal for a new/current acquisition snapshot. Test historical availability separately from byte immutability under `D-2026-10-08-s2-lab-snapshot-selection-and-run-boundary`; no cached/YAML substitute is allowed.

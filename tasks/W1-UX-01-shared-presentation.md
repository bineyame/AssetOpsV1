## Result and contract

Build one shared `ProductStatus`/`ProductLimitation` map, small exact-reference disclosure and `HeadlineVisualCard` (suggested names) in `frontend/src/ui/`. Components accept semantic **already-read** state and explicit evidence; they never derive currentness, outcome, amount, zero, completeness or source health. Use the mock hierarchy: answer headline, small visual, then “What this means / What to do”. Material missing evidence, stale/pending/refused state, scope, consequence limit and plain “as of <time>” bound stay beside the headline outside tabs and disclosures. Empty/unknown are first-class states. Give graphics readable text, support keyboard access and avoid 390 px overflow. Substantive method, coverage, comparison and calculation go to the owning Analysis/Evidence/Plan/History/Verification destination. Add a contextual Analysis tab only where no suitable destination exists; never add an empty tab. The same named destination is visible as a keyboard-accessible tab or view link at 1440 and 390 px, carrying selected Site, period, revision and object context. Directory/index rows and compact cards link to the owning detail or Analysis view. A closed “How this was worked out” disclosure holds only a few labelled exact references, IDs, versions, raw reasons or support fields. Preserve exact record links, URL selectors and historical selectors.

The shared map owns cross-screen states. It wraps existing `dispatchWords.ts`, `findingWords.ts`, `findingPresentation.tsx`, `actionPresentation.tsx`, `EvidenceClaimLimit.tsx`, `SiteFinancials.tsx`, `FindingConsequence.tsx`, `OverviewFindingList.tsx` and merged `verificationWords.ts`; each slice replaces duplicate shared entries while retaining domain-specific words. Approved navigation labels Site, Evidence, Finding, Action and Verification need nearby first-use explanations: a Finding is a bounded conclusion about an assessed period; an Action is proposed or recorded work; Evidence is the records used; Verification is a measured trial outcome when a result exists. Analysis is an approved destination. These labels do not imply a confirmed fault, applied work or verified result. Prefer “What the readings can support”, “Reporting status” and “Battery condition: cannot yet be judged”.

Example map entries must be checked against typed reads: `UNASSESSED` → “We have not checked this period”; `PENDING_REASSESSMENT` → “New readings call for another assessment” (no claim that processing has started); `STALE` → “This result may miss newer readings”; `UNKNOWN` → “We cannot judge this yet”; `CURRENT` → “Using the latest checked readings” only when proved; `INCONCLUSIVE` → “Could not conclude”, with any known failure still visible; `INEFFECTIVE` plus measured reserve/service `GUARDRAIL_FAIL` → **“Trial missed a safety or service limit”**, with failed metric, value, threshold and unit beside it; target-only `INEFFECTIVE` → **“Target not met”**. Key outcome wording on **(outcome, reason, source class)**, not outcome alone. For `VERIFIED`, say the measured target was met within the **five-minute sampled** reserve/service guardrails; never imply continuous physical SOC proof. Demo-source outcomes visibly say **policy trial** and **no savings or realized benefit**. Keep S6-02b's guardrail-fail, target-miss and unknown-fact sentences as the wording floor. Reason families get a cause sentence and next useful step. Unknown codes get neutral “We cannot explain the limit from this record”, with labelled exact code only in detail. Money distinguishes “No current amount can be shown” from “No price recorded”; never substitute `$0`. Refusal differs from proved empty. Authored examples, generated tests and simulator outputs retain explicit demonstration/simulated source qualification and never appear as field readings.

Extend `frontend/src/test/productVocabulary.ts` and `.json` with a versioned W1 term set and pattern matcher for raw enum/reason-code shapes, UUIDs, digests, rule/model versions, cursor/watermark mechanics, internal analytics phrases (`claim ceiling`, `claim limit`, `basis fingerprint`, `typed reason`) and implementation senses of `run`, `binding`, `stage`, `commit`, `fixture`, `payload`. Ordinary operational wording such as “generator ran” is allowed. Scan rendered API text, SVG labels/titles, badges, collapsed summaries, headings and accessibility attributes. This ban also applies in Analysis and Evidence prose; labelled exact traceability data is allowed there. No raw code appears in a collapsed control's accessible label. Source/user-owned names may appear where identity is the subject, with a label and explanation.

**Staged ratchet:** UX-01 proves the new term set and pattern matcher with positive and deliberate-leak mutation tests, then opts in only its three migrated routes. UX-02 through UX-05 opt in each owned route as that route migrates. Keep existing scans on unmigrated routes; no exemptions or weakened assertions to make them pass. The umbrella final gate requires all 26 W1 routes on the full set. The small disclosure is **scanned**, never exempted wholesale: scan its prose against a narrower technical list of unexplained implementation words and raw status labels, while permitting only individually labelled exact reference values. Retain the current single-value exemption rule; no container, whole screen or response exemption. Route the disclosure scan refinement under `D-2026-10-04-plain-language-analysis-views` to Architect before implementation.

Shared acceptance test: for every unassessed, pending, stale/non-current, unknown, refused, withheld-money and proved-zero case, render with the disclosure closed and assert the plain state sentence plus scope and “as of <time>” bound remain visible outside it. Every consumer repeats this check for its states. Keep a populated, missing and refused case per family, and prove the scan saw nonzero text. Include an unknown-value chart case: draw a distinct “not known” mark and text, never a zero-length bar. Inspect existing `Advanced`/`Disclosure` primitives before adding a new one.
